# チャージバック（決済の争い）の受け方

**実装 2026-08-22。**この文書は、実装したもの・**あえて実装しなかったもの**・
まだ決まっていないことを、同じ場所に置くためのものである。

---

## 0. いちばん大事な主張

> **争いが起きたことと、返金されたことは別である。**

申し立てを受けた時点では、**まだ何も返っていない**。ここで受取権を
取り消すと、**こちらが勝ったときに取り上げたものを返せない**——外部の
ウォレットへ渡したものは、こちらからは戻せないからである。

だから、**敗訴ではじめて返金として扱う**。

---

## 1. 状態

事業者（Stripe）の語彙を、こちらの 5 つへ畳む。

| こちらの状態     | Stripe                                                               | 意味                                             | 精算を止めるか |
| ---------------- | -------------------------------------------------------------------- | ------------------------------------------------ | -------------- |
| `warning`        | `warning_needs_response` / `warning_under_review` / `warning_closed` | カード会社が調べ始めただけ。**まだ争いではない** | **止めない**   |
| `needs_response` | `needs_response`                                                     | 申し立てを受けた。期限までに証拠を出す           | 止める         |
| `under_review`   | `under_review`                                                       | 証拠を出し、審理中                               | 止める         |
| `won`            | `won`                                                                | こちらが勝った                                   | 止めない       |
| `lost`           | `lost`                                                               | こちらが負けた。**もう引かれている**             | 止めない       |

⚠️ **`warning` を争いと同じにしない。** 申し立てにならずに消えることも
ある。同じ扱いにすると、消えた警告のぶんまで精算を止め、**作家さまへの
お支払いが理由なく遅れる**。

⚠️ **知らない状態は畳まない。** Stripe が語彙を増やしたとき、こちらが
勝手に「決着した」と読むのがいちばん困る。無視して `webhook_events` に
記録だけ残す。

---

## 2. 受けるイベント

`charge.dispute.created` / `.updated` / `.closed` /
`.funds_withdrawn` / `.funds_reinstated` の 5 つ。

⚠️ **イベント名で決着を判断しない。** `closed` が届いても、勝ったのか
負けたのかは `status` にしか書いていない。名前で分けると、**勝った争いを
返金として記録する**ことになる。

⚠️ **`funds_withdrawn` を敗訴と読まない。** 引き落としは審理中にも
起きる（あとで戻る）。負けたかどうかは `status` が言う。

---

## 3. 1 行に束ねる

申し立て・審理・決着で**別々の知らせ**が届く。`(provider, dispute_ref)` の
UNIQUE で 1 行に束ねる。

⚠️ **識別子で束ねないと、1 件の争いが 3 件に増え、精算が 3 重に止まる。**

⚠️ **決着からは戻さない。** 事業者の知らせは前後して届く。`closed` の
あとに `created` が届いたとき、素直に上書きすると**決着した争いが
開き直り、精算が理由なく止まり続ける**。

⚠️ **警告へも戻さない。** 申し立てを受けたあとに警告の知らせが遅れて
届くことがある。戻すと「まだ争いではない」ことになり、歯止めが外れる。

---

## 4. 敗訴を返金として記録する

⚠️ **`charge.refunded` は届かない。** 敗訴で引かれても、事業者は返金
（Refund）を作らない。**ここで記録しなければ、どこにも残らない。**

記録しないと、帳簿の上では持っていないお金を持っていることになり、
**作家さまへその分までお支払いする**ことになる。

|          |                                                 |
| -------- | ----------------------------------------------- |
| 事由     | `provider_initiated`                            |
| 実行者   | `provider`（**運営の誰かを紐づけない**）        |
| 負担者   | `platform`（**作家さまへ回さない**）            |
| 冪等の鍵 | 争いの識別子を `provider_refund_ref` として使う |

⚠️ **運営が被る。** 場を開いている側が備える筋のものである。作家さまへ
転嫁すると、**身に覚えのないカード不正で作家さまの売上が削られる**。

全額なら、既存の全額返金と同じ道を通る——受取権の取消、発行ジョブの
扱い（`processing` は取り消さず注記のみ）、在庫の解放、購入者への知らせ、
代理店へ渡す `order.refunded`。

---

## 5. 争いのあるご注文を、精算からいったん外す

**決定 B・2026-08-22。それまでは「精算そのものを止める」形だった。**

決着していない争いのあるご注文は、**その月の精算に載せない**。残りは
そのままお支払いする。外したご注文は、決着したあとの精算に含まれる。

### なぜ変えたか

前は「争いのあるご注文が 1 件でもあれば、その作家さまの精算を確定できない」
としていた。安全側ではあるが、**副作用が大きすぎた**。

⚠️ **争いは期限で閉じない。** 返金の窓は日が来れば閉じるが、争いはカード
会社が決着させるまで開いたままで、**数週間から数か月**かかる。

> **1 万円の争いが 1 件あるだけで、100 万円の精算が数か月止まる。**

作家さまから見れば、身に覚えのない他人のカード不正で、自分の売上が丸ごと
止まることになる。**筋が悪い。**

### 拾い直しと対になっている

⚠️ **外すだけでは、外したご注文が永久にお支払いされない。**

候補を集める条件（`listCandidates`）は、もともと「**その期間に入金された**
ご注文」だった。この条件のまま外すと、翌月は翌月に入金されたご注文しか
見ないので、外したご注文は二度と候補に上がらない。

そこで条件を「**その期間の終わりまでに入金され、まだどの精算にも載って
いない**」へ広げた。決着して争いが閉じれば、次の締めで自然に拾われる。

⚠️ **この 2 つは対である。片方だけ戻さないこと。** 外す処理を残したまま
条件を狭めると、静かにお支払い漏れが起きる。DB の部分 UNIQUE 索引が二重
払いを止めるので、広げた側は安全に倒れている。

### 数え方

⚠️ **警告（`warning`）は外さない。** カード会社が調べ始めただけで、申し立てに
ならずに消えることもある。外すと、消えた警告のぶんまでお支払いが理由なく
遅れる。外すのは `needs_response` と `under_review` だけ。

⚠️ **外したご注文の返金の窓は数えない。** 今回のお支払いに含まれていない
のだから、その窓が開いていても止める理由が無い。数えると、争いのある
ご注文のせいで確定できない精算ができ、変えた意味が消える。

### 外したことを画面に出す

⚠️ **合計だけ減らして理由を残さない、をしない。** 差し戻しを明細に載せて
いるのと同じ理由である。作家さまは「なぜ今月は少ないのか」を読めないと、
ご自分に落ち度があったのかとご心配される。

精算に `deferred_dispute_count` と `deferred_dispute_amount` を焼き付け、
運営の画面と作家さまの画面の両方に出す。

⚠️ **合計には入れない。** 画面へ理由を出すためだけの数である。
⚠️ **「来月これだけ入ります」と読ませない。** 負ければ返金となり、お支払いは
発生しない。
⚠️ **どなたのご注文かは作家さまへ書かない。** 買った方を探しに行く道を
作らない。

### 確定のときの網

`canConfirmPayout` の `PAYOUT_DISPUTE_OPEN` は残してある。ただし**意味が
変わった**。

下書きを作る時点で争いのあるご注文は外れているので、普通はここに引っかから
ない。引っかかるのは、**下書きを作ってから確定するまでのあいだに新しく
争いが起きたとき**だけ。

⚠️ **やることは「待つ」ではなく「作り直す」。** 作り直せばそのご注文が
外れ、残りは今回お支払いできる。画面の文言もそう出している。

| 符号                  | 文言                                     |
| --------------------- | ---------------------------------------- |
| `PAYOUT_WINDOW_OPEN`  | 「**期間が過ぎてから**確定してください」 |
| `PAYOUT_DISPUTE_OPEN` | 「**下書きを作り直してください**」       |

## 6. DB が止めること

アプリの判定に穴が開いたときの最後の砦。

| 制約                                     | 止めること                                       |
| ---------------------------------------- | ------------------------------------------------ |
| `payment_disputes_provider_ref_unique`   | 同じ争いが 2 行になる                            |
| `payment_disputes_status_known`          | 知らない状態が「永久に精算を止める行」として残る |
| `payment_disputes_reason_known`          | カード会社の文字列がそのまま流れ込む             |
| `payment_disputes_closed_has_time`       | 決着したのに「いつ終わったか」が読めない         |
| `payment_disputes_refund_only_when_lost` | 勝った争いに返金がぶら下がる                     |
| `payment_disputes_amount_positive`       | 0 円の争い                                       |

## 7. あえて実装しなかったもの

- **証拠の提出**。Stripe へ証拠を出す口は作っていない。運営が Stripe の
  画面から出す。こちらから出す口を作ると、**出したつもりで出ていない**
  状態を作りうる
- **争いの一覧画面**。管理画面から見る導線が無い。いまは注文の記録と
  監査ログから追う
- **運営への知らせ**。⚠️ **これは穴である**（次項）
- **一部の争い**。争われている額が注文の総額に満たない場合、全額返金の
  道は通らず、既存の一部返金と同じく人の確認へ回る

## 8. 気づく仕組み（2026-08-22 追記）

Stripe の申し立てには**期限**があり、**過ぎると自動的に負ける**。
こちらの言い分に関わらず、証拠を出さなかったという理由で敗訴になる。
そのうえ返金は運営が被る——**気づかないことが、そのまま損になる**。

運営の指標（`/admin/operations`）へ「カード会社との争い」を足した。

| 状態                     | 色     | 文言                                                                         |
| ------------------------ | ------ | ---------------------------------------------------------------------------- |
| 争いが無い               | 平常   | —                                                                            |
| 決着していない争いがある | **黄** | 決済事業者の画面で内容を確かめ、証拠を出す準備をしてください                 |
| 提出期限が近いものがある | **赤** | 提出期限が迫っているものが N 件あります。…**期限を過ぎると自動的に負けます** |

⚠️ **「1 件ある」だけでは足りない。** 急ぐのかどうかが分からないと、運営は
結局 Stripe の画面を見に行くことになり、気づく仕組みを作った意味が半分に
なる。だから証拠の提出期限（`evidence_due_at`）も持ち、**何件急ぐのか**を
文言に出す。

⚠️ **期限が近いかどうかの境目は 3 日**（`disputeDueSoonDays`）。証拠を集めて
出すのに数日かかるので、前日に赤くしても間に合わない。

⚠️ **期限を持たない行は「急ぎ」に数えない。** 分からないものを急ぎにすると、
毎日赤いままになり、本当に急ぐものが埋もれる。

この指標は既存の**運営への知らせ**（`UD-1102`）にそのまま乗るので、
設定してあればメールや外部の受け口へ届く。

### まだ無いもの

- **争いの一覧画面。** 件数は指標に出るが、どの注文かは注文の記録と
  監査ログから追う
- **証拠の提出。** Stripe の画面から行う（§7 参照）

## 9. 判断が要ること

- **受取済み（`claimed`）まで取り消すか（2026-08-22 に確認）。** いまは
  `REFUND_REVOKE_CLAIMED_ENABLED` に従い、**既定は取り消さない**。
  ⚠️ 外部のウォレットへ渡ったものは、こちらの帳簿に「取消済み」と印を
  付けても**実物は戻らない**。取消の知らせを相手が尊重するかは**未確認**で、
  確認できるまでは有効にしない、という判断である。
  ⚠️ **これは損を受け入れる判断である。** カード不正では、品物は不正利用者の
  手に残り、お金は運営が被る
- **証拠の提出をこちらの画面から行うか。** いまは Stripe の画面
- **争いの一覧画面を作るか。** 件数は運営の指標（§8）に出るが、どの注文かは
  注文の記録と監査ログから追う
