# 返金と精算（`UD-104` / `UD-119`）

**状態**: 🟡 仕様（実装前）
**決定日**: 2026-08-20（一般的な仕様で確定。**後から変える前提**で設計する）
**前提**: 運営が販売者となる（`Stripe Connect` は使わない）。作家さまへは別途振り込む

---

## 0. この文書の一番大事な主張

**「あとから変える」を、仕様ではなく設計で受け止める。**

決めた数字——返金を受け付ける期間、締め日、最低支払額——は、
**運用してみれば必ず変わる**。変わったときに困るのは、数字そのものではなく、
**過去の記録の意味が変わってしまうこと**である。

| うっかりやると                              | 何が起きるか                                                              |
| ------------------------------------------- | ------------------------------------------------------------------------- |
| 返金期間を毎回「決済日 + 設定値」で計算する | 14 日 → 30 日に変えた瞬間、**精算済みの注文が「まだ返金できる」に化ける** |
| 精算額を毎回集計し直す                      | 手数料率を変えた瞬間、**過去に振り込んだ額と画面の額が食い違う**          |
| 最低支払額を設定から毎回読む                | 変えた瞬間、**過去の繰越額の説明がつかなくなる**                          |

どれも「あとで気づく」類の壊れ方で、気づいたときには作家さまへの
説明ができなくなっている。手数料率で既に採った**スナップショット原則**を、
返金と精算にも同じ形で通す。

---

## 1. 三層に分ける

```
①  設定（いま何を使うか）        DB・オーナーが変更・監査に残る
        │  読むのは「新しく記録を作るとき」の一度だけ
        ▼
②  スナップショット（そのとき何を使ったか）   注文・返金・精算の行に焼き付ける
        │
        ▼
③  判断（純粋関数）              ②を引数で受け取る。①を知らない
```

⚠️ **③ が ① を直接読まないこと。** 読むと、過去の記録を判定し直したときに
今の設定で判定されてしまう。**判断に要る値は、必ず引数で渡す。**

⚠️ **① が未設定のとき、環境変数へ黙って落ちないこと**（`UD-109` と同じ）。
DB と環境変数で違う値が使われる「二重管理」を作らない。未設定なら
**その機能を止める**——止まっているほうが、間違った額で振り込むより良い。

### 変えてよいもの・変えられないもの

|                          | あとから変えられるか                | 理由                       |
| ------------------------ | ----------------------------------- | -------------------------- |
| 返金を受け付ける期間     | ✅ 変えられる（**新しい注文から**） | 注文ごとに期限を焼き付ける |
| 締め日・支払日           | ✅ 変えられる（**次の締めから**）   | 精算に期間を焼き付ける     |
| 最低支払額               | ✅ 変えられる（**次の締めから**）   | 精算に焼き付ける           |
| 振込手数料の負担         | ✅ 変えられる（**次の締めから**）   | 精算に焼き付ける           |
| 手数料率                 | ✅ 変えられる（**新しい注文から**） | 実装済（`UD-109`）         |
| **過去の注文の返金期限** | ❌ 変わらない                       | 焼き付けてある             |
| **過去の精算の内訳**     | ❌ 変わらない                       | 焼き付けてある             |

## 2. 決めたこと（一般的な仕様）

### 2-1. 返金（`UD-104`）

| 項目               | 決定                                                                   |
| ------------------ | ---------------------------------------------------------------------- |
| 受付期間           | **決済完了から 14 日**                                                 |
| 対象               | **お客様のご都合による返品・交換は受け付けない**（デジタル作品のため） |
| ただし返金する場合 | 下の表のとおり                                                         |
| 一部返金           | **自動処理しない**（記録のみ）。既定の方針を維持                       |

**発行がどこまで進んだかで線を引く。** 発行してしまうと回収できない
（`UD-511`）ので、そこが唯一の自然な境界である。

| 注文の状態                           | 返金                     | 受取権             | 発行ジョブ                         |
| ------------------------------------ | ------------------------ | ------------------ | ---------------------------------- |
| お支払い済み・**受取りがまだ**       | **全額返金する**         | `issued → revoked` | 無し                               |
| 受取り済み・**発行待ち**（`queued`） | **全額返金する**         | `claimed` のまま   | `queued → cancelled`               |
| **発行処理中**（`processing`）       | 原則しない（個別判断）   | `claimed` のまま   | **`cancelled` にしない**。注記のみ |
| **発行済み**                         | 原則しない               | `claimed` のまま   | `succeeded` のまま                 |
| **運営・システムの不具合**           | **期間を問わず全額返金** | 状況による         | 状況による                         |

⚠️ **最終行は期間の外である。** 「14 日を過ぎたので対応できません」と
自社の不具合に対して言うのは、消費者契約法上も、商売としても通らない。
**期間で自動的に断る実装にしてはならない。**

⚠️ **`processing` を `cancelled` にしない**（既存の不変条件 `INV-M4`）。
外部へ送信済みの可能性があり、多重発行は回復できない。

#### `UD-104` 追補（2026-08-20 決定・案A）

上の表のうち「受取り済みの受取権は `claimed` のまま」は、**本決定で
置き換えられた**。⚠️ **元の記述は履歴として残す**（当時どう決めていたかを
辿れるようにするため）。

**「受け取った事実」と「いま使える権利」は別の問題である。**
受取履歴は保持するが、全額返金後も権利が利用可能な状態で残ることは認めない。

| 項目                                            | 決定                                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------------- |
| `claimed` になった事実                          | **削除しない**                                                            |
| `claimed_at` / `claimed_by_*` / Wallet 配送記録 | **保持する**                                                              |
| 全額返金時の遷移                                | **`claimed → revoked` へ進める**                                          |
| Wallet 側の表示                                 | 履歴を削除せず「返金により取消・利用不可」として残す                      |
| 一部返金                                        | **対象 Entitlement を確定できない限り自動取消ししない**（運用確認へ回す） |
| 返金取消・再有効化                              | **本決定の範囲外**                                                        |
| `revoked` から戻す                              | **しない。** `revoked` は終端。再付与は新しい受取権を発行する             |

置き換え後の表（受取権の列だけ）:

| 注文の状態                           | 受取権                                   |
| ------------------------------------ | ---------------------------------------- |
| お支払い済み・**受取りがまだ**       | `issued → revoked`（従来どおり）         |
| 受取り済み・**発行待ち**（`queued`） | **`claimed → revoked`**（記録は残す）    |
| **発行処理中**（`processing`）       | `claimed` のまま（`INV-M4`。人の確認へ） |
| **発行済み**                         | `claimed` のまま（回収できない）         |

⚠️ **段階導入。** `REFUND_REVOKE_CLAIMED_ENABLED` が真のときだけ
`claimed → revoked` を行う。既定は偽で、それまでは従来どおりの振る舞い。

⚠️ **本番でこのフラグを有効にした瞬間が、後戻りできなくなる第 1 の境目**
（`docs/OPERATIONS_AND_ROLLBACK.md`）。

### 2-2. 精算（`UD-119`）

| 項目       | 決定                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| 締め       | **月末締め**（JST）                                                    |
| 支払日     | **翌月末**                                                             |
| 精算の対象 | **返金の受付期間が満了した注文だけ**                                   |
| 最低支払額 | **1,000 円**（未満は翌月へ繰越。上限なく繰り越す）                     |
| 振込手数料 | **作家さま負担**（明細に明示する）                                     |
| 明細       | 注文番号・作品名・販売額・手数料率・手数料額・お支払額を**注文ごとに** |

### 2-3. 二つを噛み合わせる —「返金の窓が閉じてから精算する」

返金期間（14 日）＜ 精算までの猶予（最短でも約 1 か月）なので、
**返金のほぼ全部が振込より前に起きる。**

```
 8/5 決済 ─── 8/19 返金期限 ─── 8/31 締め ─── 9/30 支払
             └── ここまでに返金 ──┘
                        （精算の対象に入らない）
```

⚠️ **これが設計の要である。** 支払い済みの注文が返金されると、
作家さまから返してもらう話になる。**いちばん揉める作業**で、
少額なら回収を諦めることになり、諦めた分は運営の損になる。
順序でほぼ消せるものを、あとから運用でしのごうとしない。

**それでも起きる場合**（不具合による期間外の返金、決済事業者側の
チャージバック）は、**次回以降の精算から差し引く**。差し引ききれない
分はマイナスの繰越として持ち越す。

## 3. データモデル

### 3-1. 注文へ足す列

```
orders.refundable_until   TIMESTAMPTZ NULL   -- 返金を受け付ける期限
```

⚠️ **決済確定時に確定して書く。** 「決済日 + 設定値」を毎回計算しない。
設定を変えた瞬間に過去の注文の期限が動く。

⚠️ **`NULL` は「まだ支払われていない」。** 支払前の注文に期限は無い。
CHECK 制約で `payment_status = 'succeeded'` との整合を守る。

### 3-2. 返金（`refunds`）

| 列                    | 意味                                                              |
| --------------------- | ----------------------------------------------------------------- |
| `order_id`            | どの注文か                                                        |
| `payment_id`          | どの決済を戻したか。**⚠️ 世代の鍵はここから解決する**（`UD-118`） |
| `amount`              | 戻した額（円）                                                    |
| `reason`              | こちらで決めた符号。**⚠️ 事業者の文言をそのまま入れない**         |
| `initiated_by`        | `admin` / `provider`（事業者の画面から返金された場合）            |
| `actor_account_id`    | 誰が行ったか。`provider` なら `NULL`                              |
| `provider_refund_ref` | 事業者側の識別子                                                  |
| `created_at`          |                                                                   |

⚠️ **決済事業者の画面から返金されるケースを前提にする。** 運営が慌てて
Stripe の画面から返金するのは、実際に起きる。`charge.refunded` を受けて
**こちら側を追随させる**。追随しないと、状態がずれたまま誰も気づかない。

⚠️ **返金は追記のみ。** 取り消す口を作らない。間違えたら再課金であって、
記録を消すことではない。

### 3-3. 精算（`payouts` / `payout_lines`）

**`payouts`**（1 作家さま × 1 締め期間 = 1 行）

| 列                               | 意味                                          |
| -------------------------------- | --------------------------------------------- |
| `creator_account_id`             |                                               |
| `period_start` / `period_end`    | 締め期間。**⚠️ 焼き付ける**                   |
| `gross_amount`                   | 販売額の合計                                  |
| `fee_amount`                     | 手数料の合計                                  |
| `refunded_amount`                | 差し戻した額                                  |
| `carried_in_amount`              | 前月からの繰越（マイナスもありうる）          |
| `net_amount`                     | 今回のお支払額                                |
| `carried_out_amount`             | 翌月への繰越                                  |
| `minimum_payout_amount`          | **その時点の**最低支払額。⚠️ 焼き付ける       |
| `transfer_fee_bearer`            | **その時点の**振込手数料の負担。⚠️ 焼き付ける |
| `status`                         | `draft → confirmed → paid`                    |
| `paid_at` / `paid_by_account_id` |                                               |

**`payout_lines`**（注文 1 件ぶん。明細の実体）

| 列                                                            | 意味                                      |
| ------------------------------------------------------------- | ----------------------------------------- |
| `payout_id` / `order_id`                                      |                                           |
| `artwork_title_snapshot`                                      | ⚠️ 注文時点の作品名。マスタを引き直さない |
| `gross_amount` / `fee_rate_bps` / `fee_amount` / `net_amount` | すべて注文からの写し                      |

⚠️ **二重払いは DB で防ぐ。** `payout_lines` に `UNIQUE (order_id)` を置く。
「同じ注文が 2 回精算に入る」を、アプリの注意力ではなく制約で止める。

⚠️ **`confirmed` 以降は行を書き換えない。** 締めたあとに金額が動くと、
作家さまへ渡した明細と食い違う。訂正は**次の期間での調整**として行う。

### 3-4. 設定（`settlement_settings`）

`integration_settings` と同じく DB に置き、**オーナーだけ**が変更でき、
監査に残す。

| 列                      | 既定        |
| ----------------------- | ----------- |
| `refund_window_days`    | 14          |
| `closing_day`           | `month_end` |
| `payout_offset_months`  | 1（翌月末） |
| `minimum_payout_amount` | 1000        |
| `transfer_fee_bearer`   | `creator`   |

⚠️ **既定値をコードに埋め込まない。** ここに書いた数字は
**マイグレーションで入れる初期値**であって、コードの `?? 14` ではない。
`??` を書くと、設定行が消えたことに誰も気づかないまま動き続ける。

## 4. 禁止すること

既存の §9.3 に加えて、この領域の禁止事項。

- **精算の金額を人が直接書き換える口を作らない。** 訂正は次の期間での
  調整として行う。直接書き換えを許すと、明細と振込額が食い違ったときに
  どちらが正しいのか誰にも分からなくなる
- **`confirmed` / `paid` の精算を削除しない。** 取り消しは
  「取り消したという記録」を足すことで表す
- **返金の記録を消さない。** 追記のみ
- **返金期間の判定に「いまの設定」を使わない。** 注文に焼き付けた
  `refundable_until` だけを見る
- **運営側の不具合による返金を、期間で自動的に断らない**

以下は返金の申請と審査（方針整理 2026-08-22）で加わった禁止事項。

- **作家さまが決済事業者へ返金を投げられる口を作らない。** 販売の代金は
  運営の決済アカウントで受けている。作家さまにあるのは**事実確認に
  答えること**だけで、可否を決めるのも投げるのも運営である
- **作家さまの回答を、返金の必要条件にしない。** 期限の意味は「待たずに
  進めてよい」であって「答えるまで返せない」ではない。必要条件にすると、
  答えない作家さまがいるだけで購入者が待たされる
- **承認済みの申請を却下できるようにしない。** 承認と却下が両方立った
  申請は、あとから読んで意味が取れない。取りやめは**実行しない**という
  運用で表す
- **返金を再実行する口を作らない。** やり直せるのは「投げられなかった」
  （`execution_failed`）ものだけで、`executing` のまま止まったものは
  事業者側を確かめてから手当てする。押し直しで二重返金になる
- **審査の設定が無い配備で、既定値へ黙って落ちない。** しきい値を設定した
  つもりの配備で二重承認が効いていない、という状態を作らない

## 5. 実装の順序

| #   | やること                                                     | なぜこの順か                                          |
| --- | ------------------------------------------------------------ | ----------------------------------------------------- |
| 1   | ✅ **`UD-128` 決済の鍵を世代から読む**                       | **返金は決済と同じ世代の鍵でしか行えない。** ここが先 |
| 2   | ✅ 設定（`settlement_settings`）と `orders.refundable_until` | 返金も精算もこれを見る                                |
| 3   | ✅ 返金の実行（`UD-104` / `UD-120`）                         | 精算は「返金済みを除く」ので先に要る                  |
| 4   | ✅ 精算（`UD-119`）                                          |                                                       |

### 2 で入ったもの（2026-08-20）

- `settlement_settings`（環境ごとに 1 行）と、オーナー限定＋再認証の
  変更口（`PUT /api/v1/admin/settlement-settings`）・管理画面
  （`/admin/settlement-settings`）
- `orders.refundable_until`。**決済確定の瞬間に焼き付ける**
  （`createRefundWindowResolver`）。判定のたびに設定を読み直さない
- 返金してよいかの判定（`decideRefund`）。発行の進み具合で線を引き、
  `processing` と発行済みは `needs_review` へ回す（`INV-M4`）

### 3 で入ったもの（2026-08-20）

- `refunds` 表（**追記のみ。取り消す口を作らない**）と
  `POST /api/v1/admin/orders/:id/refund`、注文の詳細画面からの操作
- 決済事業者への返金要求。**決済した当時の世代の鍵で投げる**
  （`UD-118` §2）。当時の世代を開けなければ**断る**——受付中の世代へ
  落ちると、無関係のアカウントから現金が出ていく
- `charge.refunded` の追随。事業者の画面から返金されたぶんも同じ形で
  記録する。`provider_refund_ref` の部分 UNIQUE 索引が二重反映を止める
- 在庫の戻し。⚠️ **`issued_count`（通し番号）は戻さない**——戻すと次の
  受取権が同じ番号になり `(artwork_id, serial_no)` の UNIQUE で弾かれる。
  返金した番号は使い切りとして扱う

**手順に意味がある**（`RefundService`）:

```
 1. 判定（decideRefund）  返してよいか
 2. 記録（requested）     ⚠️ 送信より先
 3. 送信（決済事業者）    ⚠️ トランザクションの外
 4. 反映（settle）        注文・受取権・発行ジョブ・在庫を 1 トランザクションで
```

⚠️ **2 と 3 を入れ替えない。** 送信してから記録すると、その間に落ちたときに
「返金したのに記録が無い」が残る。逆（記録だけ残って送信していない）は
`requested` のまま残るので洗い出せる。

⚠️ **一部返金は、いまも自動処理しない。** 画面から返せるのは残額の全部だけで、
**金額の入力欄を作っていない**。事業者の画面からの一部返金は金額だけ記録し、
受取権も発行ジョブも動かさない。

⚠️ **返金は「連携を止めている」ことを理由に断らない。** 止めるのは新規の
お支払いであって、すでに頂いたお金を返すことではない。ここを一緒にすると、
事故を止めるために止めた瞬間に、その事故の返金までできなくなる。

### 4 で入ったもの（2026-08-20）

- `payouts` / `payout_lines` と `/admin/payouts`。締める → 確定する →
  お支払い済みにする、の 3 段
- **JST の月境界で締める**（`packages/domain/src/settlement/period.ts`）。
  UTC の月で切ると、**月末の 9 時間ぶんの売上が前の月に入る**
- **返金の窓が閉じるまで確定できない**（§2-3）。下書きは作れるが、確定だけを
  止める——運営が「今月はいくらになりそうか」を見られる方が親切なので
- **繰越**。最低支払額に満たなければ全額を翌月へ送る。⚠️ **繰越を足してから
  比べる**——先に比べると、毎月 900 円の作家さまが永久に受け取れない
- **差し戻し**。確定済みの精算に載っていた注文が返金されたら、次回で差し引く。
  差し引ききれない分はマイナスの繰越として持ち越す

**押せる操作を分けてある:**

| 操作                                         | 誰が                 | なぜ                                                                     |
| -------------------------------------------- | -------------------- | ------------------------------------------------------------------------ |
| 見る（`payout.view`）                        | 運営・監査           | いくら誰へ払ったかが見えないと監査にならない                             |
| 締める・確定する（`payout.manage`）          | 運営                 | 日常業務                                                                 |
| **お支払い済みにする**（`payout.mark_paid`） | **オーナー＋再認証** | **「振り込んだ」という宣言で、実際に振り込んだかを機械は確かめられない** |
