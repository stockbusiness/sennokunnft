## 1. プロダクトの定義

✅ **事実:** 千ノ国プロジェクト向けの **NFT一次販売マーケット** を、新規システムとしてゼロから構築する。

✅ **事実:** 既存の Sengoku Market・OVEW Wallet・代理店システムのコードは**流用しない**。
ただし将来 API / Webhook で接続できる**疎結合**な構成にする。

🟡 **仮決定:** プロダクト名（システム内部識別子）を `sengoku-nft-marketplace` とする。
対外的な表示名は未定のため、UI文言はすべて i18n キー経由とし、ハードコードしない。→ `UD-101`

## 2. 想定利用者と課題

### 2.1 ペルソナ

| ペルソナ               | 役割                                | 解きたい課題                                     |
| ---------------------- | ----------------------------------- | ------------------------------------------------ |
| 運営担当者（Operator） | NFT作品の登録・出品・販売状況の把握 | 技術知識なしでデジタル作品を安全に販売したい     |
| 購入者（Buyer）        | 作品の購入とNFTの受取               | ウォレットや暗号資産の知識なしで購入・受取したい |
| 監査担当（Auditor）    | 販売実績・受取状況の確認            | 誰がいつ何を購入し、受取が完了したかを追跡したい |

🟡 **仮決定:** MVP では上記3ロールのみを想定する。作家（Creator）による自己登録は Phase 3 以降。→ `UD-102`

### 2.2 Web3 リテラシーに関する前提

🟡 **仮決定:** 購入者は暗号資産・ウォレットの知識を持たない前提とする。
UI から Web3 用語（NFT / Wallet / Mint / Gas / チェーン名）を**表に出さない**。

| 内部用語 | UI表記（案）                    |
| -------- | ------------------------------- |
| NFT      | デジタル作品 / デジタル所有証明 |
| Mint     | 発行                            |
| Claim    | 受取                            |
| Wallet   | 受取先                          |
| Gas fee  | （UIに出さない。運営負担）      |

❓ **未決定 `UD-103`:** 表記ゆれを避けるための正式な用語集は、事業側の承認が必要。上表は案。

## 3. 機能要件（MVP）

✅ **事実:** MVPの基本フローは次の8ステップ。

| #   | ステップ                                 | 主体     | 要件                                                            |
| --- | ---------------------------------------- | -------- | --------------------------------------------------------------- |
| 1   | NFT作品を登録する                        | 運営     | 作品メタデータ（名称・説明・画像・発行上限）を登録できる        |
| 2   | 固定価格で出品する                       | 運営     | 1作品に対し固定価格の出品を作成し、公開/非公開を切り替えられる  |
| 3   | ユーザーがカード決済する                 | 購入者   | カード決済で購入できる。決済確定は**Webhookのみ**で判定する     |
| 4   | 支払完了後、NFT受取権を1枚単位で発行する | システム | 数量Nの購入に対し、受取権（Entitlement）を**N件個別に**作成する |
| 5   | 購入者がClaim URLを開く                  | 購入者   | 受取権ごとに一意の Claim URL が発行される                       |
| 6   | ログインユーザーと購入者を照合する       | システム | Claim 実行者が受取権の正当な保有者であることを検証する          |
| 7   | Claim時にNFTをMintする                   | システム | Claim 成功時に Mint を実行する。**1受取権から複数Mintできない** |
| 8   | システム内のNFT一覧へ表示する            | 購入者   | 受取済みの作品を一覧・詳細で閲覧できる                          |

### 3.1 機能要件の詳細（FR）

| ID    | 要件                                                            | 分類                                    |
| ----- | --------------------------------------------------------------- | --------------------------------------- |
| FR-01 | 運営は作品（Artwork）を作成・編集・非公開化できる               | ✅                                      |
| FR-02 | 運営は作品に対する出品（Listing）を固定価格で作成できる         | ✅                                      |
| FR-03 | 販売可能数を超える購入を成立させない（オーバーセル禁止）        | ✅                                      |
| FR-04 | 購入者はカード決済で購入できる                                  | ✅                                      |
| FR-05 | 決済確定は決済事業者の Webhook 署名検証を経た通知のみで判定する | ✅                                      |
| FR-06 | 同一 Webhook イベントを複数回受信しても副作用は1回のみ          | ✅                                      |
| FR-07 | 支払確定時に、数量ぶんの受取権を1枚単位で作成する               | ✅                                      |
| FR-08 | 受取権ごとに Claim URL（推測不能なトークン付き）を発行する      | ✅                                      |
| FR-09 | Claim は認証済みユーザーのみ実行可能で、購入者本人性を照合する  | ✅                                      |
| FR-10 | 1つの受取権から Mint されるトークンは高々1つ（多重Mint不可）    | ✅                                      |
| FR-11 | Mint 失敗時は再試行でき、再試行しても多重Mintしない             | ✅                                      |
| FR-12 | 購入者は自分が受け取った作品の一覧・詳細を閲覧できる            | ✅                                      |
| FR-13 | 運営は販売・受取・Mint の状況を管理画面で確認できる             | 🟡 MVP では読み取り専用の最小画面       |
| FR-14 | 全額返金時に未Claimの受取権を無効化する                         | 🟡 返金運用は手動起点とする（`UD-104`） |

❓ **未決定 `UD-104`:** 返金ポリシー（部分返金の可否、Claim後・Mint後の返金の扱い、
オンチェーン発行済みトークンの回収可否）は事業・法務判断が必要。
DB設計では `revoked` / `cancelled` の状態を用意するに留め、自動処理は実装しない。

## 4. 非機能要件（NFR）

| ID     | 分類         | 要件                                                                | 分類                                |
| ------ | ------------ | ------------------------------------------------------------------- | ----------------------------------- |
| NFR-01 | 整合性       | 金額はすべて整数（最小通貨単位）で保持し、浮動小数点演算を行わない  | ✅                                  |
| NFR-02 | 整合性       | 受取権・Mint は冪等に設計する（同一入力の再実行で状態が増えない）   | ✅                                  |
| NFR-03 | セキュリティ | 秘密情報をリポジトリに保存しない。`.env.example` は変数名と説明のみ | ✅                                  |
| NFR-04 | セキュリティ | ログにトークン・秘密鍵・個人情報を出力しない                        | ✅                                  |
| NFR-05 | セキュリティ | 入力値は必ずサーバー側で検証する（クライアント検証は補助）          | ✅                                  |
| NFR-06 | セキュリティ | 外部 Webhook は署名検証を必須とする                                 | ✅                                  |
| NFR-07 | 可観測性     | 構造化ログ（JSON）を出力し、リクエスト単位の相関IDを付与する        | 🟡                                  |
| NFR-08 | 可用性       | Mint はオンライン処理から切り離し、非同期ワーカーで再試行可能にする | 🟡                                  |
| NFR-09 | 保守性       | ビジネスロジックをフレームワーク層に混在させない                    | ✅                                  |
| NFR-10 | 保守性       | パッケージ間に循環依存を作らない（CIで機械検査）                    | ✅                                  |
| NFR-11 | プライバシー | オンチェーン／公開メタデータに個人情報を含めない                    | 🟡 強い推奨。詳細は SECURITY_DESIGN |

### 4.1 定量目標

❓ **未決定 `UD-105`:** 想定同時接続数・想定販売点数・ピークトラフィック・SLA（稼働率、
Claim完了までの許容時間）が未提示。性能目標を数値で確定できない。
本設計では「単一リージョン・単一DBで破綻しない構成」を前提とし、具体値は計測後に定める。

## 5. 制約条件

### 5.1 技術構成（指定）

✅ **事実:** 以下が指定されている。

pnpm / Turborepo / TypeScript / Next.js / NestJS / PostgreSQL / Prisma /
Supabase Auth / Vitest または Jest / Playwright / GitHub Actions

🟡 **仮決定:** テストランナーは **Vitest** を採用する（理由: ESM・TypeScript の設定コストが低く、
Turborepo のキャッシュと相性がよい。NestJS 既定の Jest からは移行が必要だが、
モノレポ全体でランナーを1つに統一する利点が上回る）。

### 5.2 今回の作業範囲外（実装禁止）

✅ **事実:** 次はいずれも今回**実装しない**。

- Stripe 本番接続 / 本番 Supabase 接続 / 本番ブロックチェーンへのデプロイ
- 秘密鍵の生成・保存 / NFTコントラクトの本番配備 / Mint機能の本実装
- 既存システムのリポジトリ変更 / MetaMask連携 / 二次流通機能 / 外部ウォレット送信

### 5.3 法令・コンプライアンス

❓ **未決定 `UD-106`:** 本サービスにおける NFT の法的性質（前払式支払手段・暗号資産・
単なるデジタルコンテンツのいずれに該当するか）、資金決済法・景品表示法・特定商取引法上の
表示義務、消費税の取扱いは**法務確認が必須**。設計上は「デジタルコンテンツ販売」として
モデル化するが、これは法的評価ではない。

❓ **未決定 `UD-107`:** 特定商取引法に基づく表記・利用規約・プライバシーポリシーの文面と掲載要件。

## 6. 成功指標

❓ **未決定 `UD-205`:** 公開後に作品の発行上限（発行枚数）を変更できるようにするか。

増やせば、既に購入した人が前提にしていた希少性が後から変わる。
減らせば、発行済みの枚数を下回りうる。どちらも購入者との約束を
一方的に書き換える行為になるため、**現在の実装は公開後の変更を拒否する**。
これは保守的な既定であって、事業・法務の判断が済んだものではない。

❓ **未決定 `UD-108`:** KPI（販売数、Claim完了率、Claim完了までの中央値時間、
決済成功率）の目標値は事業側未提示。計測基盤（イベント記録）は
[EVENT_CATALOG.md](./EVENT_CATALOG.md) の設計で取得可能にしておく。
