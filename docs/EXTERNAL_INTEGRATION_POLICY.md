# EXTERNAL_INTEGRATION_POLICY.md — 外部連携方針

記法は [README.md](./README.md) に従う。

---

## 1. 大原則

✅ **事実:**

- 既存の **Sengoku Market / OVEW Wallet / 代理店システム**のコードは**流用しない**。
- ただし将来 **API・Webhook で接続できる疎結合な構成**にする。
- 既存システムのリポジトリを変更しない。

🟡 **仮決定:** これを次の3規律で担保する。

| #   | 規律                                       | 意味                                                                |
| --- | ------------------------------------------ | ------------------------------------------------------------------- |
| R1  | **DB を共有しない**                        | 他システムのテーブルを直接読み書きしない。連携は API / イベントのみ |
| R2  | **相手の内部IDを主キーにしない**           | 外部IDは `provider` + `external_ref` の従属属性として持つ           |
| R3  | **同期呼び出しを業務の成否に組み込まない** | 相手の障害で本システムの決済・Claim が失敗しない                    |

> **R1 を破ると疎結合ではなくなる。** DB 共有は最も手軽で最も後戻りできない結合。
> 「読むだけだから」も禁止（スキーマ変更で相手が壊れる／壊される）。

---

## 2. 連携の方向と方式

```
                  ┌──────────────────────────────────┐
   本システム ────▶│ Outbox → Webhook 送信            │────▶ 外部システム
   （発行側）      │ 署名付き・at-least-once           │      （購読側）
                  └──────────────────────────────────┘

                  ┌──────────────────────────────────┐
   外部システム ──▶│ POST /api/v1/webhooks/...        │────▶ 本システム
   （送信側）      │ 署名検証 → 冪等記録 → 処理        │
                  └──────────────────────────────────┘

                  ┌──────────────────────────────────┐
   外部システム ──▶│ GET /api/v1/...（サービストークン）│────▶ 本システム
   （参照側）      │ スコープ制限つき                  │
                  └──────────────────────────────────┘
```

🟡 **仮決定:** 既定は **イベント（非同期）**。同期API呼び出しは
「即座に結果が必要かつ相手の障害が許容できる」場合に限る。

## 3. 送信側の契約（本システム → 外部）

### 3.1 配送方式

🟡 **仮決定:**

| 項目         | 決定                                                   |
| ------------ | ------------------------------------------------------ |
| 配送         | HTTP POST（JSON）。購読者ごとにエンドポイントを登録    |
| 保証         | **at-least-once**                                      |
| 順序         | **保証しない**                                         |
| 再試行       | 指数バックオフ。🟡 最大8回（1分〜24時間）              |
| 成功判定     | HTTP 2xx。それ以外は再試行                             |
| タイムアウト | 🟡 10秒                                                |
| 停止条件     | 連続失敗が閾値を超えたら購読を一時停止し、運用アラート |

### 3.2 署名

🟡 **仮決定:** HMAC-SHA256 による署名を付与する。

```http
POST /webhooks/sengoku-nft HTTP/1.1
X-Sengoku-Event: entitlement.claimed
X-Sengoku-Event-Id: 01J8Z7Q4...
X-Sengoku-Timestamp: 1767225600
X-Sengoku-Signature: v1=<hex(hmac_sha256(secret, timestamp + "." + rawBody))>
Content-Type: application/json
```

購読側の検証手順（**この順で**）:

1. `X-Sengoku-Timestamp` の鮮度を確認（🟡 5分以内。リプレイ攻撃対策）
2. `timestamp + "." + rawBody` から HMAC を再計算
3. **タイミング安全な比較**で `X-Sengoku-Signature` と照合
4. `X-Sengoku-Event-Id` で重複排除（既処理なら破棄して 200）

> ⚠️ 購読側は **raw body** で検証すること。JSON をパースして再シリアライズすると
> キー順・空白が変わり、署名が一致しない。

🟡 **仮決定:** シークレットは購読者ごとに発行し、ローテーション期間中は
**新旧2つの鍵を同時に受け付ける**設計にする（無停止でローテーションするため）。

### 3.3 ペイロード

イベント形式は [EVENT_CATALOG.md](./EVENT_CATALOG.md) の封筒に従う。

✅ **事実:** ペイロードに個人情報を含めない。
必要な購読者は、内部ID（`accountId` 等）を使って権限付きAPIで取得する。

> ⚠️ Claim トークン・アクセストークン・秘密鍵をイベントに載せない。

## 4. 受信側の契約（外部 → 本システム）

🟡 **仮決定:** 外部からの Webhook を受け入れる場合、送信側に次を要求する。

| #   | 要求                                                               |
| --- | ------------------------------------------------------------------ |
| 1   | 署名（HMAC またはプロバイダ標準方式）を付与すること                |
| 2   | イベントに**送信側が採番した一意ID**を含めること（冪等排除に使う） |
| 3   | タイムスタンプを含めること                                         |
| 4   | 本システムが 2xx を返したら再送しないこと                          |
| 5   | 本システムの応答が遅くても、10秒以上待たないこと                   |

本システム側の処理手順は [SECURITY_DESIGN.md](./SECURITY_DESIGN.md) §6 に従う。

## 5. 既存システムごとの方針

> ⚠️ 以下は**現時点で得られている情報が極めて限られている**。
> 各システムの実際の仕様は未調査であり、記述は「本システム側の受け入れ姿勢」に留まる。

### 5.1 Sengoku Market（既存EC）

| 項目       | 方針                                                           |
| ---------- | -------------------------------------------------------------- |
| コード流用 | ✅ しない                                                      |
| DB         | R1 により共有しない                                            |
| 想定連携   | 本システムの `order.paid` / `entitlement.claimed` を購読させる |
| アカウント | ❓ `UD-1001`                                                   |

❓ **未決定 `UD-1001`:** 既存 Sengoku Market の利用者アカウントと、
本システムのアカウントを**同一人物として紐付ける必要があるか**。
必要な場合、共通の認証基盤（Supabase を共有するのか、SSO 連携するのか）が
決まらないと設計できない。**推測で実装しない。**

### 5.2 OVEW Wallet

| 項目       | 方針                                                         |
| ---------- | ------------------------------------------------------------ |
| コード流用 | ✅ しない                                                    |
| 想定連携   | 受取先（`recipientRef`）の解決、または発行済みトークンの表示 |

❓ **未決定 `UD-1002`:** OVEW Wallet が
（a）どのチェーンを前提としているか、
（b）カストディ方式は何か、
（c）外部から利用可能な API を持つか、
が未調査。これは `UD-501`（チェーン）・`UD-502`（カストディ）の
**決定に直接影響する**（[BLOCKCHAIN_DECISION_RECORD.md](./BLOCKCHAIN_DECISION_RECORD.md) Q6）。

> **調査を最優先事項とする。** 別チェーン・別カストディで作ってしまうと、
> 後から統合できず、利用者は2つの管理画面を使い分けることになる。

### 5.3 代理店システム

| 項目       | 方針                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| コード流用 | ✅ しない                                                                   |
| 報酬計算   | **本システムでは行わない。** 代理店システム側の責務                         |
| 想定連携   | 本システムが `order.paid` / `order.refunded` を発行し、代理店システムが購読 |

🟡 **仮決定:** 紹介コード（referral）を本システムが受け取る必要がある場合でも、
**本システムは「注文に紐づく不透明な文字列」として保持するだけ**とし、
報酬率の解決・報酬額の計算・支払管理には一切関与しない。

理由: 報酬ロジックを2システムに分散させると、必ず片方が古くなる。
計算の正は1箇所に置く。

❓ **未決定 `UD-1003`:** 本システムの販売に代理店報酬を適用するか。
適用する場合、紹介コードの受け渡し方法（URLパラメータ / Cookie / API）と、
どの時点でスナップショットするかを決める必要がある。

## 6. 連携の実装配置

| 要素                             | 配置                                              |
| -------------------------------- | ------------------------------------------------- |
| イベントスキーマ（送受信の契約） | `packages/contracts`                              |
| 署名の生成・検証                 | `packages/integrations`（`WebhookSignaturePort`） |
| 送信ワーカー（Outbox の配信）    | `apps/worker`                                     |
| 受信エンドポイント               | `apps/api`                                        |
| 購読者の登録・鍵管理             | ❓ `UD-1004`（DB管理か環境変数か）                |

❓ **未決定 `UD-1004`:** Webhook 購読者の登録方式。
購読者が固定少数なら環境変数、動的に増えるなら管理テーブルが必要。
運用規模が未提示のため決定しない。

---

## 7. 連携を追加するときの手順（将来のための規律）

1. **契約を先に書く。** `packages/contracts` にスキーマとバージョンを追加する。
2. **本システム側を先に完成させる。** 相手の実装を待たずに Fake で検証する。
3. **相手の障害を想定したテストを書く。** タイムアウト・5xx・不正応答。
4. **連携を切っても本システムが動くことを確認する。** R3 の検証。
5. 本書に連携先と方式を追記する。
