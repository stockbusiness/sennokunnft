# EXTERNAL_INTEGRATION_POLICY.md — 外部連携方針

記法は [README.md](./README.md) に従う。

---

## 1. 大原則

✅ **事実:**

- 既存の **Sengoku Market / OVEW Wallet / 代理店システム**のコードは**流用しない**。
- ただし将来 **API・Webhook で接続できる疎結合な構成**にする。
- 既存システムのリポジトリを変更しない。

🟡 **仮決定:** これを次の3規律で担保する。

| #   | 規律                                       | 意味                                                                |
| --- | ------------------------------------------ | ------------------------------------------------------------------- |
| R1  | **DB を共有しない**                        | 他システムのテーブルを直接読み書きしない。連携は API / イベントのみ |
| R2  | **相手の内部IDを主キーにしない**           | 外部IDは `provider` + `external_ref` の従属属性として持つ           |
| R3  | **同期呼び出しを業務の成否に組み込まない** | 相手の障害で本システムの決済・Claim が失敗しない                    |

> **R1 を破ると疎結合ではなくなる。** DB 共有は最も手軽で最も後戻りできない結合。
> 「読むだけだから」も禁止（スキーマ変更で相手が壊れる／壊される）。

---

## 2. 連携の方向と方式

```
                  ┌──────────────────────────────────┐
   本システム ────▶│ Outbox → Webhook 送信            │────▶ 外部システム
   （発行側）      │ 署名付き・at-least-once           │      （購読側）
                  └──────────────────────────────────┘

                  ┌──────────────────────────────────┐
   外部システム ──▶│ POST /api/v1/webhooks/...        │────▶ 本システム
   （送信側）      │ 署名検証 → 冪等記録 → 処理        │
                  └──────────────────────────────────┘

                  ┌──────────────────────────────────┐
   外部システム ──▶│ GET /api/v1/...（サービストークン）│────▶ 本システム
   （参照側）      │ スコープ制限つき                  │
                  └──────────────────────────────────┘
```

🟡 **仮決定:** 既定は **イベント（非同期）**。同期API呼び出しは
「即座に結果が必要かつ相手の障害が許容できる」場合に限る。

## 3. 送信側の契約（本システム → 外部）

### 3.1 配送方式

🟡 **仮決定:**

| 項目         | 決定                                                   |
| ------------ | ------------------------------------------------------ |
| 配送         | HTTP POST（JSON）。購読者ごとにエンドポイントを登録    |
| 保証         | **at-least-once**                                      |
| 順序         | **保証しない**                                         |
| 再試行       | 指数バックオフ。🟡 最大8回（1分〜24時間）              |
| 成功判定     | HTTP 2xx。それ以外は再試行                             |
| タイムアウト | 🟡 10秒                                                |
| 停止条件     | 連続失敗が閾値を超えたら購読を一時停止し、運用アラート |

### 3.2 署名

🟡 **仮決定:** HMAC-SHA256 による署名を付与する。

```http
POST /webhooks/sengoku-nft HTTP/1.1
X-Sengoku-Event: entitlement.claimed
X-Sengoku-Event-Id: 01J8Z7Q4...
X-Sengoku-Timestamp: 1767225600
X-Sengoku-Signature: v1=<hex(hmac_sha256(secret, timestamp + "." + rawBody))>
Content-Type: application/json
```

購読側の検証手順（**この順で**）:

1. `X-Sengoku-Timestamp` の鮮度を確認（🟡 5分以内。リプレイ攻撃対策）
2. `timestamp + "." + rawBody` から HMAC を再計算
3. **タイミング安全な比較**で `X-Sengoku-Signature` と照合
4. `X-Sengoku-Event-Id` で重複排除（既処理なら破棄して 200）

> ⚠️ 購読側は **raw body** で検証すること。JSON をパースして再シリアライズすると
> キー順・空白が変わり、署名が一致しない。

🟡 **仮決定:** シークレットは購読者ごとに発行し、ローテーション期間中は
**新旧2つの鍵を同時に受け付ける**設計にする（無停止でローテーションするため）。

### 3.3 ペイロード

イベント形式は [EVENT_CATALOG.md](./EVENT_CATALOG.md) の封筒に従う。

✅ **事実:** ペイロードに個人情報を含めない。
必要な購読者は、内部ID（`accountId` 等）を使って権限付きAPIで取得する。

> ⚠️ Claim トークン・アクセストークン・秘密鍵をイベントに載せない。

---

## 4. 受信側の契約（外部 → 本システム）

🟡 **仮決定:** 外部からの Webhook を受け入れる場合、送信側に次を要求する。

| #   | 要求                                                               |
| --- | ------------------------------------------------------------------ |
| 1   | 署名（HMAC またはプロバイダ標準方式）を付与すること                |
| 2   | イベントに**送信側が採番した一意ID**を含めること（冪等排除に使う） |
| 3   | タイムスタンプを含めること                                         |
| 4   | 本システムが 2xx を返したら再送しないこと                          |
| 5   | 本システムの応答が遅くても、10秒以上待たないこと                   |

本システム側の処理手順は [SECURITY_DESIGN.md](./SECURITY_DESIGN.md) §6 に従う。

## 5. 既存システムごとの方針

> ⚠️ 以下は**現時点で得られている情報が極めて限られている**。
> 各システムの実際の仕様は未調査であり、記述は「本システム側の受け入れ姿勢」に留まる。

### 5.1 Sengoku Market（既存EC）

| 項目       | 方針                                                           |
| ---------- | -------------------------------------------------------------- |
| コード流用 | ✅ しない                                                      |
| DB         | R1 により共有しない                                            |
| 想定連携   | 本システムの `order.paid` / `entitlement.claimed` を購読させる |
| アカウント | ❓ `UD-1001`                                                   |

❓ **未決定 `UD-1001`:** 既存 Sengoku Market の利用者アカウントと、
本システムのアカウントを**同一人物として紐付ける必要があるか**。
必要な場合、共通の認証基盤（Supabase を共有するのか、SSO 連携するのか）が
決まらないと設計できない。**推測で実装しない。**

### 5.2 OVEW Wallet

| 項目       | 方針                                                         |
| ---------- | ------------------------------------------------------------ |
| コード流用 | ✅ しない                                                    |
| リポジトリ | `stockbusiness/ovewwallet`                                   |
| 想定連携   | Claim 確定後、`entitlement.granted` を送って Wallet 内に表示 |

✅ **決定済 `UD-1002`（2026-08-13・調査完了）:**

| 調査項目           | 結果                                                 |
| ------------------ | ---------------------------------------------------- |
| (a) 前提チェーン   | **特定のチェーンを使用していない**（オフチェーン）   |
| (b) カストディ方式 | **MVP では不要**。Wallet アドレス・秘密鍵を扱わない  |
| (c) 外部連携 API   | **あり**。`common_user_id` ＋ イベント連携で構成する |

> **この結果は `UD-501`（チェーン）・`UD-502`（カストディ）を決定しない。**
> 「Wallet 側に既存の制約が無い」ことが分かっただけで、
> Phase 5 でチェーンを選ぶ判断は別途必要（[BLOCKCHAIN_DECISION_RECORD.md](./BLOCKCHAIN_DECISION_RECORD.md) Q6）。
> 行はレジスタに残し、決定済みの記録として保持する。

#### MVP 連携の構成

✅ **事実:** MVP ではブロックチェーンを使わない。
Wallet へ送るカード情報には必ず `blockchain_status = NOT_MINTED` を含め、
「NFT発行済み」「オンチェーン保有中」等の表示をしない。

```
購入 → 決済確定 → Entitlement 発行 → Claim URL
  → 利用者が Claim URL を開く → OVEW Wallet でログイン
  → Wallet が本システムの Claim API を呼ぶ → common_user_id 照合
  → Claim 確定（同一トランザクションで Outbox へ記録）
  → Commit 後に Worker が entitlement.granted を送信
  → Wallet が CollectibleHolding を作成
```

⚠️ **Wallet への HTTP 送信をトランザクション内で行わない。**
外部の障害で決済・Claim をロールバックさせないため、
確定は先にコミットし、送信は Outbox 経由の非同期にする。

#### 人物の識別

| 情報             | 正本               |
| ---------------- | ------------------ |
| `common_user_id` | **代理店システム** |
| 注文・受取権     | 本システム         |
| Wallet 内の表示  | OVEW Wallet        |

⚠️ **本システムが `common_user_id` を発行しない。**
発行元は代理店システムのみとし、本システムは解決結果を保持するだけにする。

⚠️ **外部の解決失敗で購入を止めない。** アカウント作成は先に完了させ、
`common_user_id` の解決は非同期に再試行する。
Claim 時点で未解決なら `202` を返し、受取権は失効させない。

✅ **決定済 `UD-1008`（2026-08-13）:** 参照先は `team478a/sengoku-agency-system`（公開）。
契約は同リポジトリの `docs/integration/COMMON_HUB_EXTERNAL_CONTRACT_2026-07-21.md`。

#### `POST /api/common-users/resolve` の契約（確認済み）

エンドポイント: `https://sengoku-ai.com/api/common-users/resolve`
認証: `x-api-key: {AI受信用APIキー}` または `Authorization: Bearer {同}`

| 項目                    | 内容                                                 |
| ----------------------- | ---------------------------------------------------- |
| `common_user_id` の形式 | `cu_` ＋ 32 桁 hex                                   |
| 発行元                  | 代理店システムのみ                                   |
| 入力キー                | `external_user_id`（`service_user_id` も受け付ける） |
| 併せて送る              | `system_key`                                         |

応答の `matched_by` は照合の根拠を示す。

| `matched_by`           | 意味                                                   |
| ---------------------- | ------------------------------------------------------ |
| `common_user_id`       | 既知の ID で一致                                       |
| `system_account_link`  | `system_key` ＋ `external_user_id` で一致              |
| `service_user_mapping` | 旧マッピングで一致                                     |
| `identity:*`           | **検証済み**の LINE / メール / 電話 / ウォレットで一致 |
| `created`              | 新規作成された                                         |

⚠️ **`create_if_missing` の既定値は `true`。**
照会のつもりで呼ぶと、副作用として人物が新規作成される。
**存在確認だけをしたい経路では明示的に `false` を渡す。**

#### 自動名寄せの安全条件（契約 §4）

代理店システムは、**未検証のメール・電話・ウォレットだけでは自動統合しない。**
未検証の候補があったまま新規作成された場合、応答は

```
identity_match_status: "unverified_candidate_not_auto_merged"
```

となる。これは**同一人物が重複した可能性がある**という警告であり、
本システム側でも無視してはならない。

> 契約 §4 は外部システムに対しても
> 「未検証メールだけで同一人物確定をしないでください」と明記している。

#### Wallet 向けの署名

✅ **事実:** 汎用 Webhook の `X-Sengoku-*` 方式（§3.2）は**削除しない**。
OVEW Wallet 向けのアダプタでのみ千ノ国共通方式へ変換する。

| 項目     | 汎用（§3.2）                | OVEW Wallet 向け                            |
| -------- | --------------------------- | ------------------------------------------- |
| ヘッダ   | `X-Sengoku-*`               | `X-SenNoKuni-*`                             |
| 署名対象 | `timestamp + "." + rawBody` | `timestamp + "\n" + nonce + "\n" + rawBody` |
| nonce    | なし                        | **あり**                                    |
| 冪等キー | `X-Sengoku-Event-Id`        | `Idempotency-Key`（値は `event_id`）        |

> 内部のイベント名を Wallet の都合で変えない。変換はアダプタの責務。

#### Claim API の認証

❓ **未決定 `UD-1005`（OVEW Wallet との合意事項）:**
Claim 確定 API（`POST /claims/{token}/confirm`）の呼び出し元認証方式。

⚠️ **本システムの立場: 必須とする。**
この API は本文で `common_user_id` を受け取るが、
**`common_user_id` は識別子であって資格情報ではない。**
呼び出し元が OVEW Wallet であることを検証しなければ、この値は自己申告にすぎず、
「Claim はログイン必須」という受入条件をサーバー側で確認する手段が無くなる。

これは本システムの既存方針（[AUTHORIZATION_DESIGN.md](./AUTHORIZATION_DESIGN.md)
「ロールの正は DB。トークンの自己申告を信用しない」）と同じ種類の判断である。

**千ノ国の既存契約にも前例がある。** 代理店システムの外部連携契約 §5 は、
API キーを**接続先ごと・通信方向ごとに分ける**と定めており、
呼び出し元を認証しない連携は想定されていない。
したがって必須化は新たな要求ではなく、既存の方式に揃えることにあたる。

残る論点は方式の選択（API キー / HMAC / 併用）であり、そこは合意が要る。

#### Claim の状態表現

❓ **未決定 `UD-1007`:** 内部状態と公開 API の `status` の対応。

指示書には 2 つの語彙があり、対応が明示されていない。
公開 `status` は Claim の状態と**Wallet への配送状態が混ざっている**ため、
どちらかだけでは決まらない。

🟡 **仮決定（合意が取れるまでの案）:**

| 内部 `claim_status`    | Wallet 配送 | 公開 `status`      |
| ---------------------- | ----------- | ------------------ |
| `ISSUED` / `CLAIMABLE` | —           | `PENDING`          |
| `CLAIMED`              | 未配送      | `DELIVERY_PENDING` |
| `CLAIMED`              | 配送済      | `DELIVERED`        |
| `EXPIRED`              | —           | `EXPIRED`          |
| `REVOKED`              | —           | `REVOKED`          |

#### 購入者の `common_user_id` の補完

❓ **未決定 `UD-1006`:** 決済時点で未解決だった購入者の `common_user_id` を、
**どの条件で後から補完してよいか。**

指示書は「解決後に安全な条件で補完する」とするが、その条件が定義されていない。
補完は受取先の決定に直結し、**誤ると他人の Wallet へ渡る。**

✅ **決定済（2026-08-14）:**

1. 補完は **`system_key` ＋ `external_user_id`（本システムの account id）でのみ**行う。
   これは本システムが発行した鍵なので、解決結果は構成上つねに同じ人物を指す
2. **未検証の属性（メール・電話・ウォレット）を照合材料として送らない。**
   送ると、他人の検証済み ID に当たって紐付く経路ができる
3. 補完は `matched_by` が `common_user_id` / `system_account_link` /
   `service_user_mapping` のときのみ受け入れる。`identity:*` では受け入れない
4. **`identity_match_status` が `ok` 以外なら `RESOLVED` にしない。**
   `CONFLICT` に倒し、Claim に使えない状態にする（下記）

#### `identity_match_status != ok` を通さない理由

代理店システムは、未検証のメール・電話・ウォレットが一致しても自動統合せず、
`unverified_candidate_not_auto_merged` を返す。
これは「**この人物が本当に一人なのか、まだ確定していない**」という意味である。

記録だけ残して `RESOLVED` へ進めると、
**確定していない人物あてに受取先が決まる。** Claim は取り返しがつかないので、
曖昧なまま通さず人の確認を待つ。

| 項目             | 扱い                                         |
| ---------------- | -------------------------------------------- |
| 状態             | `CONFLICT`                                   |
| `common_user_id` | **保存する**（確認するときの手がかりになる） |
| `linked_at`      | `null`（紐付けは成立していない）             |
| `last_error`     | `identity_match_status=<返ってきた値>`       |
| Claim            | **使えない**                                 |
| 再試行           | しない（相手の状態が変わらなければ同じ結果） |

> 残る判断は「そもそもメールアドレスを送るか」であり、これは `UD-503`
> （メールアドレスを本システムで保持するか）と連動する。
> 送らない前提なら 1〜4 だけで完結する。

### 5.3 代理店システム

| 項目       | 方針                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| コード流用 | ✅ しない                                                                   |
| 報酬計算   | **本システムでは行わない。** 代理店システム側の責務                         |
| 想定連携   | 本システムが `order.paid` / `order.refunded` を発行し、代理店システムが購読 |

🟡 **仮決定:** 紹介コード（referral）を本システムが受け取る必要がある場合でも、
**本システムは「注文に紐づく不透明な文字列」として保持するだけ**とし、
報酬率の解決・報酬額の計算・支払管理には一切関与しない。

理由: 報酬ロジックを2システムに分散させると、必ず片方が古くなる。
計算の正は1箇所に置く。

❓ **未決定 `UD-1003`:** 本システムの販売に代理店報酬を適用するか。
適用する場合、紹介コードの受け渡し方法（URLパラメータ / Cookie / API）と、
どの時点でスナップショットするかを決める必要がある。

## 7. 連携を追加するときの手順（将来のための規律）

1. **契約を先に書く。** `packages/contracts` にスキーマとバージョンを追加する。
2. **本システム側を先に完成させる。** 相手の実装を待たずに Fake で検証する。
3. **相手の障害を想定したテストを書く。** タイムアウト・5xx・不正応答。
4. **連携を切っても本システムが動くことを確認する。** R3 の検証。
5. 本書に連携先と方式を追記する。
