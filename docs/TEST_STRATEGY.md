# TEST_STRATEGY.md — テスト戦略

記法は [README.md](./README.md) に従う。

---

## 1. 方針

🟡 **仮決定:** テストの重心を **ドメイン層の単体テスト**に置く。

理由:

1. 本システムの事故は「金額」「在庫」「多重発行」の3つに集中する。
   これらはすべてドメイン層の純粋関数と DB 制約で表現される。
2. ドメイン層はフレームワーク非依存の純粋関数なので、
   高速・決定論的に大量のケースを回せる。
3. E2E は遅く不安定になりやすい。**数を絞り、代表フローのみ**に使う。

```
        ▲
        │  E2E (Playwright)          少数・代表フローのみ
        │  ─────────────────
        │  結合テスト                 API境界・DB制約・Webhook
        │  ─────────────────
        │  単体テスト (Vitest)        ドメイン・認可・バリデーション
        ▼                             ← ここが最も厚い
```

## 2. テストの層

| 層             | ツール                   | 対象                                                          | 外部依存          |
| -------------- | ------------------------ | ------------------------------------------------------------- | ----------------- |
| 単体           | Vitest                   | `domain` / `validation` / `auth` / `config` / `observability` | なし（Fake のみ） |
| 結合           | Vitest                   | `database`（実 Postgres）、`api`（HTTP 経由）                 | ローカル Postgres |
| コンポーネント | Vitest + Testing Library | `ui` の部品                                                   | なし              |
| E2E            | Playwright               | `web` の代表フロー                                            | 起動済みアプリ    |

✅ **事実:** Phase 1 で実行するのは **単体テスト**と **E2E スモーク1本**。
結合テスト（実 Postgres）は Phase 2 以降。

🟡 **仮決定:** 結合テストは **Testcontainers ではなく docker compose の Postgres** を使う。
理由: CI での起動が速く、GitHub Actions の `services:` で同じ構成を再現できる。

## 3. 必須テストケース

> 次は**必ず自動テストで検証する**。人手確認で代替しない。
> 事故が起きた場合の被害が大きく、かつ再現が難しいため。

### 3.1 冪等性（最重要）

| #   | ケース                                    | 期待                                      | Phase |
| --- | ----------------------------------------- | ----------------------------------------- | ----- |
| I-1 | 同一 Webhook イベントを2回受信            | 副作用は1回のみ。受取権が二重に作られない | 3     |
| I-2 | 同一 `Idempotency-Key` で注文APIを2回呼ぶ | 注文は1件。2回目は同じ結果を返す          | 3     |
| I-3 | **同一 Claim を同時に2回実行**            | 1回だけ成功、もう1回は 409                | 4     |
| I-4 | **同一受取権に対し発行ジョブを2回投入**   | ジョブは1件のみ                           | 4     |
| I-5 | **worker を2並列で走らせる**              | 同じジョブを2回処理しない                 | 5     |
| I-6 | Mint 成功後に同じジョブを再実行           | `nft_tokens` は1件のまま                  | 5     |
| I-7 | Mint の冪等キーが再試行で変わらない       | 同一受取権IDから同じキーが導出される      | 1     |

> **I-3 / I-5 は並行実行で検証する。** 逐次実行のテストでは競合状態を検出できない。
> 実 Postgres に対し `Promise.all` で同時発行し、成功数が1であることを確認する。

### 3.2 多重Mint防止（✅ 必須要件）

| #   | ケース                                                       | 期待                                        | Phase |
| --- | ------------------------------------------------------------ | ------------------------------------------- | ----- |
| M-1 | `nft_tokens` に同一 `entitlement_id` を2行 INSERT            | 2行目が UNIQUE 違反で失敗                   | 2     |
| M-2 | `mint_jobs` に同一 `entitlement_id` を2行 INSERT             | 2行目が UNIQUE 違反で失敗                   | 2     |
| M-3 | Claim 済み受取権を再 Claim                                   | 409。ジョブは増えない                       | 4     |
| M-4 | `processing` 中のジョブは全額返金でも `cancelled` にならない | 状態は `processing` のまま、`note` のみ追加 | 5     |

### 3.3 在庫・オーバーセル

| #   | ケース                                | 期待                               | Phase |
| --- | ------------------------------------- | ---------------------------------- | ----- |
| S-1 | 在庫1に対し**同時に**2件注文          | 1件成功、1件 `INSUFFICIENT_SUPPLY` | 3     |
| S-2 | 販売可能数を超える数量を指定          | `INSUFFICIENT_SUPPLY`              | 3     |
| S-3 | 仮引当が期限切れになると解放される    | `reserved_count` が戻る            | 3     |
| S-4 | CHECK 制約が最終防壁として働く        | 制約違反で INSERT/UPDATE が失敗    | 2     |
| S-5 | 決済確定で `reserved → issued` に移る | 合計が変わらない                   | 3     |

### 3.4 金額

| #   | ケース                           | 期待                                                  | Phase |
| --- | -------------------------------- | ----------------------------------------------------- | ----- |
| A-1 | 金額はすべて整数                 | 小数・浮動小数点が混入しない（型で保証＋テスト）      | 1     |
| A-2 | 異なる通貨の加算                 | 実行時エラー                                          | 1     |
| A-3 | 負の金額                         | 生成時に拒否                                          | 1     |
| A-4 | 注文の合計 = 明細の合計          | 一致する                                              | 3     |
| A-5 | **リクエストの価格を信用しない** | クライアントが価格を送っても listing の価格が使われる | 3     |

### 3.5 状態遷移

| #   | ケース                                                 | 期待               | Phase |
| --- | ------------------------------------------------------ | ------------------ | ----- |
| T-1 | 各集約の**許可された遷移**がすべて成功する             | 表駆動テストで網羅 | 1     |
| T-2 | 各集約の**許可されていない遷移**がすべて失敗する       | 表駆動テストで網羅 | 1     |
| T-3 | 終端状態（`claimed` / `succeeded` 等）から遷移できない | エラー             | 1     |
| T-4 | バックオフが単調増加し、上限を超えない                 | 計算関数のテスト   | 1     |
| T-5 | 試行回数が `max_attempts` を超えたら `failed`          |                    | 1     |

> **T-1 / T-2 は「遷移表を1つ書いて全組み合わせを回す」形にする。**
> 状態が増えたときにテストの追加漏れが起きない。

### 3.6 認可

| #   | ケース                                    | 期待                           | Phase |
| --- | ----------------------------------------- | ------------------------------ | ----- |
| Z-1 | 権限マトリクスの**全セル**を検証          | 表駆動テスト                   | 1     |
| Z-2 | 他人の注文IDを指定して取得（IDOR）        | 403 または 404                 | 3     |
| Z-3 | 他人の Claim URL で Claim（購入者不一致） | 403                            | 4     |
| Z-4 | 未ログインで Claim                        | 401                            | 4     |
| Z-5 | buyer が管理APIを呼ぶ                     | 403                            | 3     |
| Z-6 | **JWT のクレームで role を偽装**          | 無視され、DBの role が使われる | 4     |
| Z-7 | `alg: none` の JWT                        | 401                            | 4     |
| Z-8 | 期限切れ JWT                              | 401                            | 4     |

### 3.7 Webhook

| #   | ケース                             | 期待                        | Phase |
| --- | ---------------------------------- | --------------------------- | ----- |
| W-1 | 署名が不正                         | 400。**業務処理を行わない** | 3     |
| W-2 | 署名なし                           | 400                         | 3     |
| W-3 | タイムスタンプが古い（リプレイ）   | 400                         | 3     |
| W-4 | 署名は正しいが本文が改竄されている | 400                         | 3     |
| W-5 | 未知のイベント種別                 | 200（`ignored` として記録） | 3     |
| W-6 | 注文を特定できない                 | 200（ログのみ）             | 3     |
| W-7 | 既に `paid` の注文への確定通知     | 200。二重処理しない         | 3     |
| W-8 | 一部返金                           | 自動処理されない            | 3     |

> **W-1 は「400 を返すこと」だけでなく「副作用がないこと」を検証する。**
> 署名検証をすり抜けた処理が残っていないかを確認するため。

## 4. E2E テスト

🟡 **仮決定:** E2E は**代表フローのみ**、数を絞る。

| Phase | シナリオ                                                      |
| ----- | ------------------------------------------------------------- |
| 1     | **スモーク:** トップページが表示される                        |
| 2     | 作品一覧 → 詳細が表示される                                   |
| 3     | 注文作成 → 決済画面へ遷移（決済はモック）                     |
| 4     | Claim URL を開く → ログイン → 受取 → コレクションに表示される |

✅ **事実:** E2E で実決済サービス・実ブロックチェーンに接続しない。

🟡 **仮決定:** E2E ではブラウザから外部への通信を Playwright の
`route` で遮断し、想定外の外部接続をテスト失敗にする。
「気付かないうちに本番サービスへ繋いでいた」を防ぐ。

## 5. テストデータとモック

🟡 **仮決定:**

| 対象         | 方式                                                                 |
| ------------ | -------------------------------------------------------------------- |
| 時刻         | `ClockPort` を注入。`Date.now()` を直接呼ばない                      |
| 乱数         | `IdGeneratorPort` / `ClaimTokenPort` を注入。テストでは決定論的実装  |
| 外部サービス | ポートの Fake 実装。**HTTP モックライブラリを第一選択にしない**      |
| DB           | 結合テストのみ実 Postgres。単体テストではリポジトリの in-memory 実装 |

> **なぜ HTTP モックより Fake アダプタか:**
> HTTP モックは「相手のAPI仕様」をテストに焼き付ける。
> 仕様が変わるとテストだけ通って本番が壊れる。
> ポートの Fake なら**自分が定義した契約**を検証でき、
> 契約と実装の一致は別途の契約テストで確認できる。

## 6. カバレッジ

🟡 **仮決定:**

| パッケージ            | 行カバレッジ目標 |
| --------------------- | ---------------- |
| `packages/domain`     | 90% 以上         |
| `packages/auth`       | 90% 以上         |
| `packages/validation` | 80% 以上         |
| その他                | 目標を設定しない |

> ⚠️ **カバレッジ率を CI の合否条件にしない**（Phase 1 では計測のみ）。
> 数値を満たすためのテストは、書かないより悪い場合がある。
> 重要なのは §3 の必須ケースが**実際に存在するか**であり、これはレビューで確認する。

## 7. CI での実行

✅ **事実:** GitHub Actions で全検査が再現できること。

| ジョブ          | 内容                                     |
| --------------- | ---------------------------------------- |
| `install`       | `pnpm install --frozen-lockfile`         |
| `lint`          | ESLint + Prettier チェック               |
| `typecheck`     | `tsc --noEmit`（全パッケージ）           |
| `test`          | Vitest（全パッケージ）                   |
| `build`         | Turborepo による全アプリのビルド         |
| `check:deps`    | 循環依存・層越え検査                     |
| `check:secrets` | `.env` 混入・`.env.example` の値記入検査 |
| `e2e`           | Playwright スモーク                      |

🟡 **仮決定:** すべて**同一の pnpm スクリプト**で実行し、
ローカルと CI で挙動が変わらないようにする。
「CI でしか動かない検査」を作らない。
