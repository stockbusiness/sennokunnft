# 返金の申請と審査

方針整理 2026-08-22。`docs/SETTLEMENT_AND_REFUND.md` の続きで、
**返金そのもの**（決済事業者へ投げる処理）ではなく、**その手前の手続き**を扱う。

---

## 0. この文書の一番大事な主張

**作家さまが決済事業者へ返金を投げられる口は、この仕組みに存在しない。**

販売の代金は運営の決済アカウントで受けている。作家さまにあるのは
**事実確認に答えること**だけで、可否を決めるのも、事業者へ投げるのも運営である。

これは権限の設計ではなく、**お金の流れの事実**から来ている。受けていない
お金は返せない。作家さまへ「返金する」操作を渡すと、実際には運営の残高から
出ていくものを、作家さまが押すことになる。

⚠️ **「作家が販売者で、運営が販売を代行する」という業務仕様上の方針とは、
別の話である。** 現在の実装は運営が販売者となる構成（`SETTLEMENT_AND_REFUND.md`
§6）で、そこは今回触っていない。利用規約・特定商取引法表示・作家契約などの
法的文言は、**運営による確認が完了するまで確定・公開しない。**

## 1. 状態

```
                    ┌─ ask-creator ─→ creator_review ─┐
submitted ──────────┤                                 ├─→ reviewed
                    └──────── investigate ────────────┘        │
                                                               │
                    ┌── reject ─→ rejected                     │
                    │                                          │
      approval_pending ←── approve（1 人目・二重承認が要る額）──┤
                    │                                          │
                    └── approve（2 人目）─→ approved ←─ approve（二重承認が不要な額）
                                              │
                                          execute
                                              ↓
                                          executing
                                          ╱       ╲
                                    executed    execution_failed
                                                      │
                                                  execute（再実行）
```

- **`executed` は「事業者が受け付けた」であって「入金された」ではない。**
  銀行振込の返金は日をまたぐ
- **`rejected` と `executed` が終わり。** ここから先へ動かさない
- **承認済み（`approved`）からは却下できない。** 承認と却下が両方立った
  申請は、あとから読んで意味が取れない。取りやめは**実行しない**で表す

## 2. 事由と区分（15 / 3）

区分は**事由から機械的に決まる**。人に選ばせない——選べると、作家さまへの
確認が要る事由を「運営だけ」にして飛ばせてしまう。

| 区分                   | 事由                                                                                                              | 手続き                 |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `operator_only`        | `duplicate_payment` `wrong_amount` `system_failure` `issuance_failed` `wrong_grant` `fraudulent_use` `chargeback` | 運営だけで判断する     |
| `creator_confirmation` | `not_as_described` `creator_cannot_deliver` `rights_infringement` `quality_issue`                                 | 作家さまへ事実確認する |
| `excluded`             | `buyer_change_of_mind` `after_transfer` `after_use` `after_resale`                                                | 原則として返金しない   |

**購入者が選べるのは 12 個。** 外してあるのは、購入者には分からない 3 つだけ:

- `chargeback` ……決済事業者から届く事実であって、人が申し出る事由ではない
- `wrong_grant` ……何が正しく渡るはずだったかは、運営にしか分からない
- `fraudulent_use` ……不正利用と決めるのは運営の判断である

⚠️ **区分では絞っていない。** 「運営だけで判断する」区分にも、購入者が
いちばん先に気づくこと（二重に引き落とされた、金額が違う）が入っている。

⚠️ **原則対象外（`excluded`）も受け付ける。** 受け付けないと、その申し出が
どれだけ来ているかが記録に残らない——規約だけが正しいことになる。既定では
却下されるが、**権利侵害や重大な障害では運営が例外として承認できる**
（`approveAsException`。押し慣れで越えられないよう、明示したときだけ通る）。

## 3. 作家さまへの事実確認

- 期限は**設定の営業日数**（既定 3、1〜20）から決める。**画面から受け取らない**
  ——打てるようにすると、急ぎのたびに短くなり、意味が無くなる
- ⚠️ **祝日を見ていない。** 表を持っていないためで、**連休のある月は実際より
  短くなる**。運用でそのことを承知して使う
- **期限を過ぎても回答は受け付ける。** 遅れて届いた事実にも値打ちがある。
  期限の意味は「待たずに進めてよい」であって「もう聞かない」ではない
- **答えても申請の状態は動かない。** 進めるのは運営（`investigate`）である。
  回答で自動的に進むと、読まれないまま次へ行く
- **「返金してよい／いけない」の欄は置かない。** 伺うのは**事実**で、決めるのは
  運営である。可否の欄を置くと、答えが「反対」で埋まったときに運営が
  返金しづらくなる
- 作家さまに見せるのは**事由と経緯**まで。**金額と購入者は見せない**

## 4. 二重承認と金額の再入力

`UD-104` の当初の判断は「一部返金の金額を受け取る口を作らない」だった。
桁を 1 つ多く打った操作がそのまま通るためである。**今回これを覆した**——
一部返金が実務で要るため。代わりに歯止めを 2 つ課す。

1. **承認で金額をもう一度打っていただく。** 画面に出ている額をそのまま通す
   のではなく、**打ち直して残額の範囲に収まったときだけ**進む
2. **しきい値以上では、別の人による二重承認。**
   `settlement_settings.dual_approval_threshold_amount`
   - ⚠️ **`null` は「二重承認を使わない」。** 0 をその意味に使わない
     ——設定を消し忘れたのか、全件に課したいのかが読めなくなる
   - ⚠️ **申請した本人は承認できない。** 承認の欄が 1 つ増えただけでは
     歯止めにならない（ドメインの `canApprove` と DB の CHECK の両方が止める）
   - ⚠️ **1 人目と 2 人目も別人。** 1 人目が押し直しても `approved` へ進まない

⚠️ **運営が注文の画面から直接押す経路は、従来どおり残額の全部である。**
金額を指定できるのは、審査を通った申請を承認するときだけ。

## 5. 誰がその返金を被るか（決定 2026-08-22）

**事由から既定が決まる。運営が承認のときに選び直せる（決定 2026-08-22）。**

| 運営が被る                                                                          | 作家さまが負う                              |
| ----------------------------------------------------------------------------------- | ------------------------------------------- |
| `duplicate_payment` `wrong_amount` `system_failure` `issuance_failed` `wrong_grant` | `not_as_described` `creator_cannot_deliver` |
| `chargeback` `fraudulent_use`                                                       | `rights_infringement` `quality_issue`       |
| **例外として通したもの**                                                            |                                             |

- ⚠️ **既定を選んだ状態で出す。** 実務では表に当てはまらないことが起きるので
  **選べる**が、何もしなければ表どおりになる。既定を空にすると毎回選ばせる
  ことになり、表の意味が薄れる
- ⚠️ **既定と違う値を選んだことを残す**（`clawback_bearer_overridden`）。
  値だけ残しても、それが**既定だったのか判断だったのか**が読めない。
  あとから「なぜこの作家さまが負担したのか」を説明するときに要る
- ⚠️ **判断したという事実を、表とは別に持つ。** 事由の表を将来変えると
  「そのとき何が既定だったか」を引き直せなくなる
- ⚠️ **押す前に見せる。** 見えないまま押すと、作家さまの売上から引かれる
  ことに気づかないまま承認できてしまう
- ⚠️ **作家さま負担のときは、その先まで書く。** 「作家さま」とだけ出しても
  何が起きるか伝わらない。「次回以降の精算で差し引きます」まで見せる
- ⚠️ **選んだ値を申請へ保存し、実行はそれを使う。** 実行で事由から引き直す
  と、選び直した判断が消える
- ⚠️ **負担者が決まっていない承認済みを作らせない**（DB の CHECK）
- ⚠️ **申請を通らない返金は 3 値の事由から決める。** 運営が注文の画面から
  直接返した返金には 15 事由が無い。`our_fault` と `provider_initiated` は
  運営が被る

作家さま負担の分だけが、次回以降の精算で差し引かれる。**請求書を作る口は
無い**（`SETTLEMENT_AND_REFUND.md` §2-4）。

## 6. 受取権をどうするか

`revoke`（取り消す）か `keep`（残す）か。

- **全額返金なら、判定が提案する**（`suggestDisposition`）
- **一部返金では、機械に決められない。** どのシリアルを取り消すべきかは
  返金の中身によって変わる。承認のときに運営が指定する
- ⚠️ **`keep` は判定を上書きできるが、`revoke` は上書きできない。**
  発行が `processing` / `succeeded` の行は、外部へ送信済みの可能性があり
  **取り消しても回復できない**（`INV-M4`）

## 7. 二重返金を止めている場所

| 場所                                            | 何を止めるか                                    |
| ----------------------------------------------- | ----------------------------------------------- |
| `refund_requests_open_per_order`（部分 UNIQUE） | 同じ注文に、決着していない申請を 2 つ作らせない |
| `transition`（条件付き更新）                    | 2 人が同時に承認しても、片方しか通らない        |
| `executing` の claim                            | 2 回押しても、事業者へは 1 回しか投げない       |
| 事業者側の冪等キー（`refund_<id>`）             | 同じ返金の行から 2 度投げても、事業者側で 1 回  |

⚠️ **`execution_failed` だけが再実行できる。** `executing` のまま止まった
ものは、**投げたあとに落ちた可能性がある**。押し直しで再送させない——
事業者側を確かめてから手当てする。

## 8. 証跡

`refund_request_events` は**追記のみ**。直す口も消す口も無い
（DB のトリガーが `UPDATE` / `DELETE` を拒む）。

⚠️ **本文を写さない。** 購入者の申し出も、作家さまの回答も、証跡へは
**数と符号まで**しか残さない。証跡は長く残り、閲覧範囲も広い。

承認と却下は、証跡に加えて**監査ログ**（`audit_logs`）へも記録する。

## 9. 権限

| 操作                   | 必要な力                           | 誰が持つか                        |
| ---------------------- | ---------------------------------- | --------------------------------- |
| 一覧・詳細を読む       | `refund_request.view`              | `operator` / **`auditor`**        |
| 調べる・作家さまへ聞く | `refund_request.investigate`       | `operator`                        |
| 承認・却下・実行       | `refund_request.approve`           | **オーナーのみ**                  |
| 止まった連携をやり直す | `refund_request.retry_integration` | `operator`                        |
| 事実確認に答える       | `refund_inquiry.answer_own`        | 会員（`buyer`。**自分宛てのみ**） |
| 申し出る               | `order.view`                       | 会員（**自分の注文のみ**）        |

⚠️ **調べる人と、返すと決める人を分けてある。** 調べる過程で作家さまへ
確認を依頼する——外へ働きかける操作なので `auditor` には渡さない。

## 10. 画面

| 誰が     | どこ                          | 何ができるか                                                   |
| -------- | ----------------------------- | -------------------------------------------------------------- |
| 運営     | `/admin/refund-requests`      | 一覧（状態で絞る）／代理でお受けする                           |
| 運営     | `/admin/refund-requests/[id]` | 詳細・経過・作家さまのご回答／調査・確認依頼・承認・却下・実行 |
| 作家さま | `/creator/refund-inquiries`   | ご自分に来た確認への回答／売上からのお戻し                     |
| 購入者   | `/account/orders/[id]`        | 「返金のご相談」（お支払い済みで、まだ返金の無い注文だけ）     |

画面の側で守っていること:

- **作家さまの画面に「返金する」という言葉を出さない。** 言葉だけ置くと
  「押せば返せる」と思われる——そして「押しても動かない」と言われ、
  動くように直そうという話になる（文言の試験が見張っている）
- **購入者へ「ご返金します」と読める言い方をしない。** お受けしたことと、
  お返しすることは別である。ここを曖昧にすると、断ったときに
  「話が違う」になる——そしてそれは、こちらの書き方が悪い
- **承認の金額欄を空で出す。** 申し出の額を初期値に入れるとそのまま
  押せてしまい、打ち直しを課した意味が無くなる
- **しきい値と事由の規則を画面へ書き写さない。** 二重承認が要るかも、
  作家さまへ聞ける事由かも、API 側の判断である。画面が持つと 2 か所に
  同じ規則ができて必ずずれる
- **押せない操作をボタンで隠して終わりにしない。** 隠しても API は直接
  叩けるし、隠すだけでは「なぜ押せないか」が伝わらない。断られた符号を
  言葉に直して返す
- **`REFUND_REQUEST_NOT_ACTIONABLE` を「権限がありません」と訳さない。**
  権限はある。その申し出では押せないだけ。権限の話にすると、運営が
  権限を足そうとして、いつまでも直らない
- **作家さまへ金額と購入者を見せない。** 事実をお答えいただくのに要らない。
  出すと、いくら返るのかを先に知ることになり、回答が歪む
- **`executed` を「よかった」の色にしない。** お金が出ていった記録である。
  緑にすると、返金の多い月ほど一覧が明るく見える

## 11. 知らせ（決定 2026-08-22）

| 種別                      | 宛先         | いつ                     |
| ------------------------- | ------------ | ------------------------ |
| `refund_request.received` | 購入者       | お申し出をお受けしたとき |
| `refund_inquiry.asked`    | **作家さま** | 事実確認をお願いするとき |
| `refund_request.rejected` | 購入者       | 却下したとき             |

⚠️ **作家さまへの依頼が無いと、期限が意味を持たない。** ご回答の期限は
営業日数で決まるのに、**ログインしない限り依頼が来たことに気づけない**。
気づかないまま期限が過ぎ、運営が「回答が無いので進めた」と記録する
——作家さまから見れば、聞かれてすらいない。

文面で守っていること:

- **お受けした知らせに金額を書かない。** どれだけお返しするかは審査が決める。
  **語彙に金額を入れていない**ので、書きようが無い
- **「ご返金します」と読める文面にしない。** お受けしたことと、お返しする
  ことは別である
- **作家さまへの依頼に、金額とご購入者さまを載せない。** 事実をお答えいただく
  のに要らず、載せると「いくら返るのか」を先に知ることになって回答が歪む
- **作家さまへ「返金してよいか」を尋ねない。** 伺うのは事実で、決めるのは
  運営である
- **期限を過ぎても受け付けると書く。** 「もう遅い」と読ませない
- **却下の知らせに、運営の記録を写さない。** 運営の記録は運営の言葉で
  書かれていて、そのままお送りする文ではない
- **却下を黙って終わらせない。** 申し出た方から見ると、返事が来ないのと
  断られたのは違う。返事が来なければ、何度でも問い合わせが来る

⚠️ **承認と実行の知らせは、既存の `refund.requested` / `refund.completed`
が担う。** 実行のときに `RefundService` が積む。二重に足さない。
