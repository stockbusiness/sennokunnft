# AUTHORIZATION_DESIGN.md — 認証・認可設計

記法は [README.md](./README.md) に従う。

✅ **事実:** 認証基盤は Supabase Auth を使用する。
✅ **事実:** Phase 1 では**本番 Supabase へ接続しない**。トークン検証ポートと Fake 実装のみ用意する。

---

## 1. 認証（Authentication）

### 1.1 責務分割

🟡 **仮決定:**

| 責務                                         | 担当                                          |
| -------------------------------------------- | --------------------------------------------- |
| 資格情報の管理・ログイン・パスワードリセット | **Supabase Auth**（本システムは一切扱わない） |
| アクセストークンの検証                       | `packages/auth`                               |
| アカウントの業務属性（ロール・状態）         | 本システムの `accounts` テーブル              |

> 本システムは**パスワードを保持しない**。ハッシュも保持しない。
> 認証の実装を自前で持たないことが最大のセキュリティ対策になる。

### 1.2 トークン検証

🟡 **仮決定:** Supabase が発行する JWT を **JWKS による公開鍵検証**で検証する。

検証項目（すべて必須）:

| #   | 項目                                                            | 失敗時 |
| --- | --------------------------------------------------------------- | ------ |
| 1   | 署名が JWKS の公開鍵で検証できる                                | 401    |
| 2   | `alg` が期待するアルゴリズムと一致（**`none` と HMAC を拒否**） | 401    |
| 3   | `iss` が設定値と一致                                            | 401    |
| 4   | `aud` が設定値と一致                                            | 401    |
| 5   | `exp` が未来（クロックスキュー許容 🟡 60秒）                    | 401    |
| 6   | `sub` が存在                                                    | 401    |

> ⚠️ **`alg` の検証を省かない。** 検証ライブラリに許可アルゴリズムを明示的に渡し、
> トークン側の `alg` を信用しない（アルゴリズム混同攻撃対策）。

✅ **決定済 `UD-801`（2026-08-18）: 非対称鍵 + JWKS（ES256）で検証する。**

Supabase プロジェクト `sennokunnft` の JWT Signing Keys が
**ECC (P-256) へ切り替え済み**であることを確認した（2026-08-14 に鍵を交代。
旧 HS256 は交代前に発行されたトークンの検証用として残っているだけ）。

⚠️ **これは選好ではなく事実で決まっている。** いま HS256 を採ると、
**新しく発行されるトークンを検証できない鍵**を握ることになる。

結果的に望ましい形でもある:

- **api は公開鍵しか持たない。** api の設定が漏れてもトークンを偽造できない。
  共有シークレット方式では、鍵を持つ側が誰にでもなりすませる
- **鍵の入れ替えにデプロイが要らない。** api は鍵の一覧を取り直すだけ

⚠️ **未知の `kid` での鍵取得に回数制限を設ける。** 制限しないと、
でたらめな `kid` を大量に送るだけで JWKS 取得を詰まらせられる
（こちらの障害として跳ね返る）。

⚠️ **`TokenVerifierPort` は残す。** 検証方式が決まっても、
テストで擬似実装に差し替えられる価値は消えない。

### 1.3 アカウントの紐付け

```
Supabase JWT の sub
        │
        ▼
accounts (auth_provider='supabase', auth_subject=sub)   ← UNIQUE
        │  なければ初回アクセス時に作成（Just-In-Time provisioning）
        ▼
内部 account_id / role / status
```

🟡 **仮決定:** JIT プロビジョニングで作成されるアカウントの `role` は
**必ず `buyer`**。昇格は運営操作でのみ行う。
理由: 認証プロバイダ側の任意項目（`user_metadata` 等）は利用者が
改変しうる経路があるため、**ロールの正を外部トークンに置かない**。

> ⚠️ **JWT のクレームからロールを読まない。** ロールは常に本システムのDBを正とする。

### 1.4 セッションの保持

✅ **事実:** アクセストークンを localStorage に保存しない。

🟡 **仮決定:**

- ブラウザ側は **httpOnly / Secure / SameSite=Lax Cookie** でセッションを保持する。
- `apps/web` の Route Handler が Cookie からトークンを取り出し、
  サーバー間通信で `Authorization: Bearer` として `apps/api` に渡す。
- ブラウザの JavaScript からトークンに到達できない。

トレードオフ: 完全な SPA 的トークン運用に比べ実装が増えるが、
XSS でトークンを持ち出される経路を塞げる。

## 2. 認可（Authorization）

### 2.1 ロール

🟡 **仮決定:** MVP は次の3ロールのみ。

| ロール     | 説明                                                                   |
| ---------- | ---------------------------------------------------------------------- |
| `buyer`    | 一般利用者。自分の注文・受取権と、**自分が登録した作品**のみ操作できる |
| `operator` | 運営。作品・出品・注文の管理ができる                                   |
| `auditor`  | 監査。**読み取りのみ**。状態変更は一切できない                         |

さらに、認証していない利用者を `anonymous` として扱う。

❓ **未決定 `UD-802`:** 運営内のより細かい権限分離（作品登録者と価格決定者を分ける等）の要否。
組織体制が未提示。MVP は `operator` 単一で始める。

### 2.2 認可モデル

🟡 **仮決定:** **RBAC（ロール）＋ 所有権チェック（ABAC 的要素）** の2層。

```
リクエスト
   │
   ├─▶ ① 認証（トークン検証・アカウント解決）        … 失敗 → 401
   │
   ├─▶ ② ロール判定（エンドポイントに必要なロール）    … 失敗 → 403
   │
   └─▶ ③ 所有権判定（そのリソースは本人のものか）      … 失敗 → 403 / 404
```

> ⚠️ **② だけで済ませない。** 「buyer ならOK」で通すと、
> 他人の注文IDを指定して閲覧できる脆弱性（IDOR）になる。
> リソースを取得したうえで `resource.accountId === actor.accountId` を必ず確認する。

✅ **事実:** 管理APIは**認可ミドルウェアで一括保護**する。
ルート個別にチェックを書かない（書き忘れによる保護漏れを構造的に防ぐ）。

🟡 **仮決定:** 既定は **deny**。
`/api/v1/admin/**` はミドルウェアで `operator` を要求し、
公開してよいエンドポイントのみ明示的に `@Public()` で開放する。
「印を付け忘れたら公開されてしまう」ではなく「付け忘れたら閉じる」向きにする。

### 2.3 権限マトリクス

| 操作                                 | anonymous | buyer             | operator    | auditor |
| ------------------------------------ | --------- | ----------------- | ----------- | ------- |
| 公開作品の一覧・詳細を見る           | ✔         | ✔                 | ✔           | ✔       |
| 非公開作品を見る                     | —         | —                 | ✔           | ✔       |
| 注文を作成する                       | —         | ✔                 | —           | —       |
| **自分の**注文を見る                 | —         | ✔                 | ✔           | ✔       |
| 他人の注文を見る                     | —         | —                 | ✔           | ✔       |
| 決済セッションを作る                 | —         | ✔(自分の注文のみ) | —           | —       |
| Claim 内容を確認する                 | —         | ✔(トークン保持者) | —           | —       |
| Claim を実行する                     | —         | ✔(購入者本人のみ) | —           | —       |
| **自分の**コレクションを見る         | —         | ✔                 | ✔           | ✔       |
| **自分の**作品を登録・更新・公開する | —         | ✔                 | ✔           | —       |
| **自分の**作品を出品・販売開始する   | —         | ✔                 | ✔           | —       |
| 他人の作品を更新・公開する           | —         | —                 | ✔           | —       |
| 他人の出品を停止・終了する           | —         | —                 | ✔           | —       |
| 発行ジョブを手動再試行する           | —         | —                 | ✔           | —       |
| 監査ログを見る                       | —         | —                 | ✔           | ✔       |
| 他人の作品を削除する                 | —         | —                 | ✔           | —       |
| スタッフを招待する                   | —         | —                 | ✔(オーナー) | —       |
| スタッフの権限を変える               | —         | —                 | ✔(オーナー) | —       |
| 外部連携の状態を見る                 | —         | —                 | ✔           | ✔       |
| 外部連携の接続先を変える             | —         | —                 | ✔(オーナー) | —       |
| 外部連携の資格情報を登録・交換する   | —         | —                 | ✔(オーナー) | —       |
| 登録済みの資格情報を全文表示する     | —         | —                 | —           | —       |

✅ **決定 `UD-803`（2026-08-18）: オーナーが画面から招待・変更する。**

権限昇格経路は最も攻撃価値が高い。そこで、次の 4 つで囲ってある。

**1. 人事は「オーナー」だけが触れる。**
`staff.view` / `staff.invite` / `staff.manage` は、ロールが `operator` でも
**オーナーの印（`accounts.is_owner`）が無ければ通らない**。
運営の 1 人が乗っ取られただけで全権限を配り直されるのを防ぐ。

⚠️ **4 つ目のロールを作っていない。** ロールにすると、`operator` に許した
操作をすべて写す必要が生まれ、写し忘れが「オーナーだけできない操作」として
静かに残る。「何ができるか」（ロール）と「人に権限を配れるか」（印）を
**別の軸**にしてある。

**2. スタッフになる道は招待だけ。**
会員の一覧から誰でも昇格させる形にしていない。そうすると
(1) 誰が誰かを見分けるために全会員の連絡先を運営へ見せることになり、
(2) 押し間違いで無関係の会員が運営になる。

**3. 招待にトークンを持たせない。**
受諾は「その宛先でログインできたこと」だけで判定する。トークンを配ると、
転送・流出したリンクを拾った別人が権限を得られる。
突き合わせに使うのは、認証プロバイダが**確認済み**と示したアドレスのみ
(`email_verified`)。未確認の値を信じると、宛先を名乗るだけで権限を取れる。

⚠️ **確認済みアドレスをロールの判断に使わない。** 使ってよいのは
招待の宛先との突き合わせだけ。`Actor` にも入れていない
（入れると、いつか誰かが「このドメインの人は運営」と書く）。

**4. 締め出されない。**
自分自身の権限は変えられず（押し間違いと自己昇格の両方を防ぐ）、
有効なオーナーが 0 人になる変更は拒否される。
オーナーの人数を数えるのと書くのは**同じトランザクション**で行い、
対象行と有効なオーナーの行を `FOR UPDATE` でロックする。
分けると、2 人のオーナーが同時に互いを降ろして 0 人になれる。

⚠️ **最初のオーナーの任命だけは、アプリ内に経路を作っていない。**
自分を昇格させる経路を作らないための線引きで、DB 側で行う
（`docs/DEPLOYMENT_RUNBOOK.md` §3-6）。

### 2.4 出品できる資格（`UD-806`）

✅ **決定変更 2026-08-18（`UD-102`）:** 作家による自己出品を行う。

🟡 **仮決定 `UD-806`:** **会員登録した利用者（`buyer`）は誰でも出品できる。**
出品前の審査は行わない（事業判断）。

⚠️ **これは「合言葉の門の内側でしか使わない」ことを前提にした暫定措置。**
門（`SITE_GATE_PASSWORD`）が実質の入場制限として働いているあいだだけ成り立つ。
**門を外して一般公開する前に、必ず出品資格を締め直すこと。**
そのまま公開すると、登録した誰もが任意の画像と文章を公開できる状態になる。

⚠️ **`creator` ロールを新設しない。** 会員なら誰でも出品できるなら、
ロールは全員に付くことになり、判定として意味を持たない。
出品できるかどうかは**所有権**（`artworks.creator_account_id`）で判定する。
将来、招待制や出品者審査を入れるときは、
「役割を足す」のではなく「出品の入口に条件を足す」向きで実装する。

✅ **審査が無くても、下ろす経路はある。**
運営は他人の作品を `archive`、出品を `suspend` / `end` できる。
問題のある出品は事後に停止する運用で受け止める。

### 2.6 外部連携の設定（管理画面・外部連携 指示書 §8）

✅ **閲覧と変更で線を引く場所が違う。**
状態と履歴は `operator` と `auditor` にも見せ、接続先と資格情報は
**オーナーだけ**にする。一括で「運営なら可」にすると、運営の 1 人が
乗っ取られただけで**送信先ごと差し替えられる**。

| 操作                        | 必要なもの                     |
| --------------------------- | ------------------------------ |
| `integration.view`          | `operator` または `auditor`    |
| `integration.manage`        | `operator` ＋ **オーナーの印** |
| `integration.manage_secret` | `operator` ＋ **オーナーの印** |
| `wallet_delivery.retry`     | `operator`（印は要らない）     |

⚠️ **再送だけは印を要らない。** 運営の日常業務であり、送る内容は
Outbox に確定済みで、新しく何かを決める操作ではない。

⚠️ **登録済みの資格情報を全文表示する操作は、誰にも許していない。**
権限で絞るのではなく、**経路そのものを作らない**（指示書 §6.1・§14）。

⚠️ **止める操作にも `integration.manage` を要求する。**
誰でも止められると、それ自体が停止させる攻撃になる。

### 2.5 運営による作品の削除（`UD-113`）

✅ **事実:** 削除は `artwork.manage` で守る。**新しい操作を足していない。**
運営が他人の作品を触れること自体は `archive` で既に認めており、
削除のためだけに別の権限を作ると、権限表と実際の守りが二重になる。

⚠️ **出品者（`buyer`）に自分の作品の削除を開けていない。**
`artwork.manage_own` は編集・公開・公開停止までで、削除を含まない。
所有者なら消せる、は一見自然だが、**消してよい範囲が決まっていない**
（`UD-113`）。決まっていないものを「持ち主だから」で通すと、
決める前に取り返しがつかなくなる。

⚠️ **削除できる条件は認可ではなく、作品の状態で決まる。**
公開中でないこと・お支払い待ちと発行済みが 0 件であること。
これは「誰が押したか」ではなく「何が起きるか」の話なので、
認可ではなくドメイン（`prepareArtworkDeletion`）が判定する。

| 操作の入口           | 認可                                                         |
| -------------------- | ------------------------------------------------------------ |
| `/api/v1/admin/**`   | `operator` のみ（**これを弱めない**）                        |
| `/api/v1/creator/**` | 認証済み利用者。**対象が自分のものであることを毎回確認する** |

⚠️ **管理APIを出品者に開放しない。** `/api/v1/admin/**` を
「所有者なら通す」に変えると、一括保護という性質そのものが失われ、
どこか一箇所の書き漏れが他人のデータへの到達に変わる。
入口を分け、`admin` は `operator` 専用のまま保つ。

### 2.4 Claim の本人照合（最重要）

✅ **事実:** 「ログインユーザーと購入者を照合する」ことが MVP フローに含まれる。

🟡 **仮決定:** Claim 実行時に次を**すべて**満たすことを要求する。

| #   | 条件                                                              | 満たさない場合            |
| --- | ----------------------------------------------------------------- | ------------------------- |
| 1   | 認証済みであること                                                | 401（ログイン画面へ誘導） |
| 2   | Claim トークンのハッシュが `entitlements.claim_token_hash` と一致 | 404                       |
| 3   | `entitlements.status = 'issued'`                                  | 409                       |
| 4   | 期限内（`expires_at` が NULL または未来）                         | 409                       |
| 5   | **`entitlements.account_id` = 認証アカウントID**                  | 403                       |
| 6   | アカウントが `active`                                             | 403                       |

> ⚠️ **条件5を省略しない。** トークンだけで Claim できる設計にすると、
> URL が漏れた時点で第三者に受け取られる。
> 「トークンは URL の当てずっぽうを防ぐもの、本人性は認証で担保するもの」と役割を分ける。

❓ **未決定 `UD-804`:** 購入者と受取人が異なるケース（贈答・法人一括購入）を許すか。
許す場合、条件5を「受取人として指名されたアカウント」に緩和する設計が必要になる。
MVP は**購入者本人のみ**とする。

### 2.5 認可の実装配置

| 層              | 責務                                                                                   |
| --------------- | -------------------------------------------------------------------------------------- |
| `packages/auth` | トークン検証、アカウント解決、**純粋な認可判定関数**（`can(actor, action, resource)`） |
| `apps/api`      | NestJS Guard から `packages/auth` の判定関数を呼ぶ。HTTP へのマッピングのみ            |
| `apps/web`      | 画面の出し分けのみ。**認可の正としない**                                               |

> ⚠️ 画面側の出し分けはUXのためであり、セキュリティ境界ではない。
> サーバー側で必ず再判定する（✅「入力値はサーバー側で検証する」と同じ原則）。

判定関数を純粋関数にすることで、権限マトリクスを**表駆動のテスト**で網羅検証できる
（[TEST_STRATEGY.md](./TEST_STRATEGY.md)）。

## 3. サービス間認証

| 経路                      | 方式                           | 備考                                                               |
| ------------------------- | ------------------------------ | ------------------------------------------------------------------ |
| `apps/web` → `apps/api`   | 利用者の Bearer トークンを転送 | 利用者権限で動作する                                               |
| `apps/worker` → DB        | DB 資格情報                    | HTTP を経由しない                                                  |
| 内部 cron → `apps/api`    | 🟡 共有シークレットヘッダ      | 経路がある場合のみ                                                 |
| 外部システム → `apps/api` | Webhook 署名                   | [EXTERNAL_INTEGRATION_POLICY.md](./EXTERNAL_INTEGRATION_POLICY.md) |

❓ **未決定 `UD-805`:** 外部システム（既存の代理店システム等）が
本システムのAPIを呼ぶ必要があるか。ある場合、サービスアカウントと
スコープ設計が追加で必要になる。
