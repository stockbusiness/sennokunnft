## 1. 先に読むべきこと — 本番を作る前に必ず要る決定

構成の前に、**これが決まらないと本番が物理的に起動しない**ものが 3 件ある。
どれもサーバーを用意しても解決しない。

| #   | 事項                   | 今どうなっているか                                                                          | 影響                                              |
| --- | ---------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 1   | `UD-801` JWT 検証方式  | `AUTH_PROVIDER` の候補が `dev` のみ。`assertProductionSafety` が本番で `dev` を拒否         | **本番 api が起動しない**（設定ミスではなく仕様） |
| 2   | `UD-508` 画像の長期URL | 方式は Cloudflare R2 に確定。**アダプタ実装済み**（`R2Storage`）。Cloudflare 側の設定が残る | 設定するまで画像を配信できない                    |
| 3   | `UD-702` 決済事業者    | 未決定。Payment / Checkout は未実装                                                         | **購入導線が無い**。売れる本番にはならない        |

> ⚠️ **1 は「本番で dev 認証が使えない」という安全装置が正しく働いている状態。**
> 迂回してはならない。誰でもトークンを作れる検証方式で本番を開けることになる。

### 「本番」をどちらの意味で作るか

3 のため、**いま作れる本番は「売る本番」ではない**。2 通りある。

| 案                           | 何が動くか                                 | 前提                    |
| ---------------------------- | ------------------------------------------ | ----------------------- |
| **ア（推奨）連携先行の本番** | カタログ公開・管理画面・Claim・Wallet 配送 | 1 と 2 の解決           |
| イ 販売開始まで待つ          | 上記 ＋ 購入・決済                         | 1・2 ＋ `UD-702` の決定 |

**ア を推奨する。** 決済の決定を待つあいだ、本番と同じ形の環境で
OVEW Wallet との実接続を済ませられる。器を先に作っておけば、
決済が決まったあとに足すのは決済だけになる。

⚠️ ただし **ア の本番は「まだ何も売っていない本番」**である。
公開範囲（カタログを一般公開するか、関係者限定にするか）は別途決めていただきたい。

## 2. 構成（推奨案）

```
                                 [利用者のブラウザ]
                                        │ HTTPS
                ┌───────────────────────┼────────────────────────┐
                │                       │                        │
                ▼                       ▼                        ▼
        web (Next.js)            画像 (R2 Custom Domain)   ※ api への直接
        Vercel / 東京            media.example.jp             アクセスは無い
                │                  Cloudflare R2
                │ サーバー側から呼ぶ（BFF）
                ▼
        ┌───────────────────┐
        │  api (NestJS)     │◀────── HMAC v1.1 ────── [OVEW Wallet]
        │  Fly.io nrt ×2    │                          （Claim 2 本）
        └─────────┬─────────┘
                  │
                  ▼
        ┌───────────────────┐
        │  PostgreSQL 16    │
        │  Supabase 東京    │
        └─────────┬─────────┘
                  │
        ┌─────────┴─────────┐
        │  worker           │────── HMAC v1.1 ──────▶ [OVEW Wallet]
        │  Fly.io nrt ×1    │            （entitlement.granted / revoked）
        │                   │────── API key ────────▶ [代理店システム]
        └───────────────────┘            （common_user_id の解決）
```

### 選定の理由

| 要素       | 採用             | 理由                                                                                               |
| ---------- | ---------------- | -------------------------------------------------------------------------------------------------- |
| web        | Vercel           | Next.js 16 の素直な置き場。web は状態を持たないので台数が増えても壊れない                          |
| api        | Fly.io（東京）   | **常駐プロセスが要る。** NestJS + Express は関数実行に向かない（後述 §3）                          |
| worker     | Fly.io（東京）   | 配送のバックオフが 1 分刻み。cron の粒度では追随できない                                           |
| DB         | Supabase（東京） | 認証を Supabase に寄せる設計（`accounts.auth_provider` / `auth_subject`）と同居させる。PITR がある |
| 画像       | Cloudflare R2    | `UD-508` で決定済み。転送量課金が無く、Custom Domain で長期 URL を出せる                           |
| リージョン | 東京             | 利用者・OVEW Wallet・代理店システムのいずれも国内。往復を跨がせない                                |

## 2-2. サーバの選定 — 日本リージョン / 簡単 / 自動デプロイ

### 落ちた候補と、その理由

| 候補                   | 日本リージョン | 落ちた理由                                              |
| ---------------------- | -------------- | ------------------------------------------------------- |
| Render                 | ❌ 無し        | 最寄りがシンガポール。往復が増える                      |
| Railway                | ❌ 無し        | 同上                                                    |
| Heroku                 | ❌ 無し        | 同上                                                    |
| AWS App Runner         | ✅ 東京        | **HTTP サービス専用。worker を常駐させられない**        |
| さくらのVPS / クラウド | ✅ 国内        | 自動デプロイ・監視・OS 更新をすべて自前で持つことになる |

> 🟡 リージョン一覧は各社の都合で変わる。**契約前に一次情報で再確認すること。**

### 残った 2 つ

| 観点           | **Fly.io（推奨）**                  | Google Cloud Run                                                                                      |
| -------------- | ----------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 日本リージョン | ✅ `nrt`（東京）                    | ✅ `asia-northeast1`（東京）                                                                          |
| 常駐 worker    | ✅ そのまま常駐できる               | ⚠️ `min-instances=1` ＋ CPU 常時割当が要る（既定では止まる）                                          |
| 覚える概念     | app / machine / secret の **3 つ**  | project / service / revision / Artifact Registry / Cloud Build / Secret Manager / IAM の **7 つ以上** |
| 設定ファイル   | `fly.toml` **1 つ**                 | 複数（＋コンソール操作）                                                                              |
| 自動デプロイ   | GitHub Actions から `flyctl deploy` | GitHub 連携でビルドトリガー                                                                           |
| 日本語の情報量 | 少ない                              | 多い                                                                                                  |

**Fly.io を推奨する。** 判断は「常駐 worker」と「覚える概念の数」で決まった。

Cloud Run で worker を常駐させるには `min-instances=1` と CPU 常時割当を
**両方**設定する必要がある。⚠️ **どちらかを忘れると worker は静かに止まる。**
リクエストが来ないので落ちたことにも気づけず、Wallet への配送だけが溜まっていく。
Fly.io にはこの落とし穴が無い。

「簡単さ」は機能の多さではなく、**事故を起こしうる設定項目の少なさ**で見た。
Cloud Run は個々の操作は簡単だが、正しく動かすまでに触る箇所が多い。

### Fly.io を選ぶときの落とし穴

⚠️ **`auto_stop_machines` を worker で有効にしない。**
Fly.io は既定でアイドル時にマシンを止める設定を提案してくるが、
worker は HTTP を受けないので**常にアイドルに見える**。
止まると配送が進まず、しかもエラーは出ない。`fly.toml` に明示的に書く。

⚠️ **`primary_region = "nrt"` を必ず書く。**
省略すると、デプロイした人の最寄りリージョンになる。
出張先からデプロイしたら本番が海外に移った、が起こりうる。

⚠️ **api と worker を 1 つのアプリに同居させない。**
別アプリにする。同居させると台数を独立に変えられず、
api を 2 台にした瞬間に worker も 2 台になる（→ §3-2 の事故）。

### 自動デプロイの形

```
GitHub へ push（main）
   ↓
CI: lint / typecheck / test / build   ← 既存の ci.yml
   ↓ すべて通ったら
prisma migrate deploy（Direct 接続）  ← 独立ステップ
   ↓
flyctl deploy（api）→ flyctl deploy（worker）
   ↓
Vercel（web）は GitHub 連携で自動
```

必要な秘密情報は GitHub の Secrets に 2 つだけ。

| 名前                  | 用途                           |
| --------------------- | ------------------------------ |
| `FLY_API_TOKEN`       | Fly.io へのデプロイ            |
| `DIRECT_DATABASE_URL` | マイグレーション適用（Direct） |

⚠️ **`main` への push で自動デプロイするのは、本番の公開後は避ける。**
`main` を触るたびに本番が変わる。タグ（`v*`）か手動実行を起点にする。
公開前の構築中は `main` 起点で構わない。

### web を Vercel に置く理由

Next.js を GitHub 連携するだけで動く。設定ファイルが要らない。
⚠️ **サーバー処理のリージョンを東京（`hnd1`）に指定すること。**
既定のままだと api との往復が海外を経由する。

🟡 **全部を Fly.io に寄せる案もある**（管理先が 1 つになる）。
ただし Next.js は Dockerfile を自分で持つことになり、画像最適化なども自前になる。
**web だけ Vercel** を推奨する。

| クライアントがこう言ったら                 | 案                                    |
| ------------------------------------------ | ------------------------------------- |
| 「早く安く出したい」                       | **A**                                 |
| 「大手クラウドで」                         | **B**（費用重視）／ **C**（実績重視） |
| 「監査がある」「将来ほかの会社へ引き継ぐ」 | **C**                                 |
| 「データは国内事業者に置きたい」           | **D**                                 |

人が持つことになる。**月 1 万円の差より、担当者 1 人の負担の方が大きい。**

### 先に触れておくべき論点 — 個人情報の所在

案 A・B・C の事業者はいずれも海外法人（B・C はリージョンが東京でも同じ）。
個人情報保護法の「外国にある第三者への提供」に該当しうるため、
**プライバシーポリシーへの記載など、クライアントの法務が確認する事項**になる。

> ⚠️ **これは法的な助言ではない。** 弁護士・専門家の確認が要る。
> ただし**こちらから先に論点として出しておくと、あとで揉めない。**

このとき伝えられる材料が 1 つある。**本システムは個人情報を最小限しか持たない設計**になっている。

| 項目              | 本システムの扱い                                                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| メールアドレス    | **平文で保持しない。**照合用の値のみ（`UD-503`）。⚠️ 素のハッシュではなく鍵付き HMAC（`UD-121`）。素だと、よくあるアドレスを並べた表で元に戻せる |
| パスワード        | **一切保持しない。**認証の正は認証基盤側                                                                                                         |
| 受取トークン      | **平文で保持しない。**ハッシュのみ                                                                                                               |
| Wallet へ送る情報 | 個人情報を載せない。`common_user_id` まで                                                                                                        |

案 D を選んでも保護すべき情報の量は変わらない。**この設計は 4 案すべてに共通する。**

## 3. 台数を増やすと静かに壊れるもの（最重要）

「とりあえず 2 台にしておく」で壊れる箇所が **api に 1 つ、worker に 1 つ**ある。
どちらも**エラーを出さずに壊れる**ので、事前に手当てする。

### 3-1. api を 2 台にすると、レート制限の実効上限が 2 倍になる

`InMemoryRateLimiter` は**プロセス内メモリ**に数える。
2 台なら、1 台あたりの上限がそれぞれ独立に効くので、全体では 2 倍まで通る。

⚠️ **これは落ちない。ログにも出ない。** 上限を 300 に設定したつもりが
600 通る状態が、誰にも気づかれずに続く。台数を変えるたびに実効値が変わるので、
「いくつに設定したか」と「いくつ通るか」が永久にずれる。

| 対応                                  | 評価                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------ |
| **PostgreSQL 実装へ差し替え（推奨）** | `RateLimiterPort` があるので実装 1 本の追加で済む。毎分・鍵IDごとに 1 行 |
| Redis を足す                          | 速いが、監視・バックアップ対象が 1 つ増える。この規模では割に合わない    |
| api を 1 台に固定する                 | 上限は正しくなるが、**可用性が無くなる**。デプロイのたびに落ちる         |

**本番前に PostgreSQL 実装へ差し替える。** `hmac_nonces` と同じく、
一意制約と条件付き UPSERT で数える。1 分あたり鍵 ID ごとに 1 行なので、
書き込み量は問題にならない。

> ✅ 冪等キー（`idempotency_keys`）と nonce（`hmac_nonces`）は**既に DB にある**。
> api を何台に増やしても壊れない。残っているのはレート制限だけ。

### 3-2. worker を 2 台にすると、代理店システムを二重に呼ぶ

配送（`wallet_delivery_outbox`）は `FOR UPDATE SKIP LOCKED` で掴むので、
**何台でも同じ行を掴まない。**

しかし共通顧客ID の解決ジョブは違う。`listDue` は素の `SELECT` で、
行をロックしない。2 台が同時に走ると**両方が同じアカウントを拾い、
両方が代理店システムを呼ぶ**。

書き込みは `expectedAttemptCount` を条件にした `updateMany` なので
**データは壊れない**（勝つのは 1 本だけ）。壊れるのは相手側で、
`create_if_missing` が付いていると **`common_user_id` の新規発行が二重に走りうる**。

| 対応                                 | 評価                                                     |
| ------------------------------------ | -------------------------------------------------------- |
| **worker を 1 台に固定する（推奨）** | いま必要な処理量に対して 1 台で十分。追加実装が要らない  |
| `listDue` を SKIP LOCKED にする      | 台数を増やせるようになる。増やす必要が出てから行えばよい |

**当面 worker は 1 台。** 配送が詰まり始めたら、先に `listDue` を直してから増やす。

⚠️ **worker が 1 台であることを、デプロイ設定に明記して固定する。**
「なんとなく 1 台」だと、負荷対応で誰かが増やしたときに壊れる。
理由をコメントとして設定ファイルに残す。

## 4. DB への接続

| 項目             | 決め                                                            |
| ---------------- | --------------------------------------------------------------- |
| 接続経路         | Supabase の **Transaction Pooler**（pgBouncer）経由             |
| Prisma の指定    | 接続文字列に `?pgbouncer=true` を**必ず**付ける                 |
| マイグレーション | **Direct Connection** を使う（Pooler 経由では実行できない）     |
| プールサイズ     | api 1 台あたり小さく（5 前後）。台数 × プール ≦ 上限 を必ず守る |

⚠️ **`?pgbouncer=true` を忘れると、動いたり動かなかったりする。**
Prisma は prepared statement を使うが、Transaction Pooler は接続を使い回すため、
別のセッションが張った statement を参照して失敗する。
**負荷が上がってから初めて出る**ので、テスト環境では気づけない。

⚠️ **接続文字列を 2 本持つことになる。**（Pooler 用 / Direct 用）
取り違えると、マイグレーションが通らないか、アプリが不安定になる。
環境変数名で用途を分ける（`DATABASE_URL` / `DIRECT_DATABASE_URL`）。

## 5. デプロイの手順

```
1. CI（GitHub Actions）— lint / typecheck / test / build
        ↓ すべて通ったら
2. prisma migrate deploy         ← ★ 独立したステップ。1 回だけ
        ↓
3. api をデプロイ（ローリング）
        ↓
4. worker をデプロイ
        ↓
5. web をデプロイ
```

⚠️ **マイグレーションをアプリの起動時に走らせない。**
api が 2 台なら 2 回同時に走る。Prisma は advisory lock で衝突を避けるが、
片方が待たされて起動がタイムアウトし、**デプロイが不定期に失敗する**ようになる。
しかも失敗は「たまに」なので、原因がマイグレーションだと気づきにくい。

⚠️ **前方互換のマイグレーションだけを打つ。**
ローリング更新中は、新旧のコードが**同時に同じ DB を見る**。
列の削除や NOT NULL 化を 1 回のデプロイでやると、旧コードが落ちる。
「足す → 両対応で動かす → 使わなくなってから消す」の 3 回に分ける。

### ヘルスチェック

| エンドポイント | 用途                          | 設定先                     |
| -------------- | ----------------------------- | -------------------------- |
| `GET /healthz` | プロセスが生きているか        | コンテナの liveness        |
| `GET /readyz`  | DB へ届くか（503 を返しうる） | ロードバランサの readiness |

⚠️ **`/readyz` を liveness に使わない。** DB が一時的に落ちたときに
コンテナが再起動を繰り返し、DB が戻っても復帰が遅れる。

### 停止

api・worker とも SIGTERM で**処理中の仕事を終えてから**落ちる実装になっている。
プラットフォーム側の猶予時間を、worker の 1 巡より長く取る（30 秒以上）。

⚠️ **worker を強制終了させない。** `PROCESSING` のまま殺された配送行は、
外部へ送信済みかどうかが分からない。15 分後に自動回収するが、
その 15 分は「届いたか分からない」状態が続く。

## 6. 秘密情報

リポジトリに置かない。`.env.example` には**変数名と説明だけ**（`check:secrets` が検査している）。

| 変数                                   | 置き場                     | 備考                                           |
| -------------------------------------- | -------------------------- | ---------------------------------------------- |
| `DATABASE_URL` / `DIRECT_DATABASE_URL` | Fly secrets                | api・worker の両方                             |
| `CLAIM_HMAC_KEYS`                      | Fly secrets（api のみ）    | **受信用。** 鍵の入れ替え中は 2 本並べられる   |
| `WALLET_DELIVERY_SECRET`               | Fly secrets（worker のみ） | **送信用。** 受信用と別の鍵にする              |
| `COMMON_USER_API_KEY`                  | Fly secrets（worker のみ） | 代理店システム                                 |
| R2 のアクセスキー                      | Fly secrets（api のみ）    | 画像アップロードは api だけが行う              |
| `ADMIN_DEV_TOKEN`                      | —                          | **本番では使わない。** `UD-801` の解決で不要に |

⚠️ **送信用と受信用の HMAC 鍵を同じにしない。**
同じにすると、こちらが署名できる本文は相手も署名できる。
方向ごとに鍵を分けておけば、片方が漏れてももう片方は無事でいられる。

⚠️ **api に配送用の鍵を渡さない。worker に受信用の鍵を渡さない。**
必要な側だけに置く。漏れたときに影響する範囲が狭くなる。

## 7. 監視（`UD-1102`）

一般的な指標（CPU・メモリ・エラー率）に加えて、**この設計に固有の 3 つ**を見る。
どれも「落ちないまま間違っている」状態の検出で、他では気づけない。

| 見るもの                                      | 意味                              | 閾値の考え方          |
| --------------------------------------------- | --------------------------------- | --------------------- |
| `wallet_delivery_outbox` の `DEAD` / `FAILED` | Wallet へ届かないまま止まった配送 | **1 件でも通知**      |
| 「受取済みなのに配送行が無い」件数            | 行列に載せ損ねた受取（静かな穴）  | **常に 0 であるべき** |
| `accounts.common_user_status = 'CONFLICT'`    | 人手の確認が要る名寄せ            | 1 件でも通知          |

3 つめの検出クエリ:

```sql
-- 受け取ったのに Wallet へ届く見込みが無い受取権。常に 0 件であること。
SELECT e.id
  FROM entitlements e
  LEFT JOIN wallet_delivery_outbox o ON o.entitlement_id = e.id
 WHERE e.status = 'claimed'
   AND e.wallet_delivery_status = 'pending'
   AND o.id IS NULL;
```

⚠️ **配送が無効なあいだは、この件数が増えるのが正常。**
`WALLET_DELIVERY_ENABLED=false` のときは行列に載せない設計なので、
有効化するまでは 0 にならない。**有効化と同時に、それまでの分を
行列へ載せ直す必要がある**（載せ直しの手順は有効化の直前に用意する）。

### ログ

構造化ログ（pino）に相関IDが乗っている。**Claim から Wallet 配送まで
同じ `correlation_id` で追える。** 相手のログと突き合わせるときはこれを使う。

⚠️ **ログに個人情報・トークン・鍵を出さない。** マスキングは実装済みだが、
新しいログを足すときに素通りする出口を作らないこと。

## 8. バックアップ（`UD-1103`）

| 段階                   | 方式                                  | 理由                                              |
| ---------------------- | ------------------------------------- | ------------------------------------------------- |
| **公開前〜販売開始前** | Supabase Pro の日次バックアップ       | 失っても困る取引データがまだ無い。追加費用ゼロ    |
| **販売開始後**         | PITR（ポイントインタイムリカバリ）    | 注文が入る。**日次では最大 1 日分の注文が消える** |
| 保持期間               | 🟡 7 日以上を提案。要決定             |                                                   |
| 復旧手順の確認         | **本番稼働前に 1 回、実際に復元する** |                                                   |

⚠️ **PITR は Supabase Pro に含まれない有料アドオンで、月額が本体より高い**（§8-2）。
販売開始まで日次で足りるので、**決済を入れるときに合わせて足す**。

⚠️ **手順を書いただけで確認しないバックアップは、無いのと同じ。**
必要になるのは事故のときで、そのときに初めて試すことになる。

### ⚠️ 費用の罠 3 つ

**1. Vercel の Hobby は商用利用が禁止されている。**
無料だからと Hobby で本番を出すと規約違反になる。**Pro（$20）が必須**。
しかも **1 人あたり**の課金なので、関わる人が増えると比例して増える。

> 🟡 **web も Fly.io に置けば月 $20 → 約 $3 になる。**
> ただし Next.js の Dockerfile を自分で持つことになり、画像最適化も自前になる。
> **人数が 3 人を超えるなら、Fly.io へ寄せる方が安くなる。**
> 逆に 1〜2 人のうちは、Vercel の手間の少なさが $20 に見合う。

**2. Supabase の Free は本番に使えない。**
1 週間アクセスが無いとプロジェクトが**一時停止**する。
公開直後のアクセスが少ない時期に、まさにこれが起きる。

**3. PITR は本体より高い。**
Supabase Pro（$25）に PITR は含まれず、アドオンで約 $100。
⚠️ **これを「バックアップがあるはず」と思い込んだまま販売を始めない。**
Pro の既定は日次バックアップで、**障害の直前 23 時間分の注文が消えうる**。

### 費用より先に考えるべきこと

決済手数料は売上の 3〜4%（`UD-702` 未決定）。
**月商 30 万円で約 1 万円**になり、インフラ費とほぼ並ぶ。
月商 100 万円ならインフラ費は誤差になる。

⚠️ **インフラ費を削る方向に最適化しない。**
ここで削れるのはせいぜい月 1 万円で、削り方を間違えると
（api 1 台のまま販売開始・PITR 無しで運用）**失うものの方が大きい**。
節約するなら、段階1 のあいだに削る。

### 段階1 で api を 1 台にしてよい理由

公開前は利用者がいないので、デプロイ中に落ちても誰も困らない。
そして **1 台のあいだはレート制限（§3-1）が正しく効く**。
つまり「1 台 → PostgreSQL 版レート制限を実装 → 2 台」の順にすれば、
**壊れた状態を一度も通らずに済む**。

⚠️ **逆順にしない。** 2 台にしてからレート制限を直すと、
そのあいだ上限が 2 倍になる。しかも気づけない。

## 9. 段階的な公開手順

Feature Flag はすべて既定 OFF で実装済み。次の順で ON にする。
**1 つ ON にしたら、次に進む前に動作を確かめる。**

| 順  | フラグ                        | 前提                                           |
| --- | ----------------------------- | ---------------------------------------------- |
| 0   | （全 OFF で本番を起動）       | `UD-801` の解決                                |
| 1   | R2 アダプタの投入             | `UD-508` の設定完了。画像が HTTPS で見える     |
| 2   | `COMMON_USER_LINKING_ENABLED` | 代理店システムの本番鍵                         |
| 3   | `CLAIM_API_ENABLED`           | OVEW Wallet と固定テストベクトルが一致         |
| 4   | `WALLET_DELIVERY_ENABLED`     | **相手の 2xx が Holding 永続化を意味する**こと |

⚠️ **4 の前提を口頭で済ませない。**
相手が「共通顧客IDが合わないので何もしなかった」ときに 2xx を返す仕様だと、
こちらの `delivered` は嘘になる。**契約として確認してから ON にする。**

⚠️ **1 を飛ばして 4 を ON にしない。**
長期 URL の画像が無い作品では、受取そのものが失敗する。

## 10. 今回入れないもの

| 見送るもの       | 理由                                                                   |
| ---------------- | ---------------------------------------------------------------------- |
| Redis            | レート制限は PostgreSQL で足りる。監視・バックアップ対象を増やさない   |
| メッセージキュー | Outbox ＋ `SKIP LOCKED` で足りている。二重に持つと壊れ方が読めなくなる |

| 複数リージョン   | 利用者も連携先も国内。跨がせる理由が無い                               |
| Kubernetes       | プロセスが 3 つ。運用の手数に見合わない                                |
