# 実運用に必要な管理画面機能の洗い出し

**作成**: 2026-08-19
**目的**: 本番販売を始めたときに「画面から対応できない」で詰まる場面を、事前に洗い出す

⚠️ **この文書は「足りないもの」を並べている。** 実装済みのものは §2 にまとめてあり、
それ以外は原則として**まだ無い**。

---

## 0. 基本方針：運営者が管理画面だけで運営できること

**2026-08-19 決定。** 日々の運営に必要な設定・文言・表記は、**管理画面から変えられる**ようにする。
配備環境の設定ファイルを書き換えないと変えられない、という状態を残さない。
運営会社が変わる、料率が変わる、規約を直す——どれも起こることで、そのたびに
開発者の手を借りる形にすると、**変更が必要なときに変更できない**。

### 意図してこの方針から外すもの

外すものには理由がある。**「まだ作っていない」ではなく「作らないと決めた」**を区別する。

| 外すもの                                                        | 理由                                                                                                                                             | 代わりの経路                                                                                                               |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 決済の秘密鍵・Webhook 署名鍵                                    | 画面から替えられる口だけ先に作ると、**間違えたときに戻せない**。鍵の交換には再認証・二者承認・ローテーション・接続確認・緊急停止・復旧経路が要る | 配備環境の Secret 管理。管理画面は**状態だけ**を表示する。交換の仕組みは `UD-118`（`docs/PAYMENT_CREDENTIAL_ROTATION.md`） |
| Supabase の認証方式                                             | 認証の設定を画面から壊すと、**その画面へ入れなくなる**。締め出されると復旧の手立てが無い                                                         | 配備環境の設定                                                                                                             |
| 金額の直接書き換え・`paid` への手動変更・注文や決済データの削除 | 「直せる」ことが証跡を壊す（P0/P1 §9.3）                                                                                                         | そもそも作らない                                                                                                           |

⚠️ **例外を増やすときは、ここへ理由ごと書く。** 書かずに増やすと、次の人には
「作り忘れ」に見え、いつか作られる。

## 1. いちばん重要な結論

**現状のままでは、1 件目が売れた直後に運用が詰まる。** 理由は 3 つ。

| #   | 詰まる場面             | いま起きること                                                                                       |
| --- | ---------------------- | ---------------------------------------------------------------------------------------------------- |
| 1   | **作家さまへの支払い** | 売上の 80% を渡す必要があるが、**いくら渡すべきかを集計する画面が無く、渡したという記録も残せない**  |
| 2   | **返金**               | 決済事業者の画面で返金しても、こちらの注文・在庫・受取権が**追随しない**。手で直す経路も無い         |
| 3   | **問い合わせ対応**     | 「お金が引かれたのに届かない」と言われても、**注文番号でしか探せない**。日付・作品・金額から辿れない |

1 と 2 は**お金に直結**するため、本番販売の開始前に用意する必要がある。

## 3. 場面別の不足

### A. 作家さまへの支払い（精算）✅ **実装済 2026-08-20**（`UD-119`）

売上はこちらの決済アカウントに入る。作家さまの取り分（80%）は**別途こちらから振り込む**。
Stripe Connect は導入しない方針（`UD-702` の範囲外）なので、**振込の管理はこちらで持つしかない**。

洗い出した 7 点は、次のとおり埋まった。

| 不足していたもの                 | いまの状態                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------- |
| 作家さま別の売上集計             | ✅ 月末締め（JST）。`/admin/payouts` から締める                                                   |
| 締め期間の指定（月次など）       | ✅ `2026-08` の形で指定。⚠️ **締めを迎えていない月は締められない**                                |
| **支払い済み／未払いの記録**     | ✅ `draft → confirmed → paid`。⚠️ **二重払いは `payout_lines` の UNIQUE (order_id) が止める**     |
| 支払い明細（作家さまへ渡すもの） | ⚠️ **画面で見えるのは運営だけ。** 作家さまへ渡す形（PDF・メール）は未実装                         |
| 振込先口座の保持                 | ⚠️ **未実装。** 本人確認の範囲（`UD-124`）が決まっていないため                                    |
| 源泉徴収・支払調書               | ⚠️ **差し引いていない。** 要否が未確定（`UD-106`）                                                |
| 返金があった分の差し戻し         | ✅ 確定済みの精算に載っていた注文が返金されたら、次回で差し引く。差し引ききれない分はマイナス繰越 |

⚠️ **支払い記録は注文と同じ「動かない記録」として持ってある。** 最低支払額も
振込手数料の負担も、締めた時点の値を精算の行へ焼き付ける。あとから設定を
変えても過去の精算は動かない。

⚠️ **「お支払い済みにする」は振込そのものではない。** 実際に振り込んだかを
機械は確かめられないので、**オーナー限定＋再認証**にしてある。締める人
（`payout.manage`）と、払ったと宣言する人（`payout.mark_paid`）を分けている。

⚠️ **金額を人が直接書き換える口は無い。** 訂正は翌月の精算での調整として行う。
詳細と禁止事項は [SETTLEMENT_AND_REFUND.md](./SETTLEMENT_AND_REFUND.md) §3-3・§4。

### B. 返金 🔴 **本番前に必須**

いま返金の口はどこにも無い（決済 Phase P2 で明示的に対象外とした）。

| 不足しているもの                   | なぜ要るか                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------- |
| 全額返金                           | 誤購入・不具合への対応                                                      |
| 一部返金                           | 一部だけ提供できなかった場合                                                |
| 返金理由の記録                     | あとから説明できない                                                        |
| **在庫カウンタとの連動**           | ⚠️ 返金しても `reserved_count` が戻らないと、売れないのに売り切れ表示になる |
| **受取権との連動**                 | ⚠️ 発行済み・送付済みの受取権をどうするか（`UD-104` 未決定）                |
| 作家さまへの支払いとの連動         | 支払い済みなら差し戻しが要る                                                |
| 決済事業者側で返金された場合の追随 | 画面を使わず直接返金されることは必ず起きる                                  |

⚠️ **決済事業者の画面で返金されるケースを前提にする。** 運営が慌てて Stripe の管理画面から
返金するのは、実際に起きる。Webhook（`charge.refunded`）を受けてこちら側を追随させないと、
状態がずれたまま気づかれない。

✅ **`UD-104`（返金ポリシー）は 2026-08-20 に決定した。** 発行がどこまで進んだかで線を引く——
発行前は全額返金、発行済みは原則返金しない（回収できないため）、運営の不具合は期間を問わず
全額返金。受付は決済から 14 日。詳細は [SETTLEMENT_AND_REFUND.md](./SETTLEMENT_AND_REFUND.md) §2-1。

✅ **`UD-128`（決済の鍵を世代から読む）は 2026-08-20 に入った。** 返金は決済と同じ世代の
鍵でしか行えないため、これが前提だった。

**2026-08-20 に実装した**（`UD-104` / `UD-120`）。上の表は次のとおり埋まった。

| 不足していたもの                   | いまの状態                                                                      |
| ---------------------------------- | ------------------------------------------------------------------------------- |
| 全額返金                           | ✅ 注文の詳細画面から。⚠️ **合言葉「返金」の入力が要る**                        |
| 一部返金                           | ⚠️ **記録のみ**（方針どおり）。画面に金額の入力欄を作っていない                 |
| 返金理由の記録                     | ✅ 理由・対応の記録・行った人を残す                                             |
| 在庫カウンタとの連動               | ✅ 押さえていた枠を戻す。⚠️ **通し番号（`issued_count`）は戻さない**            |
| 受取権との連動                     | ✅ 未受取なら取り消し、受取り済みなら残す。発行処理中は取り消さない（`INV-M4`） |
| 作家さまへの支払いとの連動         | ⚠️ **未実装**（精算そのものが未実装のため。`UD-119` で入る）                    |
| 決済事業者側で返金された場合の追随 | ✅ `charge.refunded` を受けて追随。二重反映は DB の UNIQUE で止める             |

⚠️ **返金は「決済した当時の世代の鍵」で投げる**（`UD-118` §2）。当時の世代を
開けなければ**断る**。受付中の世代へ落ちると、無関係のアカウントから現金が
出ていく。運営会社を切り替えたあとも、**旧世代の鍵を退役させても消さない**こと。

⚠️ **チャージバック（`charge.dispute.*`）は未対応。** 事業者から争議の
知らせが来ても、こちらは何もしない。当面は事業者の画面で対応する。

### C. 問い合わせ対応 ✅ **実装済 2026-08-20**（`UD-121`）

洗い出した 4 点はすべて入った。

| 不足していたもの                               | どう入ったか                                                                            |
| ---------------------------------------------- | --------------------------------------------------------------------------------------- |
| 注文の検索（注文番号・期間・作品・金額・状態） | `GET /api/v1/admin/orders` に条件を追加。画面は `/admin/orders` の「注文をお探しする」  |
| 購入者から注文を辿る                           | `POST /api/v1/admin/orders/search`（メールの照合）。⚠️ **一覧・詳細画面は作っていない** |
| 注文の経過（タイムライン）                     | `GET /api/v1/admin/orders/:id/timeline`。決済試行・Webhook・対応メモを 1 列（古い順）   |
| 対応メモ                                       | `order_notes`（追記のみ）。`POST /api/v1/admin/orders/:id/notes`                        |

#### メールからの照合をどう作ったか

⚠️ **購入者のメールアドレスは平文で保持していない**（`UD-503` の決定。`email_hash` のみ）。
そのため「メールアドレスで検索」はできない。**購入者から聞いたアドレスをこちらで変換して
一致を探す**、という形になる。**問い合わせ手順そのものが変わる**ので、対応する人に周知が要る。

決めたこと:

1. **素のハッシュにしない。** メールアドレスは取りうる値が狭く、よくあるアドレスを
   並べた表と突き合わせれば元に戻せる。それでは平文を持たない意味が無い。
   鍵付きの HMAC-SHA-256（`EMAIL_LOOKUP_PEPPER`）で作る。
2. **鍵が無い配備では照合値を付けない。** 素のハッシュへ黙って落とさない。
   落とすと、配備によって保護の強さが変わり、どちらで作られた行なのか
   見分けが付かないまま同じ列に混ざる。
3. **「引けない」と「見つからない」を必ず分ける**（`EMAIL_LOOKUP_UNAVAILABLE` / 503）。
   同じ扱いにすると、鍵を入れ忘れた配備で問い合わせてきた方に
   「そのご注文はありません」と、事実でないことを答えることになる。
4. **`POST` で本文に入れて送る。** 問い合わせ文字列はアクセスログ・ブラウザ履歴・
   共有されたリンクに残る。平文を持たないと決めた値を、持たない代わりにログへ撒かない。
5. **照合値は初回アクセス時に付く。** 認証プロバイダが**確認済み**としたアドレスだけを
   変換して残す。**鍵を入れ替えると、それ以前の照合値は引けなくなる**（下記）。

⚠️ **検索欄を作るときに、購入者の情報を一覧へ出さないこと。** 探せることと、並べて見えることは別。
メールから辿ったときも同じ札（`AdminOrderCard`）を使っている。辿り方によって見える量が
変わらないようにするため。

#### 鍵（`EMAIL_LOOKUP_PEPPER`）を入れ替えるとき

⚠️ **入れ替えると、それ以前に付いた照合値は引けなくなる。** 元のアドレスを持っていないので
付け直せない。**入れ替えるのは、漏洩したときだけ**にする。入れ替えたあとは、
各利用者が次にログインした時点で新しい鍵の照合値が付く。それまでは引けない。

#### まだ無いもの（`UD-121` の残り）

- **購入者の一覧・詳細画面**は作っていない。⚠️ 作ると「購入者を眺める画面」になる。
  問い合わせに要るのは「この方の注文を出す」ことで、一覧ではない。
- **`operator` が購入者の情報をどこまで見てよいか**（§5 の論点）は**未決定のまま**。
  いまは狭い側に倒してある: `auditor` にはメールからの照合も対応メモの記入も渡していない
  （`order.lookup_buyer` / `order.note` は `operator` のみ）。広げるのは簡単、狭めるのは難しい。
- **件数が増えたときの検索の速さ。** 注文番号の末尾一致と作品名の部分一致は `LIKE '%...'` に
  なり、B-Tree 索引が効かない。効かない索引は置いていない（置くと書き込みだけ重くなる）。
  遅くなったら `pg_trgm` + GIN で対応する。

## 4. 優先度

### 🔴 本番販売の開始前に必須

1. **作家さまへの支払い（精算）** — 無いと 1 件目から詰まる
2. **返金** — `UD-104`（返金ポリシー）の事業判断が先
3. **特商法表記の中身**（`UD-111`）— 編集の仕組みは用意済み。法務確認が先

## 5. 設計上、先に決めておきたいこと

これらは実装の形を左右するので、作り始める前に決める。

| 論点                           | なぜ先に決めるか                               |
| ------------------------------ | ---------------------------------------------- |
| ~~**返金の範囲**（`UD-104`）~~ | ✅ 決定済 2026-08-20。発行の進み具合で線を引く |
| **精算の締め方**               | 月次か、都度か。締めた記録の持ち方が変わる     |
| **税の扱い**（`UD-401`）       | 税額を注文に持つのか、集計時に計算するのか     |
| **本人確認の要否**             | 作家さま登録の流れが変わる                     |
| **問い合わせ対応の権限**       | `operator` が購入者の情報をどこまで見てよいか  |

⚠️ **`operator` が見てよい範囲は、早めに決めたほうがよい。** あとから絞ると
「今まで見えていたものが見えない」となり、運用が回らなくなる。広げるのは簡単、
狭めるのは難しい。
