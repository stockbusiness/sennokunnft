# 実運用に必要な管理画面機能の洗い出し

**作成**: 2026-08-19
**目的**: 本番販売を始めたときに「画面から対応できない」で詰まる場面を、事前に洗い出す

⚠️ **この文書は「足りないもの」を並べている。** 実装済みのものは §2 にまとめてあり、
それ以外は原則として**まだ無い**。

---

## 0. 基本方針：運営者が管理画面だけで運営できること

**2026-08-19 決定。** 日々の運営に必要な設定・文言・表記は、**管理画面から変えられる**ようにする。
配備環境の設定ファイルを書き換えないと変えられない、という状態を残さない。
運営会社が変わる、料率が変わる、規約を直す——どれも起こることで、そのたびに
開発者の手を借りる形にすると、**変更が必要なときに変更できない**。

### 意図してこの方針から外すもの

外すものには理由がある。**「まだ作っていない」ではなく「作らないと決めた」**を区別する。

| 外すもの                                                        | 理由                                                                                                                                             | 代わりの経路                                                                                                               |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 決済の秘密鍵・Webhook 署名鍵                                    | 画面から替えられる口だけ先に作ると、**間違えたときに戻せない**。鍵の交換には再認証・二者承認・ローテーション・接続確認・緊急停止・復旧経路が要る | 配備環境の Secret 管理。管理画面は**状態だけ**を表示する。交換の仕組みは `UD-118`（`docs/PAYMENT_CREDENTIAL_ROTATION.md`） |
| Supabase の認証方式                                             | 認証の設定を画面から壊すと、**その画面へ入れなくなる**。締め出されると復旧の手立てが無い                                                         | 配備環境の設定                                                                                                             |
| 金額の直接書き換え・`paid` への手動変更・注文や決済データの削除 | 「直せる」ことが証跡を壊す（P0/P1 §9.3）                                                                                                         | そもそも作らない                                                                                                           |

⚠️ **例外を増やすときは、ここへ理由ごと書く。** 書かずに増やすと、次の人には
「作り忘れ」に見え、いつか作られる。

---

## 1. いちばん重要な結論

**現状のままでは、1 件目が売れた直後に運用が詰まる。** 理由は 3 つ。

| #   | 詰まる場面             | いま起きること                                                                                       |
| --- | ---------------------- | ---------------------------------------------------------------------------------------------------- |
| 1   | **作家さまへの支払い** | 売上の 80% を渡す必要があるが、**いくら渡すべきかを集計する画面が無く、渡したという記録も残せない**  |
| 2   | **返金**               | 決済事業者の画面で返金しても、こちらの注文・在庫・受取権が**追随しない**。手で直す経路も無い         |
| 3   | **問い合わせ対応**     | 「お金が引かれたのに届かない」と言われても、**注文番号でしか探せない**。日付・作品・金額から辿れない |

1 と 2 は**お金に直結**するため、本番販売の開始前に用意する必要がある。

## 3. 場面別の不足

### A. 作家さまへの支払い（精算）🔴 **本番前に必須**

売上はこちらの決済アカウントに入る。作家さまの取り分（80%）は**別途こちらから振り込む**。
Stripe Connect は導入しない方針（`UD-702` の範囲外）なので、**振込の管理はこちらで持つしかない**。

| 不足しているもの                 | なぜ要るか                                                                       |
| -------------------------------- | -------------------------------------------------------------------------------- |
| 作家さま別の売上集計             | いくら振り込むのか、画面から出せない                                             |
| 締め期間の指定（月次など）       | いつからいつまでの分か決められない                                               |
| **支払い済み／未払いの記録**     | ⚠️ **これが無いと二重払いを防げない。** 振り込んだかどうかを記憶に頼ることになる |
| 支払い明細（作家さまへ渡すもの） | 内訳を示せないと問い合わせになる                                                 |
| 振込先口座の保持                 | いま持っていない                                                                 |
| 源泉徴収・支払調書               | 国内の個人作家では必要になりうる（`UD-106` と連動）                              |
| 返金があった分の差し戻し         | 返金後に支払うと払い過ぎになる                                                   |

⚠️ **支払い記録は注文と同じ「動かない記録」として持つこと。** 集計をその都度計算するだけの
作りにすると、あとから率や返金が変わったときに過去の支払額と合わなくなる。
**支払い時点でスナップショットを取る**（注文の手数料率と同じ考え方）。

### B. 返金 🔴 **本番前に必須**

いま返金の口はどこにも無い（決済 Phase P2 で明示的に対象外とした）。

| 不足しているもの                   | なぜ要るか                                                                  |
| ---------------------------------- | --------------------------------------------------------------------------- |
| 全額返金                           | 誤購入・不具合への対応                                                      |
| 一部返金                           | 一部だけ提供できなかった場合                                                |
| 返金理由の記録                     | あとから説明できない                                                        |
| **在庫カウンタとの連動**           | ⚠️ 返金しても `reserved_count` が戻らないと、売れないのに売り切れ表示になる |
| **受取権との連動**                 | ⚠️ 発行済み・送付済みの受取権をどうするか（`UD-104` 未決定）                |
| 作家さまへの支払いとの連動         | 支払い済みなら差し戻しが要る                                                |
| 決済事業者側で返金された場合の追随 | 画面を使わず直接返金されることは必ず起きる                                  |

⚠️ **決済事業者の画面で返金されるケースを前提にする。** 運営が慌てて Stripe の管理画面から
返金するのは、実際に起きる。Webhook（`charge.refunded`）を受けてこちら側を追随させないと、
状態がずれたまま気づかれない。

⚠️ **`UD-104`（返金ポリシー）が未決定のまま。** Claim 後・Mint 後に返金してよいかが決まらないと、
実装の形が決まらない。**事業判断が先**。

### C. 問い合わせ対応 🟠 **開始直後に必要**

| 不足しているもの                               | なぜ要るか                                                               |
| ---------------------------------------------- | ------------------------------------------------------------------------ |
| 注文の検索（注文番号・期間・作品・金額・状態） | いまは状態での絞り込みだけ。「先週このくらいの金額で買った」から辿れない |
| 購入者から注文を辿る                           | 購入者の一覧・詳細画面が無い                                             |
| 注文の経過（タイムライン）                     | いつ何が起きたかが、決済試行と Webhook 記録に分かれていて追いにくい      |
| 対応メモ                                       | 誰がどう対応したかが残らない                                             |

⚠️ **購入者のメールアドレスは平文で保持していない**（`UD-503` の決定。`email_hash` のみ）。
そのため「メールアドレスで検索」はできない。**購入者から聞いたアドレスをこちらでハッシュ化して
一致を探す**、という形になる。これは設計として妥当だが、**問い合わせ手順そのものが変わる**ので、
対応する人に周知が要る。

⚠️ **検索欄を作るときに、購入者の情報を一覧へ出さないこと。** 探せることと、並べて見えることは別。

### D. 会計・税務 🟠 **開始直後に必要**

| 不足しているもの             | なぜ要るか                                 |
| ---------------------------- | ------------------------------------------ |
| 日次・月次の売上レポート     | 締めができない                             |
| 消費税の集計                 | `UD-401` が「税額の内訳計算は未定」のまま  |
| CSV 書き出し                 | 会計処理へ渡せない                         |
| インボイス（適格請求書）対応 | 事業者向け販売がある場合に必要             |
| 決済事業者の入金との突合     | 入金額と注文の合計が合うかを確かめられない |

⚠️ **突合の口は早めに作る。** 決済事業者からの入金と、こちらの注文合計が合わないことは起きる
（返金・チャージバック・手数料）。合わないことに月末に気づくと、原因を遡るのが難しくなる。

### E. 受取権と配送（Phase P3）🟠

| 不足しているもの                  |
| --------------------------------- |
| 受取権の発行状況の一覧            |
| 発行失敗の再試行（画面から）      |
| Claim の状況・再発行（`UD-1009`） |
| シリアル番号の確認                |

Wallet 送信の一覧・再送は**実装済み**（`/admin/wallet-deliveries`）。

### F. 作家さまの管理 🟠

| 不足しているもの             | なぜ要るか                     |
| ---------------------------- | ------------------------------ |
| 作家さまの一覧・詳細         | いまは作品からしか辿れない     |
| 登録の審査・承認             | 誰でも出品できてよいのか       |
| 本人確認                     | 支払いを行う以上、必要になる   |
| 契約状態（規約への同意記録） | 手数料率の合意をどう示すか     |
| 作家さま単位での出品停止     | 問題が起きたときに止められない |

### G. 法務・表示 🔴 **本番前に必須**

| 不足しているもの                           | 状態                                                                                                          |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 特商法表記の**編集と公開**                 | ✅ 実装済（2026-08-19）。`/admin/legal/tokushoho`。12 項目が埋まるまで公開できない。`docs/LEGAL_DOCUMENTS.md` |
| 利用規約・プライバシーポリシーの版管理     | ✅ 実装済（2026-08-19）。`/admin/legal`。公開済みの版は書き換えも削除もできない                               |
| 特商法表記の**法務確認**                   | `UD-111` 未決定。**書ける状態にはなったが、何を書くかの確認が済むまで本番販売を開始できない**                 |
| 規約への**同意記録**                       | ✅ 実装済（2026-08-19、`UD-126` 決定）。初回ログイン時に同意を取り、注文へその時点の版を残す                  |
| 改定を既存の購入者へ知らせる経路           | `UD-127` 未着手。再同意の印は次のログインまで効かない                                                         |
| 作家さまごとの表記（出品者が事業者の場合） | `UD-111` に含む                                                                                               |

### H. 監視・異常検知 🟠

| 不足しているもの                                             | なぜ要るか                                                                                  |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| ダッシュボード（当日の売上・失敗した決済・滞留している注文） | いま「何か起きているか」を知る手段が無い                                                    |
| **滞留注文の検出**                                           | `checkout_created` のまま放置された注文。決済 P2 §13 で「定期照合ジョブは次工程」としたもの |
| Webhook の失敗・未処理の検出                                 | 記録はあるが、気づく仕組みが無い                                                            |
| Outbox の DEAD 監視                                          | 記録はある。通知が無い                                                                      |
| アラートの通知先                                             | `UD-1102` 未決定                                                                            |

⚠️ **「記録がある」と「気づける」は別。** いまは全部、人が見に行かないと分からない。

### I. データ整合の点検 🟠

| 不足しているもの             | なぜ要るか                                                             |
| ---------------------------- | ---------------------------------------------------------------------- |
| 在庫カウンタと実データの照合 | `reserved_count` / `issued_count` が予約行・受取権の実数と合っているか |
| ずれたときの修復手順         | 直す口が無い                                                           |

⚠️ **修復の口は「人が自由に値を入れる」形にしないこと。** 決済 P0/P1 §9.3 が
「在庫数と無関係な予約作成」を禁じている。**再計算して合わせる**形にする。

### J. 通知 🟠

| 不足しているもの                                     | 状態                         |
| ---------------------------------------------------- | ---------------------------- |
| 購入者への通知（注文確認・支払い完了・受取のご案内） | `UD-201`（メール基盤）未決定 |
| 送信履歴                                             | 未着手                       |
| 文面の管理                                           | 未着手                       |

## 4. 優先度

### 🔴 本番販売の開始前に必須

1. **作家さまへの支払い（精算）** — 無いと 1 件目から詰まる
2. **返金** — `UD-104`（返金ポリシー）の事業判断が先
3. **特商法表記の中身**（`UD-111`）— 編集の仕組みは用意済み。法務確認が先
4. **決済資格情報の世代管理**（`UD-118`）— 販売開始後だとデータ移行が要る

### 🟠 開始直後に必要

5. 注文の検索と問い合わせ対応
6. 滞留注文・Webhook 失敗の検出とダッシュボード
7. 売上レポートと CSV 書き出し
8. 受取権の発行状況（Phase P3 と同時）

### 🟡 落ち着いてから

9. 作家さまの管理（審査・本人確認）
10. データ整合の点検と修復
11. 通知の文面管理

## 5. 設計上、先に決めておきたいこと

これらは実装の形を左右するので、作り始める前に決める。

| 論点                       | なぜ先に決めるか                                      |
| -------------------------- | ----------------------------------------------------- |
| **返金の範囲**（`UD-104`） | Claim 後・Mint 後に返金するかで、受取権の扱いが変わる |
| **精算の締め方**           | 月次か、都度か。締めた記録の持ち方が変わる            |
| **税の扱い**（`UD-401`）   | 税額を注文に持つのか、集計時に計算するのか            |
| **本人確認の要否**         | 作家さま登録の流れが変わる                            |
| **問い合わせ対応の権限**   | `operator` が購入者の情報をどこまで見てよいか         |

⚠️ **`operator` が見てよい範囲は、早めに決めたほうがよい。** あとから絞ると
「今まで見えていたものが見えない」となり、運用が回らなくなる。広げるのは簡単、
狭めるのは難しい。
