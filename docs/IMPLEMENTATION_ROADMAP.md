> ⚠️ **Phase 5 は凍結（2026-08-14 の方針変更）。**
> MVP では Blockchain Mint を行わない。購入時にも Claim 時にも Mint しない。
> 当面は「**ブロックチェーン未発行**」のデジタルコレクションとして運用する。

### MVP の完成条件（2026-08-14 確定）

```text
作品登録 → 出品 → 購入 → 決済 → Entitlement 発行 → Claim
  → OVEW Wallet へ entitlement.granted → CollectibleHolding 作成
  → Wallet Collection へ表示
```

**ここまでが MVP。Mint 成功は受入条件に含めない。**

⚠️ **「後回し」であって「やめた」ではない。**
将来、利用者が「NFT として発行する」を選んだとき・外部 Wallet へ送るとき・
二次流通へ出すとき・オンチェーンの所有証明が要るときに、
**オンデマンドで** Mint する。そのための未決定事項は消さずに残してある。

⚠️ **いま Mint を見越した作り込みをしない。**
チェーンが決まっていない状態で「あとで差し替えられるように」と器だけ作ると、
決まったときにその器が合わず、二重に作り直すことになる。
必要になってから、決まった仕様に合わせて作る。

## 3. Phase 2 以降の概要

### Phase 2 — カタログ（完了）

実装したもの:

- 初期マイグレーション（18 個の CHECK 制約を手書きで追加）
- `artworks` / `listings` のリポジトリ実装（キーセットページング）
- ドメイン層の作品・出品ユースケース（状態遷移・公開条件・購入可否判定）
- 管理API（作品の登録・更新・公開・非公開、出品の作成・更新・開始・停止・終了）
- 公開カタログAPI（一覧・詳細）と画面
- 認可ガード（既定 deny・ロール判定）と開発用トークン検証
- 実 PostgreSQL に対する制約の結合テスト（M-1/M-2/S-4）

**実装しなかったもの:**

- **管理画面（UI）** — 運営がログインする経路が Phase 4（認証連携）なので、
  いま画面だけ作ると擬似ログインを画面側に置くことになる。
  それを本番へ持ち込む事故を避けるため、**Phase 4 へ送る**。
  管理APIは実装済みで、テストからも手元からも操作できる。
- **ロール変更API** — 権限昇格の経路は最も攻撃価値が高い（`UD-803`）。
  経路そのものを作らず、DB 直操作＋監査で運用する。

### Phase 3 — 決済と注文（**MVP の次工程**）

⚠️ **`UD-702`（決済事業者）が未決定でも着手する。**
ポートと Fake / テスト用アダプタで注文フローを先に完成させる。
決済事業者が決まってから実アダプタを足す。

⚠️ **決済事業者を前提にしたドメイン設計にしない。**
事業者固有のIDを主キーにしない。同期の決済結果だけで業務の成功を確定しない
（確定は Webhook で行う）。ここを崩すと、事業者を変えるときに
ドメインごと作り直しになる。

- 注文作成（在庫仮引当・行ロック）
- 決済セッション作成（**テスト環境のみ**）
- Webhook 受信（署名検証・冪等・受取権発行）
- 期限切れ注文の回収ワーカー
- 必須テスト I-1/I-2、S-1〜S-5、W-1〜W-8、A-4/A-5

**前提となる決定:** `UD-702`（決済事業者）、`UD-401`（通貨・税）

### Phase 4 — 認証と Claim

- Supabase Auth 連携（JWT 検証、JIT プロビジョニング）
- **`common_user_id` の解決と保持**（正本は代理店システム。本システムでは発行しない）
- Claim 確認（GET）と実行（POST）
- **Claim の本人照合**（購入者の `common_user_id` と一致すること）
- コレクション表示
- 必須テスト I-3/I-4、M-3、Z-1〜Z-8

**前提となる決定:** `UD-801`（JWT 検証方式）、`UD-505`（Claim 期限）、`UD-504`（ゲスト購入）、
`UD-1005`（Claim API の認証）、`UD-1006`（`common_user_id` の補完条件）

> ⚠️ **外部の解決失敗で購入を止めない。**
> `common_user_id` の解決は非同期にし、未解決でも受取権は発行する。

### Phase 4.5 — OVEW Wallet 連携

Phase 4 の完了後、Phase 5 の前に行う。
**ブロックチェーンの決定を待たずに進められる**のが、この Phase を切り出す理由。

- Wallet Integration Adapter（内部イベント → 外部イベントの変換）
- 千ノ国共通 HMAC（`X-SenNoKuni-*`）。汎用の `X-Sengoku-*` は残す
- Wallet Outbox Dispatcher（`entitlement.granted` / `entitlement.revoked`）
- 配送状態の記録、再試行、DLQ と手動再送
- staging での結合試験

**前提となる決定:** `UD-508`（画像の長期参照方式）、`UD-1007`（Claim 状態の対応）

> ⚠️ **`UD-508` は Phase 4.5 のブロッカー。**
> Wallet へ渡せるのは Wallet 側から取得できる HTTPS URL であり、
> 現在のローカル保存では発行できない。短期署名 URL を長期表示用に
> スナップショットへ保存することもできない（期限切れで表示が壊れる）。

詳細は [EXTERNAL_INTEGRATION_POLICY.md](./EXTERNAL_INTEGRATION_POLICY.md) §5.2。

### Phase 5 — Mint

- worker のジョブループ（`SKIP LOCKED` 排他取得、バックオフ）
- 実 `MintingPort` アダプタ
- メタデータ生成と保存
- 必須テスト I-5/I-6、M-4

**前提となる決定:** `UD-501` `UD-502` `UD-506`〜`UD-512` `UD-902`
→ いずれも**未決定のまま保持**。MVP のブロッカーからは外した。

> ⚠️ **2026-08-14 の方針変更で凍結。** MVP では Mint を行わない。
> 将来のオンデマンド Mint の流れは次のとおり。
>
> ```text
> Holding ACTIVE → 利用者が発行を要求 → Mint Job → Blockchain
>   → token_id / tx_hash / contract_address / network → Wallet Holding ONCHAIN
> ```

### Phase 6 — 運用

- 管理画面（注文・受取権・ジョブの一覧と手動再試行）
- 返金処理
- Outbox 配信ワーカーと外部連携
- 整合性チェックの日次実行、監視・アラート

**前提となる決定:** `UD-104`（返金ポリシー）、`UD-1102`（監視基盤）

⚠️ **`UD-109`（手数料率）・`UD-110`（送金）・`UD-111`（特商法表記）が
未決定のあいだは、出品はできても販売を開始してはならない。**
代金を受け取る仕組みと、作家へ渡す仕組みと、法定の表示が揃っていない。
Claim Token の平文を保持しない設計のため、紛失時に**再表示できない**。
これは正しい設計だが、復旧手段が無いままでは運用できない。
OVEW Wallet 連携の指示書を精査した結果、実装前に決めないと
取り返しがつかない箇所が見つかったため。

## 4-9. 実運営に向けた 4 つの決定（2026-08-20）

「NFTマーケット 実運営不足機能 実装指示書」の精査で、既存の決定と
食い違う 4 点が見つかった。いずれも同日に決着している。

### ✅ 作品審査へは戻さない（`UD-102` を維持）

指示書 §12 は「初期運営は管理者承認制」とし、
`draft → submitted → under_review → approved/rejected → published` を求めていた。
**採らない。** `UD-102`（決定変更 2026-08-18）の「作家の自己出品を行う。
出品前の審査は行わない」を維持する。

⚠️ **`UD-102` の行は書き換えない。** 覆さなかったことも記録として要る。

審査と切り離せる 2 つは別途扱う——公開後の緊急販売停止（既存の `archive` と
出品の `suspend` で足りている）と、著作権・第三者権利侵害の確認欄
（**審査ではなく出品者ご自身の申告**として置く）。

> **2026-08-21 に再確認した。** P1-2（作家さま運営）の実装で指示書 §12 の
> 審査の流れを再度検討したが、**入れないことを維持**した。ただし
> **将来入れる可能性は残す**。入れるときに先に決めるべきことは §4-17 に
> 一覧してある（とくに**既存の `published` 作品の扱い**）。

### ✅ 購入者のお名前は注文へ焼き付ける。メールは平文で持たない（`UD-503` 維持）

指示書 §11 は顧客詳細に「氏名、メールアドレス」を求めていた。

**前提のずれがあった。** 購入者の氏名は、どこにも保存していない。
`accounts.display_name` は**作家さまの名乗り**（決定 2026-08-20）で、
購入者はほぼ未設定である。

決定は次のとおり。

|          |                                                                                                                   |
| -------- | ----------------------------------------------------------------------------------------------------------------- |
| お名前   | Stripe が決済時に受け取る請求先氏名を、**注文へスナップショット保存**する                                         |
| 置き場所 | `orders.buyer_name_snapshot`（P1-1 で追加）                                                                       |
| メール   | **平文で持たない**（`UD-503` 維持）。詳細画面には既存の「聞き取ったアドレスで照合」（`order.lookup_buyer`）を置く |

⚠️ **なぜスナップショットか。** 決済のたびに必ず取れて、購入者に追加入力を
求めず、注文時点の値なので既存のスナップショット原則にそのまま乗る。

✅ **決定 2026-08-21・実装済:** 運営がご連絡先を見られるようにした。ただし
**保存はしない。** `UD-503` は維持したまま、**押されたときだけ認証基盤から
取り寄せて表示し、閲覧を監査ログへ残す**。詳しくは §4-18。

### ✅ 役割は増やさない。`support` を 1 つだけ足す（`UD-803` の範囲で）

指示書 §18 は Owner / Admin / Support / Finance / Creator の 5 分離を求めていた。
**5 つには増やさない。**

- **Creator を役割にしない。** いまは「作品の持ち主か」で判定している
  （`artwork.manage_own` など）。役割にすると、**作家でもあり買い手でもある人**を
  表せなくなる。実際そうなる方が多い。
- **Finance は既にオーナー限定で押さえている。** `settlement.manage` /
  `payment_credential.manage` / `payout.mark_paid` はオーナーの印＋再認証が要る。
- **増やすほど、操作を 1 つ足すたびに 5 か所の判断が要る。** 広げるのは簡単だが、
  一度渡した権限は取り上げにくい。

⚠️ **ただし `support` の穴は実在する。** いまサポート担当を雇うと `operator` を
渡すことになり、**全作品の削除・返金・精算の締め**まで押せる。
`buyer / support / operator / auditor` の 4 つにし、`support` は `operator` の
部分集合（注文の閲覧・メール照合・対応メモ・Claim 再発行・Wallet 再配送まで。
返金・作品削除・精算は含めない）とする。**実装は P1-1（顧客管理）と同時**でよい。

❓ **未決:** `payout.manage`（精算期間を締める）をオーナー限定へ寄せるか。
締めた行は `confirmed` 以降書き換えない設計なので実質戻せないが、いまは
`operator` なら誰でも押せる。

### ✅ MFA は Supabase の `aal` クレームで判定する（段階導入）

指示書 §10 の「管理者 MFA 方針が満たされている」の判定方法。

**Supabase の JWT は `aal` クレームを持つ。** 二要素まで済ませたセッションは
`aal2`、パスワード／マジックリンクだけなら `aal1`。**外部への問い合わせは要らず、
いま署名検証している同じトークンから読める**（`supabase-token-verifier.ts` は
現在 `sub` / `exp` / `iat` / `email` しか見ていない）。

| 段  | やること                                                                                              |
| --- | ----------------------------------------------------------------------------------------------------- |
| 1   | `aal` を読んで `Actor` に載せ、管理画面に「二要素：有効／未設定」を出す。**この段では何も拒否しない** |
| 2   | オーナーが Supabase で TOTP を登録する                                                                |
| 3   | `OWNER_ONLY_ACTIONS` に `aal2` を必須にする                                                           |
| 4   | `productionReady` の条件に「オーナーが `aal2`」を入れる                                               |

⚠️ **段 1〜2 を飛ばして段 3 を入れないこと。** 誰も TOTP を登録していない状態で
必須にすると、**オーナーが自分の管理画面から締め出される**。人事権を持つのは
オーナーだけなので、締め出されると DB を直接触る以外に戻る道がない。

## 4-10. 受取権の発行（P0-1・実装済 2026-08-20）

**決済が済んだ注文を受取権（Entitlement）に変える経路を開いた。**
それまで受取権を作っていたのは試験と staging の Fixture だけで、
**本番の経路が存在しなかった**。Claim も Wallet 配送も返金時の失効も、
作ってあるのに一度も動いていなかった。

⚠️ **発行の待ち行列を別の表にしていない**（指示書 §4 は Outbox を挙げていた）。
「決済が済んでいるのに受取権が足りない注文」は、注文と受取権から必ず導ける。
行を足す方式にすると「行の入れ忘れ」「行だけ残る」という**実物と食い違う
壊れ方**が新しく増える。導出なら、取りこぼしても次の掃き出しで拾い直せる。
Outbox の目的（起動の取りこぼしを無くす）は、より強い形で満たしている。

|          |                                                                                     |
| -------- | ----------------------------------------------------------------------------------- |
| 冪等の鍵 | `UNIQUE(order_line_id, unit_index)`（指示書 §4 の `order_item_id + unit_index`）    |
| 起動     | 決済確定の直後（即時）＋ `/api/v1/internal/jobs/issue-entitlements`（掃き出し）     |
| 再試行   | 1 / 5 / 15 / 60 / 240 分、最大 5 回。超過で人手へ                                   |
| 在庫     | 押さえた枠を発行済みへ**移す**だけ。合計は動かない（決定 A）                        |
| 整合性   | `reconcile()` が受取権の件数と `issuedCount` の食い違いを**数えて返す**（直さない） |

⚠️ **発行の失敗で決済の確定を巻き戻さない。** お金は既に動いている。
巻き戻すと「払ったのに注文が無い」になる。

⚠️ **平文の受取トークンは発行時に持ち回さない。** 保存するのはハッシュだけで、
購入者はご自分の画面から受取URLを発行し直す
（`POST /api/v1/entitlements/:id/claim-token`）。持ち回すと、ログ・監査・通知の
どこかに残る道ができる。

## 4-11. Wallet への自動配送（P0-2・実装済 2026-08-20）

**受取用のウォレットを登録済みの方には、こちらから届ける。** それまでは、
買った方が受取URLを開いて Wallet から受け取りに来るのを待つ形だった。
登録が済んでいるのに待たせるのは、こちらの都合でしかない。

|          |                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------- |
| 起動     | 発行の直後（即時）＋ `/api/v1/internal/jobs/deliver-entitlements`（掃き出し）                     |
| 対象     | `entitlements.status = 'issued'` かつ購入者の `common_user_status = 'RESOLVED'`                   |
| 判定     | `evaluateAutoDelivery`。**中では人が受け取りに来たときと同じ関数**（`evaluateWalletClaim`）を通す |
| 二重防止 | 受取の確定は現在の状態を条件にした UPDATE。競合した側は「すでに受け取り済み」として数える         |

⚠️ **人が受け取りに来る経路を消していない。** 未登録の方はそちらで受け取る。
両方を残すのは重複ではなく、**登録していない方を締め出さない**ため。

⚠️ **「登録完了の合図」を新しく作っていない。** あとから登録した方は、共通顧客IDの
解決ジョブが `RESOLVED` にした時点で掃き出しに拾われる。合図を作ると、
合図の取りこぼしという壊れ方が増える。

⚠️ **「まだ登録していない」を失敗として数えない。** 数えると、登録前の方が
居るだけで監視が赤くなり、本当の異常が埋もれる。応答では `skippedCount` に入る。

⚠️ **届け先を外から受け取らない。** 使うのは受取権に記録された購入者ご本人の
`common_user_id` だけ。引数で渡せる形にすると、そこが**他人の Wallet へ届ける道**になる。

⚠️ **`CONFLICT` の行は拾わない。** 名寄せ途中のアカウントにも値は入っているが、
値があることと本人だと確定していることは別。

⚠️ **画像の公開URLが無い配備では配送を有効にできない。** Wallet へ送る本文は
長期に参照できる `https` の画像URLを要求する。相対パスを返す保管庫のままだと、
本文の組み立てで落ちる。

## 4-12. 買った方のマイページ（P0-3・実装済 2026-08-20）

**ご自分のご注文と、お受け取りの作品を確かめられるようにした。** それまでは、
買ったあとに見られるのは注文 1 件の画面だけで、一覧も、受け取った作品も
見る手立てが無かった。

| 画面                    | 中身                                              |
| ----------------------- | ------------------------------------------------- |
| `/account`              | 入口。**次にしていただくことを 1 つだけ**上に置く |
| `/account/orders`       | ご注文の履歴                                      |
| `/account/orders/[id]`  | 1 件の詳細。お支払い・ご返金・お受け取りの状態    |
| `/account/collectibles` | お受け取りの作品                                  |
| `/account/settings`     | 受取用のウォレットの案内・ログアウト              |

### 内部の言葉を出さない（指示書 §6）

| 公開状態           | 画面の表示               |
| ------------------ | ------------------------ |
| `PENDING`          | 発行の準備をしています   |
| `DELIVERY_PENDING` | ウォレットへお届け中です |
| `DELIVERED`        | お受け取りが完了しました |

⚠️ **`issued` / `claimed` をそのまま出さない。** 運営の言葉で、買った方には
「いま何が起きているか」が伝わらない。

⚠️ **次にしていただくことを 1 つに絞る。** 複数並べると、どれから手を付ければ
よいのか分からなくなる。スマートフォンでは画面の上に置けるのは 1 つだけ。
順序は**お金が動く話を先に**（未払い → 支払い失敗）。

### 決めたこと

- **`/orders/[id]` は消さず、`/account/orders/[id]` へ転送する。** お支払いの
  控えやメールに旧いURLが残っている。ただし**画面の中身は 1 つだけ**置く
  （2 つ置くと、片方だけ直したときに見え方が食い違う）。
- **`orders.refund_status` を買った方にも返す。** ご自分の返金であり、隠すと
  「返金されたはずなのに画面には何も出ない」になる。⚠️ **金額は返さない**——
  一部返金は自動処理しない決まりで、画面に出した額と実際の額が食い違いうる。
- **手数料とクリエイター配分は返さない。** 買った方に関係が無く、事業の
  取り分を外へ晒すことになる。管理側の一覧を流用しない。
- **お受け取りの一覧は作品名を注文時点の値で出す。** 作家さまが改題しても、
  お買い上げの記録は当時の表示のまま。⚠️ **画像だけは現在のもの**——
  スナップショットの列が無い。
- **設定にメールアドレスの変更を置いていない。** 本人確認の範囲が未決
  （`UD-124`）で、確認なしに差し替えられる口を作ると、乗っ取った側が
  連絡先ごと奪える。運営への申請という形にする（P1-1）。
- **マイページへの導線はログイン中だけ出す。** 出しっぱなしにすると、
  ログインしていない方が押してログイン画面へ飛ばされる。

## 4-13. 全額返金にともなう取り消し（M3a・実装済 2026-08-21）

**返金したのに、作品が相手側に残ったままだった。** 受取済みの受取権は
取り消さない決まりだったため、全額返金しても Wallet の Holding が生き続けていた。

|          |                                                                                 |
| -------- | ------------------------------------------------------------------------------- |
| 起点     | 全額返金の成立（管理画面からの返金・決済事業者からの追随）                      |
| 遷移     | `issued → revoked` に加えて **`claimed → revoked`**（`UD-104` 追補）            |
| 送る条件 | **付与イベントの行があるか**ひとつ。状態は問わない                              |
| 版       | `entitlement.revoked` は **`1.1`**（`reason_code` を追加）。付与は `1.0` のまま |
| 冪等     | `event_id` = `evt_rvk_` + 受取権ID。UNIQUE が二重作成を物理的に止める           |
| フラグ   | **3 本**（業務方針／生成／配送）。すべて既定は無効                              |

⚠️ **「受け取った事実」と「いま使える権利」を分けた。** `claimed_at` /
`claimed_by_*` / 配送記録は**残したまま** `status` だけを進める。
記録を消すと、あとから経緯を説明できない。

⚠️ **`revoked` は終端。** 再付与は、この行を戻すのではなく**新しい受取権**を
発行する。戻せるようにすると「いま有効か」を状態列だけで答えられなくなる。

⚠️ **相手が知らない受取権へ取消を送らない。** 付与を一度も作っていない
（＝未受取のまま返金された）分は、送ると「知らないIDの取消」が届き続ける。

⚠️ **UNIQUE 違反で返金を巻き戻さない。** 重複した Webhook 1 通で
**返金の記録ごと消える**のを避けるため、追加は `ON CONFLICT DO NOTHING` に
`payload_hash` の照合を重ねてある。食い違いは例外にせず運用確認へ回す。

⚠️ **一部返金では自動で取り消さない。** どのシリアルを取り消すべきかは
機械に決められない。`operations_reviews` に**未対応として残す**——
ログだけでは、忙しい日にそのまま埋もれる。

⚠️ **補完は生成フラグに従う。** 従わせないと、フラグを戻したのに日次の
時計が作り続ける。取りこぼしは、先に生成フラグを有効にしてから拾う。

## 4-14. 購入者への知らせ（P0-4・実装済 2026-08-21）

**買った方に、何が起きたのかが届いていなかった。** 注文しても、支払っても、
返金しても、こちらの画面を開き直さないと分からない。届かないぶんは
そのまま問い合わせになる。

|        |                                                                      |
| ------ | -------------------------------------------------------------------- |
| 種別   | 9 つ（注文・決済 3 種・受取の案内・受取完了・お届け遅延・返金 2 種） |
| 文面   | DB に版で持つ。**コードへ書かない**。公開した版は書き換えない        |
| 重複   | `UNIQUE(event_type, subject_type, subject_id)` で 1 通だけ           |
| 宛先   | **平文を持たない**（`UD-503`）。送る瞬間に認証基盤から取り、捨てる   |
| 履歴   | 伏せた表記（`t*****@e******.jp`）と鍵付きハッシュだけ                |
| フラグ | **2 本**（作るか／送るか）。どちらも既定は無効                       |

⚠️ **積むのは業務更新と同じトランザクション、送るのはコミットのあと。**
先に送ると、業務側が巻き戻ったときに「起きていないこと」を知らせる。
あとから積むと、そのあいだに落ちた注文が誰にも知らされずに残る。

⚠️ **知らせが積めないことで業務を止めない。** 決済が通っているのに注文が
立たないほうが、はるかに困る。積めなかったことは記録に残して先へ進める。

⚠️ **素の `INSERT` を書かない。** 重複した Webhook 1 通の UNIQUE 違反が、
**業務側のトランザクションごと巻き戻す**。`ON CONFLICT DO NOTHING` で受ける。

⚠️ **お届けの結果はキューから積まない。** 「届いた」「止まっている」は
どちらも配送ワーカーの側で起きるが、そこへ口を生やすと、ワーカーが落ちて
いた時間ぶんが永久に抜ける。**いまの状態から導ける**ことは状態から導く
（受取権の発行（P0-1）と同じ考え方）。

⚠️ **語彙に無い語は文面へ書けない。** 氏名・メールアドレス・住所を
差し込み語彙に入れていないので、書きようがない（`UD-503`）。

## 4-15. 運営ダッシュボード（P0-6・実装済 2026-08-21）

**運営が、何かが起きていることに気づく手立てが無かった。** 発行が止まって
いても、知らせが送れていなくても、誰かが問い合わせてくるまで分からない。
問い合わせが来た時点で、それはもう遅い。

|            |                                                                          |
| ---------- | ------------------------------------------------------------------------ |
| 画面       | 4 つ（運営の状況／受取権／知らせの履歴／記録の食い違い）                 |
| 指標       | 16（本日の動き 4・待ちと打ち切り 6・外部連携 1・決済の知らせ 1・時計 5） |
| 赤の条件   | **4 つだけ**（発行の打ち切り・人の確認待ち・知らせの打ち切り・時計停止） |
| 手当て     | 発行のやり直し／その方ぶんの再配送。**どちらも何度押しても増えない**     |
| 食い違い   | 5 種を数える。**直さない**                                               |
| 時計の生死 | `job_runs`（種別ごとに 1 行）。cron が通るたびに上書き                   |

⚠️ **赤は「いま手を動かす」ものだけ。** 待ちが溜まっているのは仕組みが
動いている証拠で、次の巡回で減る。件数が多いだけで赤くすると、運営は毎朝
赤を見ることになり、そのうち見なくなる。**赤が意味を持つのは、赤でない
ときがある場合だけ**である。

⚠️ **赤い行には必ず次の一手を添える。** 「異常です」だけを出しても、
受け取った人は何をすればよいか分からない。分からないまま放置されるくらい
なら、出さないほうがまだ害が少ない。

⚠️ **静かなことを赤で断言しない。** ご注文が無ければ決済の知らせも来ない。
売れていない日と Webhook が壊れている日を、こちらからは区別できない。
区別できないことを、赤で言い切らない。

⚠️ **失敗しても `last_succeeded_at` を消さない。** 消すと「最後にいつ
成功したか」——見たい値そのもの——が失われる。失敗は別の列に残す。

⚠️ **記録の無い時計仕掛けも項目として返す。** 返さないと画面から項目ごと
消え、「動いていない」ではなく「そんな処理は無い」に見える。

⚠️ **食い違いは数えるだけで直さない。** 見つけた機械が黙って直すと、なぜ
食い違ったのかが分からないまま同じことが繰り返される。0 件のものも返す。
**調べて 0 件だった**ことを示すのが、この画面の値打ちである。

⚠️ **見るのと動かすのを分ける。** 指標と一覧は監査担当にも開くが、やり直し
（発行・再配送）は運営だけ。どちらも外部へ実際に送る操作である。

⚠️ **禁じた操作の口を作らない**（P0/P1 §9.3）。金額の直接書換え・`paid` への
手動変更・在庫と無関係な予約・記録を残さない状態変更・注文や決済の物理削除は、
この画面にも API にも存在しない。試験がその不在を確かめている。

⚠️ **応答に個人を特定できる値を混ぜない**（`UD-503`）。氏名・メールの項目が
契約（zod）そのものに無いので、載せようとすると型で落ちる。

### 作品審査待ちの指標を作らなかった理由

指示書は「作品審査待ち」を指標に挙げているが、**この仕組みには審査という
状態が無い**。作品の状態は `draft` / `published` / `archived` の 3 つで、
出品者が自分で公開する（`UD-102` で審査を戻さないと決めている）。

無い状態を数えると、常に 0 が並ぶ。**0 が並ぶ指標は「異常が無い」と読まれる**
ので、あとから審査を入れたときに、誰も気づかないまま 0 のままになりうる。
数えられないことは、数えているふりをせずに書き残す。

## 4-16. 本番販売ガード（P0-7・実装済 2026-08-21）

**売れる状態と、売ってよい状態は別である。** 支払い口を作る仕組みは動いて
いても、規約が掲げられていない・鍵の接続が確かめられていない・誰も責任を
引き受けていない、という状態で売ると、返せない・届けられない・説明できない
ことが起きる。起きてから直すのでは間に合わない。

|            |                                                                            |
| ---------- | -------------------------------------------------------------------------- |
| 条件       | 10（機械が確かめるもの 8・人が署名するもの 2）                             |
| 止める場所 | **支払い口を作る側**（`CheckoutService`）。画面ではない                    |
| 止める環境 | **`production` のみ**。staging は判定するが通す                            |
| 証跡       | `production_attestations`（**追記のみ**。DB のトリガーが更新と削除を拒む） |
| 失効       | **受付中の決済世代が替わったら、証跡は自動で失効する**                     |

### 10 条件と読み元

| 条件                       | どこから読むか                                           |
| -------------------------- | -------------------------------------------------------- |
| 決済の鍵が有効             | `payment_credentials` の受付中世代＋接続確認（`UD-118`） |
| Webhook の署名             | **その世代で実際に知らせを受け取ったことがあるか**       |
| 手数料率が承認済み         | `integration_settings.platform_fee_rate_bps > 0`         |
| 規約・プライバシー・特商法 | `legal_document_versions` の**施行日を迎えた**版         |
| OVEW Wallet の接続確認     | `integration_connection_checks`（直近 1 件・30 日以内）  |
| メール送信の接続確認       | 同上。**試し送り**（`test_send`）で確かめる              |
| 発行・お届けの時計         | `job_runs`（P0-6 の心拍をそのまま使う）                  |
| 運営責任者の二要素         | `accounts.last_aal2_at`（`UD-801` の段階導入 段 1）      |
| 直近の通し試験             | `production_attestations`（`e2e_sale_test`）             |
| 運営責任者の承認           | `production_attestations`（`owner_approval`）            |

⚠️ **分からないことは「満たしていない」へ倒す。** 記録が無いことを
「たぶん大丈夫」と読むと、この仕組みは何も守らない。**証拠が無い＝未達**。

⚠️ **判定を毎回やり直す。** 「一度そろったから以後は通す」という記憶を
持たない。条件は崩れるもので、**崩れたことに気づかないまま売り続ける**のが
いちばん困る。

⚠️ **「署名鍵が入っている」では足りない。** 入れ間違えても、受け取るまで
誰も気づかない。**実際に届いたこと**を条件にしている。

⚠️ **「公開した」ではなく「施行日を迎えた」。** 予約公開があるので両者は
一致しない。未来の施行日を数えると、まだ掲げていないものを掲げたことにする。

⚠️ **一度通った接続確認を永久の証拠にしない。** 相手側の証明書も鍵も
入れ替わる。切れていることに、売れなくなってから気づく。

⚠️ **staging では止めない。** 止めると誰も試せず、本番で初めて動かすことに
なる。**判定そのものはどちらの環境でも同じ**で、違うのは止めるかどうかだけ。
その違いは画面にも応答（`enforced`）にも出す。

⚠️ **購入者へ理由の内訳を出さない。** どの条件が欠けているかは運営の内部
事情であって、買おうとした方に伝えることではない。断る言葉は「準備中」で
揃える。運営は管理画面で内訳を見られる。

### 人が署名する 2 つについて

10 条件のうち 8 つは機械が確かめられる。残る 2 つ——**通し試験が通ったこと**と
**責任者が承認したこと**——は、機械には確かめようがない。

⚠️ **これは「試験が通った証明」ではない。** 押した人が「通した」と言って
いる記録にすぎない。だからこそ**誰がいつ押したかを残し、書き換えられない**
ようにする。書き換えられるなら、記録である意味が無い。

- **追記のみ。** アプリに更新・削除の口が無く、DB のトリガーも拒む。
  二重にしているのは、**アプリを通さない書き込み**も止めるため
- **訂正は新しい記録を足して表す。** 失敗した記録も残るので、
  「何度やり直したか」が読める
- **決済世代に紐づく。** 鍵が替わるのは、運営会社や入金先が変わるという
  こと。前の鍵で通した試験は、新しい鍵の証拠にならない
- **順序を強制しない。** 10 条件が満たされる前でも承認は記録できる。
  強制すると、鍵の切り替え日に合わせて段取りする運用ができなくなる。
  押した記録は残り、条件の判定は毎回やり直されるので、**早く押しても
  近道にならない**
- **記録できるのはオーナーだけ**（`OWNER_ONLY_ACTIONS`）。運営の 1 人が
  乗っ取られただけで本番販売が始められる状態にしない

### 二要素認証（`UD-801` の段階導入・段 1 と段 4）

ロードマップ §4-9 の段取りのうち、**段 1（`aal` を読んで記録する）と
段 4（`productionReady` の条件にする）を実装した**。段 3（`OWNER_ONLY_ACTIONS`
に `aal2` を必須にする）は**入れていない**。

⚠️ **段 3 が危ないのは、誰も TOTP を登録していない状態で必須にすると
オーナーが自分の管理画面から締め出されるため。** 段 4 は締め出さない——
条件が未達なら「本番販売を始められない」だけで、管理画面は開ける。
だから段 3 を飛ばして段 4 を先に入れてよい。

⚠️ **「入ったことがある」であって、いまの設定ではない。** 二要素を外した
ことは、こちらからは分からない。だから判定の側で**期限を切る**（既定 90 日）。

### メール送信の接続確認

到達性の確認（`reachability`）では足りない。api.resend.com へ届くことは、
鍵が正しいことも差出人が確認済みであることも意味しない。**試し送り**
（`test_send`）で確かめる。

⚠️ **宛先は、押した本人の業務用アドレスに限る。** 宛先を受け取る形にすると、
この口が「任意の相手へメールを送れる口」になる。誰の手元にも届かないから、
試し送りが安全でいられる。

⚠️ **この試し送りを OVEW Wallet へ広げない。** あちらの受け口は受取権を
作る口で、試し打ちしてよい相手ではない（要決定 06 は未解決のまま）。

⚠️ **鍵を DB へ移していない。** `mail` を連携の語彙に足したのは、
**確かめた記録の置き場**が要るからであって、管理画面から鍵を触れるように
するためではない（`storesSecrets` / `isManagedFromAdmin` はどちらも偽）。

## 4-16-2. 顧客サポート（P1-1・実装済 2026-08-21）

**問い合わせは「注文番号を控えていない人」から来る。** どの注文の話か、
受け取れているのか、返金は済んでいるのか——それらが 1 画面に揃っていないと、
応対する人が画面を 5 つ開いて突き合わせることになる。突き合わせは間違う。

|        |                                                                         |
| ------ | ----------------------------------------------------------------------- |
| 画面   | 2 つ（お探しする／お客さま 1 人の状況）                                 |
| 探し方 | 注文番号・ご連絡先・共通顧客ID・アカウントID。**条件無しの一覧は無い**  |
| 集約   | 注文・受取権・返金・申し送り・重複候補・ご連絡先の変更申請              |
| 救済   | **既存の口へ繋ぐ**（Claim 再発行 `UD-1009`／ウォレット再配送 P0-6）     |
| 新設   | `account_notes`（追記のみ）／`email_change_requests`（本人確認つき）    |
| 権限   | `customer.view` / `customer.note` / `customer.email_change`（運営のみ） |

⚠️ **氏名とメールアドレスの平文を、この画面は持たない**（`UD-503`）。API の
契約に項目そのものが無いので、載せようとすると型で落ちる。ご本人の確認は、
ご注文の内容や登録済みのご連絡先への確認で行う。

⚠️ **持ち主を付け替える口を作っていない**（指示書 §11）。注文・受取権・
ウォレットの持ち主を人が変えられる経路は、ドメインにも API にも画面にも
存在しない。**本人確認をしていない付け替えは、他人の持ち物を渡すことと
同じ**である。試験がその不在を **404** で確かめている。

⚠️ **重複は「候補の表示」まで。** 統合の口は作らない。文言も
「同一人物」と書かない——読み違えたまま判断されると、取り返しがつかない。
候補の手がかりは 2 つだけ（照合用のメール値の一致・共通顧客IDの一致）で、
どちらも「同じ人である」ことは意味しない。

⚠️ **ご連絡先はこの画面では変わらない。** 認証の正は認証基盤側にあり、
こちらが持つのは照合用の値だけ。この仕組みが受け持つのは 3 つの記録だけ
——「申し出があった」「**誰が**本人確認をした」「向こうで変えた」。

⚠️ **本人確認を飛ばして「済」にできない。** ドメインが断り、DB の CHECK も
断る。二重にしてあるのは、アプリを通さない書き込みも止めるため。
**飛ばされたことは、乗っ取られるまで誰にも分からない。**

⚠️ **監査担当には渡していない。** 監査は「運営が何をしたか」を見る仕事で、
「その方が何を買ったか」を 1 画面で見る必要は無い。**まとめて見えること
そのものが力**なので、必要のない人には渡さない。

⚠️ **検索したことは記録に残すが、引いた値は残さない。** 記録に平文が残れば、
`UD-503` を監査ログの側から破ることになる。残すのは「どの種類の手がかりで
引いたか」と件数まで。

### 代理店・紹介元のスナップショットを作らなかった理由

指示書は顧客詳細の項目に挙げているが、**注文に紹介元を残す列がまだ無い**。
代理店システムとの連携（M0〜M4）が契約待ちで、スナップショットに何を
残すかも相手の契約で決まる（`Q4`：**Market では報酬率も報酬額も計算しない**）。

いま形を決めて作ると、契約が届いたときに作り直すことになり、そのあいだに
入った注文だけ形が違う、という残り方をする。**API は項目を `null` で返し、
画面には「まだこの仕組みにありません」と出す。** 埋まっているふりをしない。

## 4-17. 作家さま運営（P1-2・実装済 2026-08-21・作品審査を除く）

**作家さまが知りたいのは 3 つだけ。** 売れたか、いくら入るか、いつ入るか。
それが見えないと、運営へ「今月どうなっていますか」と尋ねることになり、
運営はそのたびに DB を引くことになる。

|          |                                                                       |
| -------- | --------------------------------------------------------------------- |
| 画面     | 2 つ（売上とお振込 `/creator/earnings`／お店の情報 `/creator/shop`）  |
| 売上     | 今月ぶんの見込み・作品ごとの売れ行き・明細・締めた月の履歴            |
| 持ち出し | CSV（BOM つき・**買った方の情報を 1 つも含まない**）                  |
| お店     | ショップ名・ご紹介・SNS（5 件まで）・インボイス登録番号・ご準備の状況 |
| 新設     | `creator_profiles`／販売規約 `creator_terms`（法務文書の 4 つ目）     |
| 権限     | `creator.earnings.view_own`（会員と運営）／`profile.manage_own`       |

⚠️ **見込みと締めた実額を、別の式で出さない。** 見込みは
`PayoutService.estimateFor` を通し、締めるときと**同じ `buildFor`** を呼ぶ。
見込み用に手早く書いた合計を置くと、翌月に締めたときだけ数字が動き、
**「話が違う」**になる。試験は月をまたいで（6 月に見た見込み → 7 月に締めた
実額）一致することを確かめている。

⚠️ **「誰の分か」を受け取る口が、どこにも無い。** URL にも本文にも
問い合わせにも無く、アカウントはトークンから取る。**売上はその方の商いの
中身そのもの**で、指定できる形にした時点でそこが覗き口になる。試験は、
別のアカウントを問い合わせに付けても自分の分が返ることと、他人の分を見る
経路が **404** であることを確かめている。

⚠️ **運営向けの「作家さまの売上を見る」口をここへ足さない。** 必要なら
`/api/v1/admin/payouts`（`payout.view`）を使う。同じ経路に混ぜると、
「自分の分だけ」という縛りが緩む。

⚠️ **売上の門を、名乗りの門と分けてある。** 名前を決めるのは
`profile.manage_own`、売上を見るのは `creator.earnings.view_own`。
後者は**会員にも渡す**——この場では会員なら誰でも出品できる（`UD-806`）ので、
締め出すと**作家さま本人が自分の売上を見られなくなる**。売っていない方には
空が返るだけで、他人の分は指定しようが無い。閲覧者（`auditor`）には渡さない。

⚠️ **CSV は数式として解釈されうる値を、消さずに前へ逃がす。** `=` `+` `-`
`@` で始まる作品名は `'` を付けて無害化する。消してしまうと**作品名が
変わってしまう**。BOM を付けるのは、無いと Excel が UTF-8 と判断せず、
開いた作家さまには**こちらの不具合に見える**ため。

⚠️ **ご返金があった分を、売れた数から黙って引かない。** 別の欄に出す。
引いてしまうと「売れたはずの数」と合わず、作家さまの手元の記録と食い違う。

⚠️ **0 円のお振込予定を出さない。** 最低支払額に満たない分は繰り越される。
「ありません」で終わらせず、**繰り越されること**まで書く。書かないと
「消えた」と読まれる。

⚠️ **お振込先は「未登録」で終わらせない。** 登録の仕組みは P1-3 で、
いまは無い。「未登録」とだけ出すと、登録する場所を探させてしまう。
**「まだご登録いただけません（準備中）」**と、こちらから言う。

⚠️ **販売規約は、買う方の利用規約と束ねない。** `creator_terms` は同意を
求める文書として登録したが、ログイン時の判定は `'terms'` だけを見る。
束ねると、**買っただけの方が販売規約に同意したことになる**。DB の
`legal_consents_kind_valid` も、同意の語彙を 2 つに限っている（文書の語彙は
4 つだが、そこへ揃えると「取っていない同意を取ったことにできる」穴が開く）。

### 作品審査は入れない（決定 2026-08-21・`UD-102` 維持）

指示書 §12 は `draft → submitted → under_review → approved/rejected →
published` という審査の流れを求めているが、**入れない。** `UD-102`
（決定変更 2026-08-18）の「作家の自己出品を行う。出品前の審査は行わない」を
維持する。作品の状態は `draft` / `published` / `archived` の 3 つのままとする。

✅ **決定 2026-08-21:** 作品審査は入れない。**将来的に入れる可能性は残す。**

⚠️ **`UD-102` の行は書き換えない。** 覆さなかったことも記録として要る。

試験は、審査の口がいまは存在しないこと（**404**）を確かめている。

#### 将来入れることになったときに、先に決めるべきこと

「あとで足せばよい」で済まない部分があるので、書き残しておく。

| 決めること                       | 決めないと起きること                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| **既存の `published` の扱い**    | すべて `approved` とみなすか、`under_review` へ戻すか。戻せば**公開中の作品が店先から消える** |
| 審査の待ち行列を誰が見るか       | 権限を決めないと、審査は「誰の仕事でもない」まま滞る                                          |
| 審査待ちのあいだ作家さまに出す顔 | 「審査中」と出すなら、**何日で見るか**も同時に決める。決めないと問い合わせが増えるだけ        |
| 差し戻しの理由の残し方           | 理由の無い差し戻しは、直しようが無く、同じものが再提出される                                  |
| 出品中の作品を審査へ戻せるか     | 戻せるなら、売れている最中に止まる。戻せないなら、後から問題が見つかったときの手が `archive`  |

⚠️ **いま状態だけ先に足しておく、をしない。** 使われない状態が
`ARTWORK_STATUSES` に並ぶと、**その状態を前提にした分岐が少しずつ増える**。
入れると決まってから、上の表を埋めたうえで足す。

## 4-18. ご連絡先を見る（決定 2026-08-21・実装済）

**運営が問い合わせに答えるには、ご連絡先が要る。** 一方で、`UD-503` は
「購入者のメールアドレスを平文で保持しない」と決めている。この 2 つは
両立する——**保持しないことと、見られないことは別**である。

|      |                                                                            |
| ---- | -------------------------------------------------------------------------- |
| 保存 | **しない**（`UD-503` 維持）。DB にもログにも入らない                       |
| 取得 | 押されたときだけ認証基盤（Supabase）から取り寄せ、応答に載せて捨てる       |
| 権限 | `customer.view_email`（運営のみ）。`auditor` にも `buyer` にも渡さない     |
| 記録 | 監査ログへ「誰が・いつ・どのアカウントの分を・取れたか」。**値は残さない** |
| 画面 | `/admin/customers/:id` の「ご連絡先を表示する」。**開いただけでは出ない**  |

⚠️ **`UD-503` を反転しなかった。** 反転して平文を保存すると、こちらの
バックアップにも個人情報が載り、漏れたときの被害範囲が広がる。しかも
**過去のご注文は見られない**——いま保存していないので、これから入る分だけに
なる。認証基盤から取り寄せる形なら、**過去の方の分も見られる**（アドレスは
元々あちらにある）。持たないほうが、できることが多かった。

⚠️ **顧客詳細（`GET :accountId`）に混ぜていない。** 混ぜると、画面を開いた
だけで全員のアドレスが流れ、監査ログが「開いた人」で埋まって
**本当に読んだ人が埋もれる**。読むと決めたときだけ、別の口を叩く。
試験は、詳細を開いても認証基盤へ問い合わせが飛ばないことを確かめている。

⚠️ **`auditor` には渡していない。** 監査は**読んだことを確かめる側**で
あって、読む側ではない。読む側と確かめる側が同じ人だと、歯止めにならない。

⚠️ **監査ログにアドレスの値を入れない。** 入れれば、監査ログの側から
`UD-503` を破ることになる。試験がこの 1 点を釘付けにしている——実際に
`summary` へアドレスを載せると、その試験だけが落ちることを確かめてある。

⚠️ **知らせの送信が有効かどうかとは切り離した。** `NOTIFICATION_DELIVERY_ENABLED`
にぶら下げると、**送信を止めた日から応対ができなくなる**。取り寄せる口は
Supabase の設定さえあれば作る。

⚠️ **居ないアカウントは 404 で断る。** 引けると、この口が「そのアカウントが
在るか」を確かめる道になる。

⚠️ **「分からない」と「取れなかった」を分ける。** 前者はその方が認証基盤に
居ないということで、待っても変わらない。後者は届かなかったということで、
時間をおけば直りうる。同じ顔で出すと、応対する人がもう一度試すべきかを
判断できない。**設定されていない**（`not_configured`）も、この 2 つと分ける
——混ぜると、設定漏れが「たまたま失敗した」に見えて放置される。

### 残っている限り

**ゲスト購入（`UD-504` 未決定）には効かない。** アカウントが無ければ認証基盤にも
居ないので、取り寄せようがない。ゲスト購入を入れるなら、そのときに
ご連絡先の扱いを別に決める必要がある。

## 4-19. 改定を既存の会員へ知らせる（`UD-127`・実装済 2026-08-21）

**再同意の印は、次にログインするまで効かない。** ログインしない方には、
**約束の中身が変わることが一度も伝わらないまま**変わったことになっていた。

|        |                                                                         |
| ------ | ----------------------------------------------------------------------- |
| 対象   | **再同意が要る改定だけ**。誤字直しでは送らない                          |
| 宛先   | その文書の、**その版より前に同意した方**                                |
| 送る先 | 本文ではなく**読みに行く先**（`legalUrl`）と**施行日**                  |
| 経路   | 公開の直後にベストエフォート＋日次の掃き寄せ（`enqueue-legal-notices`） |
| 文面   | `/admin/notifications` で運営が書く。既定の文面はマイグレーションで投入 |

⚠️ **送らない判断も、送る判断と同じくらい大事。** 誤字を直しただけで全員へ
送ると、**次に本当に大事な改定を送ったときに読まれなくなる**。再同意が要るか
どうかは公開する人が決める（`UD-126` の設計をそのまま使う）。

⚠️ **一度も同意していない方へは送らない。** 再同意のしようが無く、会員でない
方へ届く形にもしない。

⚠️ **停止中のアカウントは外していない。** ログインできないので再同意はできない
が、これは**その方が当事者である約束についての連絡**である。こちらの都合で
止めている相手に、黙って中身を変えたことにしない。

⚠️ **本文をメールへ写さない。** 規約は長く、写すと版が 2 か所に増える。あとで
「メールに書いてあった内容」と「公開されている内容」が食い違ったとき、
**どちらが約束なのか誰にも言えなくなる**。

⚠️ **公開は取り消せないので、積めなくても公開を巻き戻さない。** 例外にすると、
公開した人には「失敗した」と見えるのに文書は公開済み、という最も混乱する形に
なる。落ちたときは印が立たず、掃き寄せが拾い直す（発行 P3 と同じ形）。

⚠️ **積めなかった宛先が 1 人でもあれば、印を立てない。** 文面が公開されて
いないなどの理由で積めなかったときに印を立ててしまうと、**その改定の知らせは
永久に届かない**。

### 重複送信の鍵へ宛先を足した

これまでの鍵は（種別・対象種別・対象ID）だった。注文・受取権・返金はどれも
宛先が 1 人なので、それで足りていた。**改定の知らせは 1 つの版を大勢へ送る**
ので、この鍵のままだと **1 人目しか積まれない**。

⚠️ **緩めているように見えるが、意味は変わらない。** 止めたいのは「同じ知らせが
同じ人へ 2 通届くこと」であって、「1 つの対象について 2 人へ届くこと」では
ない。鍵が言いたかったことを、そのまま書き直した。既存の種別で行が増えることは
ない（宛先が 1 人なので同じ組み合わせにしかならない）。

### 残っている限り

**改定を「読んだ」ことは分からない。** 届いたかどうか（送信の成否）までは
記録に残るが、開いたか・読んだかは追わない。開封の追跡は入れていない。
