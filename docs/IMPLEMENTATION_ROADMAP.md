> ⚠️ **Phase 5 は凍結（2026-08-14 の方針変更）。**
> MVP では Blockchain Mint を行わない。購入時にも Claim 時にも Mint しない。
> 当面は「**ブロックチェーン未発行**」のデジタルコレクションとして運用する。

### MVP の完成条件（2026-08-14 確定）

```text
作品登録 → 出品 → 購入 → 決済 → Entitlement 発行 → Claim
  → OVEW Wallet へ entitlement.granted → CollectibleHolding 作成
  → Wallet Collection へ表示
```

**ここまでが MVP。Mint 成功は受入条件に含めない。**

⚠️ **「後回し」であって「やめた」ではない。**
将来、利用者が「NFT として発行する」を選んだとき・外部 Wallet へ送るとき・
二次流通へ出すとき・オンチェーンの所有証明が要るときに、
**オンデマンドで** Mint する。そのための未決定事項は消さずに残してある。

⚠️ **いま Mint を見越した作り込みをしない。**
チェーンが決まっていない状態で「あとで差し替えられるように」と器だけ作ると、
決まったときにその器が合わず、二重に作り直すことになる。
必要になってから、決まった仕様に合わせて作る。

## 3. Phase 2 以降の概要

### Phase 2 — カタログ（完了）

実装したもの:

- 初期マイグレーション（18 個の CHECK 制約を手書きで追加）
- `artworks` / `listings` のリポジトリ実装（キーセットページング）
- ドメイン層の作品・出品ユースケース（状態遷移・公開条件・購入可否判定）
- 管理API（作品の登録・更新・公開・非公開、出品の作成・更新・開始・停止・終了）
- 公開カタログAPI（一覧・詳細）と画面
- 認可ガード（既定 deny・ロール判定）と開発用トークン検証
- 実 PostgreSQL に対する制約の結合テスト（M-1/M-2/S-4）

**実装しなかったもの:**

- **管理画面（UI）** — 運営がログインする経路が Phase 4（認証連携）なので、
  いま画面だけ作ると擬似ログインを画面側に置くことになる。
  それを本番へ持ち込む事故を避けるため、**Phase 4 へ送る**。
  管理APIは実装済みで、テストからも手元からも操作できる。
- **ロール変更API** — 権限昇格の経路は最も攻撃価値が高い（`UD-803`）。
  経路そのものを作らず、DB 直操作＋監査で運用する。

### Phase 3 — 決済と注文（**MVP の次工程**）

⚠️ **`UD-702`（決済事業者）が未決定でも着手する。**
ポートと Fake / テスト用アダプタで注文フローを先に完成させる。
決済事業者が決まってから実アダプタを足す。

⚠️ **決済事業者を前提にしたドメイン設計にしない。**
事業者固有のIDを主キーにしない。同期の決済結果だけで業務の成功を確定しない
（確定は Webhook で行う）。ここを崩すと、事業者を変えるときに
ドメインごと作り直しになる。

- 注文作成（在庫仮引当・行ロック）
- 決済セッション作成（**テスト環境のみ**）
- Webhook 受信（署名検証・冪等・受取権発行）
- 期限切れ注文の回収ワーカー
- 必須テスト I-1/I-2、S-1〜S-5、W-1〜W-8、A-4/A-5

**前提となる決定:** `UD-702`（決済事業者）、`UD-401`（通貨・税）

### Phase 4 — 認証と Claim

- Supabase Auth 連携（JWT 検証、JIT プロビジョニング）
- **`common_user_id` の解決と保持**（正本は代理店システム。本システムでは発行しない）
- Claim 確認（GET）と実行（POST）
- **Claim の本人照合**（購入者の `common_user_id` と一致すること）
- コレクション表示
- 必須テスト I-3/I-4、M-3、Z-1〜Z-8

**前提となる決定:** `UD-801`（JWT 検証方式）、`UD-505`（Claim 期限）、`UD-504`（ゲスト購入）、
`UD-1005`（Claim API の認証）、`UD-1006`（`common_user_id` の補完条件）

> ⚠️ **外部の解決失敗で購入を止めない。**
> `common_user_id` の解決は非同期にし、未解決でも受取権は発行する。

### Phase 4.5 — OVEW Wallet 連携

Phase 4 の完了後、Phase 5 の前に行う。
**ブロックチェーンの決定を待たずに進められる**のが、この Phase を切り出す理由。

- Wallet Integration Adapter（内部イベント → 外部イベントの変換）
- 千ノ国共通 HMAC（`X-SenNoKuni-*`）。汎用の `X-Sengoku-*` は残す
- Wallet Outbox Dispatcher（`entitlement.granted` / `entitlement.revoked`）
- 配送状態の記録、再試行、DLQ と手動再送
- staging での結合試験

**前提となる決定:** `UD-508`（画像の長期参照方式）、`UD-1007`（Claim 状態の対応）

> ⚠️ **`UD-508` は Phase 4.5 のブロッカー。**
> Wallet へ渡せるのは Wallet 側から取得できる HTTPS URL であり、
> 現在のローカル保存では発行できない。短期署名 URL を長期表示用に
> スナップショットへ保存することもできない（期限切れで表示が壊れる）。

詳細は [EXTERNAL_INTEGRATION_POLICY.md](./EXTERNAL_INTEGRATION_POLICY.md) §5.2。

### Phase 5 — Mint

- worker のジョブループ（`SKIP LOCKED` 排他取得、バックオフ）
- 実 `MintingPort` アダプタ
- メタデータ生成と保存
- 必須テスト I-5/I-6、M-4

**前提となる決定:** `UD-501` `UD-502` `UD-506`〜`UD-512` `UD-902`
→ いずれも**未決定のまま保持**。MVP のブロッカーからは外した。

> ⚠️ **2026-08-14 の方針変更で凍結。** MVP では Mint を行わない。
> 将来のオンデマンド Mint の流れは次のとおり。
>
> ```text
> Holding ACTIVE → 利用者が発行を要求 → Mint Job → Blockchain
>   → token_id / tx_hash / contract_address / network → Wallet Holding ONCHAIN
> ```

### Phase 6 — 運用

- 管理画面（注文・受取権・ジョブの一覧と手動再試行）
- 返金処理
- Outbox 配信ワーカーと外部連携
- 整合性チェックの日次実行、監視・アラート

**前提となる決定:** `UD-104`（返金ポリシー）、`UD-1102`（監視基盤）

✅ **`UD-801` は選好ではなく事実で決まった。** Supabase プロジェクトの
署名鍵が既に ECC(P-256) へ交代しており、HS256 を採ると
新しいトークンを検証できない。**本番 api が起動しない最後の障害が解けた。**
`UD-102` を覆して作家の自己出品を行うことにしたため。
⚠️ **`UD-102` の行は書き換えず、状態欄に「決定変更」と日付を残す。**
覆したこと自体が記録として要る。消すと、なぜ方針が変わったのかが
後から誰にも分からなくなる。

✅ **`UD-803` は「入口を 1 本に絞る」ことで決めた。** スタッフになる道は
招待だけで、会員の一覧から誰でも昇格させる形にしていない。そうすると
(1) 誰が誰かを見分けるために全会員の連絡先を運営へ見せることになり、
(2) 押し間違いで無関係の会員が運営になる。
人事を触れるのは**オーナーだけ**とし、役割（3 つ）は増やしていない。
「何ができるか」と「人に権限を配れるか」を別の軸にしたのは、
運営に操作をひとつ足すたびに人事権まで一緒に配ってしまうのを防ぐため。

⚠️ **最初のオーナーの任命だけはアプリ内に経路を作っていない。**
自分を昇格させる経路を作らないための線引きで、DB 側で行う
（`docs/DEPLOYMENT_RUNBOOK.md` §3-6）。

⚠️ **`UD-503` を全面的に覆したわけではない。** 平文で持つのは
オーナーが自分で入力した**スタッフの業務用アドレス**だけで、
購入者のアドレスは今までどおり持たない。DB の CHECK
（`accounts_staff_email_only_for_staff`）が、そこを物理的に縛っている。

🟡 **`UD-113` は狭いほうへ倒してある。** 「消す」は取り消せない操作なので、
決まっていない範囲を運営の裁量に委ねると、決める前に取り返しがつかなくなる。
発行済みのある作品を消せるようにするかは、購入者への説明責任と保存義務の
話になるため、事業と法務の判断が要る。それまでは公開停止（`archived`）で
表示だけを止める。

✅ **`UD-702`（決済事業者）を 2026-08-19 に確定。** Stripe Checkout。
API バージョンは `2026-07-29.dahlia`（SDK が固定している版）に**固定する**。
固定しないとアカウントの既定版が使われ、Stripe 側の更新でイベントの形が
変わったときに、こちらの知らないうちに壊れる。

⚠️ **本番の決済はまだ有効にしていない。** テストモードのみ。
本番鍵の設定は、`UD-111`（特商法表記）の法務確認が済んでから。

✅ **`UD-109` と `UD-114` を 2026-08-19 に確定。**
プラットフォーム手数料 20%、決済会社の手数料は千ノ国運営が負担、
クリエイター配分は購入金額の 80%。対象はデジタルアート販売 MVP で、
グッズは将来、別の体系を設定する。

⚠️ **`PLATFORM_FEE_RATE_BPS` の 0 は「手数料無料」ではなく
「販売設定未完了」として扱う。** 0 のままでは Checkout を作らせない。
「無料で売れてしまう」より「売れない」ほうが取り返しがつくため。
購入者には内部の設定値を見せず、「購入準備中」とだけ伝える。

🟠 **`UD-114` は `UD-109` と分けてある。** 「プラットフォームが何割取るか」と
「決済会社の手数料を誰がかぶるか」は別の決定で、後者は出品者への配分額の
**計算式そのもの**を変える。決済会社の手数料を出品者負担にするなら、
配分額は `合計 − 手数料 − 決済会社手数料` になり、確定するのは
決済が通ったあと（金額が分かるのは Webhook）になる。
⚠️ **決めないまま実装しない。** 先に片方の式で作ると、あとで
「もう配ってしまった注文」の再計算が要る。決済 Phase P0・P1 では
手数料率を 0% で記録し、配分額は `合計 − 手数料` の引き算だけにしてある。

⚠️ **`UD-109`（手数料率）・`UD-110`（送金）・`UD-111`（特商法表記）が
未決定のあいだは、出品はできても販売を開始してはならない。**
代金を受け取る仕組みと、作家へ渡す仕組みと、法定の表示が揃っていない。
Claim Token の平文を保持しない設計のため、紛失時に**再表示できない**。
これは正しい設計だが、復旧手段が無いままでは運用できない。
OVEW Wallet 連携の指示書を精査した結果、実装前に決めないと
取り返しがつかない箇所が見つかったため。
