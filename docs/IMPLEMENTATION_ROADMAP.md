## 3. Phase 2 以降の概要

### Phase 2 — カタログ（完了）

実装したもの:

- 初期マイグレーション（18 個の CHECK 制約を手書きで追加）
- `artworks` / `listings` のリポジトリ実装（キーセットページング）
- ドメイン層の作品・出品ユースケース（状態遷移・公開条件・購入可否判定）
- 管理API（作品の登録・更新・公開・非公開、出品の作成・更新・開始・停止・終了）
- 公開カタログAPI（一覧・詳細）と画面
- 認可ガード（既定 deny・ロール判定）と開発用トークン検証
- 実 PostgreSQL に対する制約の結合テスト（M-1/M-2/S-4）

**実装しなかったもの:**

- **管理画面（UI）** — 運営がログインする経路が Phase 4（認証連携）なので、
  いま画面だけ作ると擬似ログインを画面側に置くことになる。
  それを本番へ持ち込む事故を避けるため、**Phase 4 へ送る**。
  管理APIは実装済みで、テストからも手元からも操作できる。
- **ロール変更API** — 権限昇格の経路は最も攻撃価値が高い（`UD-803`）。
  経路そのものを作らず、DB 直操作＋監査で運用する。

### Phase 3 — 決済と注文

- 注文作成（在庫仮引当・行ロック）
- 決済セッション作成（**テスト環境のみ**）
- Webhook 受信（署名検証・冪等・受取権発行）
- 期限切れ注文の回収ワーカー
- 必須テスト I-1/I-2、S-1〜S-5、W-1〜W-8、A-4/A-5

**前提となる決定:** `UD-702`（決済事業者）、`UD-401`（通貨・税）

### Phase 4 — 認証と Claim

- Supabase Auth 連携（JWT 検証、JIT プロビジョニング）
- **`common_user_id` の解決と保持**（正本は代理店システム。本システムでは発行しない）
- Claim 確認（GET）と実行（POST）
- **Claim の本人照合**（購入者の `common_user_id` と一致すること）
- コレクション表示
- 必須テスト I-3/I-4、M-3、Z-1〜Z-8

**前提となる決定:** `UD-801`（JWT 検証方式）、`UD-505`（Claim 期限）、`UD-504`（ゲスト購入）、
`UD-1005`（Claim API の認証）、`UD-1006`（`common_user_id` の補完条件）

> ⚠️ **外部の解決失敗で購入を止めない。**
> `common_user_id` の解決は非同期にし、未解決でも受取権は発行する。

### Phase 4.5 — OVEW Wallet 連携

Phase 4 の完了後、Phase 5 の前に行う。
**ブロックチェーンの決定を待たずに進められる**のが、この Phase を切り出す理由。

- Wallet Integration Adapter（内部イベント → 外部イベントの変換）
- 千ノ国共通 HMAC（`X-SenNoKuni-*`）。汎用の `X-Sengoku-*` は残す
- Wallet Outbox Dispatcher（`entitlement.granted` / `entitlement.revoked`）
- 配送状態の記録、再試行、DLQ と手動再送
- staging での結合試験

**前提となる決定:** `UD-508`（画像の長期参照方式）、`UD-1007`（Claim 状態の対応）

> ⚠️ **`UD-508` は Phase 4.5 のブロッカー。**
> Wallet へ渡せるのは Wallet 側から取得できる HTTPS URL であり、
> 現在のローカル保存では発行できない。短期署名 URL を長期表示用に
> スナップショットへ保存することもできない（期限切れで表示が壊れる）。

詳細は [EXTERNAL_INTEGRATION_POLICY.md](./EXTERNAL_INTEGRATION_POLICY.md) §5.2。

### Phase 5 — Mint

- worker のジョブループ（`SKIP LOCKED` 排他取得、バックオフ）
- 実 `MintingPort` アダプタ
- メタデータ生成と保存
- 必須テスト I-5/I-6、M-4

**前提となる決定:** `UD-501` `UD-502` `UD-506`〜`UD-512` `UD-902`
→ **これらが未決定の間は Phase 5 に着手しない。**

> ⚠️ **Phase 4.5 の完了前に Phase 5 を理由なく先行させない。**
> Wallet 連携はチェーン決定に依存しないため、先に価値を出せる。

### Phase 6 — 運用

- 管理画面（注文・受取権・ジョブの一覧と手動再試行）
- 返金処理
- Outbox 配信ワーカーと外部連携
- 整合性チェックの日次実行、監視・アラート

**前提となる決定:** `UD-104`（返金ポリシー）、`UD-1102`（監視基盤）

## 5. 次に決めるべきこと（優先順）

Phase 2 以降を止めないために、次の順で決定を求める。

| 順  | 決定事項                               | 理由                                                   |
| --- | -------------------------------------- | ------------------------------------------------------ |
| 1   | `UD-1008` 代理店システムの参照先と契約 | **参照先が見つからず、着手そのものができない**         |
| 2   | `UD-1005` Claim API の認証             | 受入条件「Claim はログイン必須」を検証可能にするため   |
| 3   | `UD-1006` `common_user_id` の補完条件  | 誤ると他人の Wallet へ渡る。実装前に必要               |
| 4   | `UD-702` 決済事業者                    | Phase 3 の前提                                         |
| 5   | `UD-401` 通貨・税                      | Phase 3 の前提                                         |
| 6   | `UD-504` ゲスト購入の可否              | Phase 3 の前提。認証設計が変わる                       |
| 7   | `UD-801` JWT 検証方式                  | Phase 4 の前提                                         |
| 8   | `UD-508` 画像の長期参照方式            | Phase 4.5 の前提。Wallet へ渡す URL を作れない         |
| 9   | `UD-106` 法的性質（法務見解）          | 表示義務・税務の前提。リードタイムが長いので早めに着手 |
| 10  | `UD-501` `UD-502` チェーン・カストディ | Phase 5 の前提。**Wallet 連携はこれを待たない**        |

> **`UD-1002` は 2026-08-13 に完了した。** 調査の結果、OVEW Wallet は
> 特定のチェーンを使っておらず、MVP ではカストディも不要と分かった。
> これにより **Wallet 連携がチェーン決定から切り離せた**（Phase 4.5）。
>
> 一方で、その指示書を精査した結果 `UD-1005`〜`UD-1008` が新たに必要になった。
> このうち **`UD-1008` は同日に解決した**（代理店システムは公開リポジトリで、
> 契約書と実装の両方を確認できた）。`UD-1006` も契約 §4 の安全条件が判明したため、
> 仮決定を置ける状態になった。
>
> **残る `UD-1005` だけが、こちらでは決められない。** 相手との合意が要る。
