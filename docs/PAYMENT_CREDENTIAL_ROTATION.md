# 決済資格情報の世代管理（`UD-118`）

**状態**: 🟡 仕様案（実装前）
**決定日**: 2026-08-19（管理画面から交換できるようにする方針を決定）
**前提**: 運営会社の変更が 1 年以内に起こりうる（2026-08-19 確認）

---

## 1. なぜ要るか

決済の鍵を配備環境の秘密情報管理にだけ置くと、鍵を替えられるのは
その配備環境を触れる人だけになる。次の場面で運用が止まる。

| 場面               | 起きること                                           |
| ------------------ | ---------------------------------------------------- |
| **運営会社の変更** | 決済アカウントごと替わる。替えられないと販売が止まる |
| 鍵の漏洩           | 即座に止めて差し替えたいが、配備の手順を踏むしかない |
| 定期ローテーション | 手順が重いので、実質行われなくなる                   |

⚠️ **「配備をやり直せばよい」で済ませない。** 決済が止まっている間、
購入者は「購入準備中」の画面しか見られない。復旧までの時間が、
そのまま売上の穴になる。

---

## 2. 「鍵の入れ替え」と「運営会社の変更」は別物

ここを混ぜると設計を誤る。

|                    | 鍵のローテーション | 運営会社の変更                     |
| ------------------ | ------------------ | ---------------------------------- |
| 決済アカウント     | 同じ               | **別になる**                       |
| 過去注文の決済参照 | 新しい鍵で引ける   | **新しい鍵では引けない**           |
| 過去注文の返金     | 新しい鍵でできる   | **旧アカウントの鍵でしかできない** |
| 入金先             | 同じ               | **旧注文の入金は旧社の口座**       |
| Webhook            | 同じ宛先           | **旧アカウントからも届き続ける**   |

`payments` は注文ごとに `provider_session_ref` / `provider_charge_ref` を
保存している。これらは**発行したアカウントに紐づく識別子**で、別の
アカウントの鍵では解決できない。

⚠️ **「いまの鍵を新しい値で上書きする」作りにしない。** 上書きにすると、
切り替えた瞬間に過去注文の返金と照会ができなくなる。お金を返せない
注文が残るのは、取り返しがつかない部類の事故になる。

したがって設計の中心は「鍵の入力欄」ではなく、**新旧の鍵が同時に
有効でいられること**に置く。

## 3. データモデル

### 3.1 `payment_credentials`（新設）

決済の資格情報を**世代**として複数持つ。

| 列                             | 型           | 説明                                                                          |
| ------------------------------ | ------------ | ----------------------------------------------------------------------------- |
| `id`                           | uuid         |                                                                               |
| `provider`                     | text         | `stripe` など                                                                 |
| `environment`                  | text         | `staging` / `production`                                                      |
| `generation`                   | int          | 1 から始まる連番。⚠️ 同一 (provider, environment) 内で一意                    |
| `account_ref`                  | text?        | 決済事業者側のアカウント識別子（`acct_…`）。⚠️ **秘密ではない**。画面に出す   |
| `label`                        | text?        | 運営が付ける覚え書き（「旧運営」など）。⚠️ 秘密を書かせない                   |
| `status`                       | text         | `pending` / `active` / `retired`                                              |
| `secret_key_ciphertext` 他     | —            | 既存の `integration_secrets` と同じ封の形（AEAD・nonce・authTag・keyVersion） |
| `webhook_secret_ciphertext` 他 | —            | 同上                                                                          |
| `api_version`                  | text?        | この世代で固定する API 版                                                     |
| `registered_by_account_id`     | uuid         | 登録した人                                                                    |
| `activated_by_account_id`      | uuid?        | 有効化した人                                                                  |
| `last_check_succeeded`         | bool?        | 直近の接続確認の成否。⚠️ **成功していないと有効化できない**                   |
| `activated_at` / `retired_at`  | timestamptz? |                                                                               |
| `accepts_new_payments`         | bool         | `active` でも新規受付だけ止められる                                           |
| `created_at` / `updated_at`    | timestamptz  |                                                                               |

**制約**

- `UNIQUE (provider, environment, generation)`
- 部分 UNIQUE: `(provider, environment) WHERE status = 'active' AND accepts_new_payments`
  → **新規の支払い口を作る世代は常に 1 つ**
- `CHECK (status <> 'active' OR last_check_succeeded)`
  → **接続確認を通らずに有効化できない**（鍵の打ち間違いをここで止める）
- `CHECK (status <> 'active' OR activated_by_account_id IS NOT NULL)`
  → 誰が有効化したか分からない `active` を作らせない
- `CHECK (status = 'active' OR NOT accepts_new_payments)`
  → `pending` や `retired` が新規受付になることはない

⚠️ **`integration_secrets` を流用しない。** あちらは「1 用途につき有効 1 件」で、
古いものは `retired` にして使わなくなる形。決済は**古い世代を使い続ける**
必要があるので、前提が違う。無理に載せると、返金の経路が
「退役した鍵を読む」という説明のつかない形になる。

### 3.2 `payments.credential_id`（追加）

その決済を**どの世代の鍵で処理したか**を記録する。

- 支払い口を作るときに、その時点の受付世代を書き込む
- 返金・照会は**この世代の鍵**で行う
- `ON DELETE RESTRICT`。世代を消せなくする（消すと返金経路が消える）

⚠️ **これが設計の要。** ここが無いと、切り替え後に「どの鍵で返せばよいか」を
誰も判断できない。

### 3.3 既存データの移行

配備環境にある鍵を**世代 1** として取り込む。

1. 移行スクリプトが `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` を読み、
   封をして `generation = 1`・`status = 'active'` で登録する
2. 既存の `payments` 行すべてに `credential_id = 世代1` を埋める
3. 以後、環境変数は**読まない**

⚠️ **一度限りの移行処理。** 起動のたびに環境変数から読み直す作りにはしない。
読み直すと、DB と環境変数で違う鍵が使われる二重管理になる。
（手数料率で同じ判断をしている。`UD-115` 参照）

## 4. 状態遷移

```
        登録              承認 + 接続確認
pending ────► pending ──────────────────► active
   │          (承認待ち)                     │
   │                                        │ 新規受付だけ止める
   ▼                                        ▼
retired ◄──────────────────────────── active (accepts_new_payments = false)
（破棄）                                     │
                                            │ 次の世代が受付を引き継ぎ、
                                            │ 未処理の決済が無くなったら
                                            ▼
                                         retired
```

**`retired` でも鍵は消さない。** 過去注文の返金と照会に要る。
「新規受付をしない」だけの状態。

⚠️ **世代を削除する操作を作らない。** 消せる口があると、いつか
「もう古いから」と消され、その世代の注文が返金不能になる。
保持期間の方針は `UD-1103`（バックアップ・保持期間）と合わせて別途決める。

## 5. 運営会社を切り替える手順

1. 新しいアカウントの鍵を**登録**する（`pending`）
   - ⚠️ この時点では何も起きない。**戻せる状態を必ず経由させる**
2. **接続確認**を行う。新しい鍵で決済事業者へ実際に問い合わせ、
   アカウント識別子を取得して `account_ref` に記録する
   - ⚠️ ここで初めて「別のアカウントかどうか」が確定する
   - ⚠️ **これを通らないと次へ進めない。** 鍵の打ち間違いはここで止まる
3. 新世代を**有効化**する。新規の支払い口はここから新世代を使う
4. 旧世代を `accepts_new_payments = false` にする
   - ⚠️ **`retired` にしない。** 返金と照会は旧世代の鍵で続く
5. 旧世代の未確定な決済（`checkout_created` の滞留）が無くなり、
   返金の可能性が業務上無くなったら `retired` にする

⚠️ **3 と 4 は同一トランザクションで行う。** 分けると、受付世代が
2 つある瞬間か 0 の瞬間ができる。前者はオーバーセル、後者は販売停止。

### 切り戻し（ロールバック）

手順 3 の直後に問題が分かった場合、旧世代を受付に戻すだけで元に戻る。
新世代は `pending` へは戻さず、`accepts_new_payments = false` の
`active` として残す（その間に発生した決済の返金経路が要るため）。

## 6. Webhook の検証

⚠️ **旧アカウントからも知らせは届き続ける。** 切り替え後も、旧アカウントで
発生した決済の `payment_intent.succeeded` などが来る。

- 署名検証は、**`retired` を含むすべての世代の署名鍵**で試す
- 最初に検証が通った世代を、その受信記録へ残す
- どの世代でも通らなければ 400（理由は返さない）

⚠️ **試す順序で結果を変えない。** 通るか通らないかだけを見る。
「新しい世代を先に試す」のは速さのためで、判定には影響させない。

⚠️ **世代が増えるほど検証の回数が増える。** 保持する世代数に上限を設け、
超えるときは運用で `retired` を整理する（削除ではなく、検証対象からの除外）。
上限は実装時に決める（初期案: 5）。

## 7. 認可と再認証

**2026-08-19 決定: 二者承認は行わない。** 登録 → 接続確認 → 有効化の 3 段とする。

⚠️ **理由を残す。** 当初案は「登録者と別のオーナーが承認する」だったが、
オーナーが 1 人の運営では**管理画面から鍵を交換できなくなる**。復旧経路
（CLI・緊急上書き）は配備環境を触れる人向けなので、通常の交換が毎回
CLI 頼みになり、「運営者が管理画面のみで運営できる」という方針
（`ADMIN_OPERATIONS_GAP.md` §0）から外れる。

二者承認の代わりに、次の 3 つで「うっかり」を防ぐ。

1. **戻せる状態を必ず経由する** — 登録した時点では何も起きない（`pending`）
2. **接続確認を通らないと有効化できない** — 鍵の打ち間違いはここで止まる
3. **本番では確認入力と再認証を求める** — 押し慣れによる誤操作を防ぐ

| 操作             | 権限          | 再認証   |
| ---------------- | ------------- | -------- |
| 状態を見る       | operator 以上 | 不要     |
| 世代を登録する   | **オーナー**  | **必要** |
| 接続確認を行う   | **オーナー**  | 不要     |
| 有効化・受付切替 | **オーナー**  | **必要** |
| 退役させる       | **オーナー**  | **必要** |
| 緊急停止         | operator 以上 | **不要** |

⚠️ **緊急停止だけは条件を付けない。** 事故を止める操作なので、いつでも
通らなければならない。条件を足すと、止めたいときに止められない。

**再認証の方式**: トークンの発行時刻が一定時間内（初期案: 5 分）で
あることを求める。古ければ `401` と「再度ログインしてください」を返す。
⚠️ パスワードを再入力させる形にはしない。認証は Supabase 側にあり、
こちらでパスワードを受け取る経路を作るべきではない。

**確認画面**: 本番環境の操作では、`production` の文字と対象の
アカウント識別子を**利用者に入力させてから**実行する。
⚠️ 「本当によろしいですか」の一段だけにしない。押し慣れると意味を失う。

## 8. 緊急停止と復旧経路

### 緊急停止

決済連携を止める。既存の「停止」と同じ経路。⚠️ 止めても
**手数料率と過去注文の返金経路は変わらない**。

### 管理画面へ入れない場合

⚠️ **これを用意しないと、鍵を DB へ移した瞬間に「詰む経路」ができる。**
ログインが壊れている・オーナーが全員不在、という場面で決済を復旧できない。

用意するもの:

1. **CLI**（`apps/worker` の staging fixture と同じ形）
   - DB へ直接つないで世代を登録・有効化する
   - ⚠️ 実行には配備環境の暗号鍵が要る。つまり**配備環境を触れる人**にしかできない
   - ⚠️ 監査ログへ「CLI から実行された」ことを残す。誰がやったか分からない
     変更を残さない
2. **緊急上書き**（`PAYMENT_EMERGENCY_CREDENTIAL_OVERRIDE`）
   - 環境変数の鍵を一時的に使う。⚠️ **明示的に有効化したときだけ**
   - 有効な間は、管理画面の先頭に「緊急上書きが有効です」と大きく出す
   - 起動ログにも毎回出す
   - ⚠️ **既定では無効。** 既定で有効にすると、二重管理が黙って復活する

## 9. 監査ログ

すべての操作を残す。⚠️ **鍵そのもの・先頭・末尾・署名値は残さない。**

| 記録する                                             | 記録しない |
| ---------------------------------------------------- | ---------- |
| 世代番号                                             | 鍵の値     |
| アカウント識別子（`acct_…`）                         | 鍵の一部   |
| 操作の種類（登録・接続確認・有効化・受付切替・退役） | 署名値     |
| 操作者                                               |            |
| 実行日時                                             |            |
| 接続確認の結果                                       | 応答本文   |
| CLI 実行か画面操作か                                 |            |

⚠️ **鍵の平文入力欄は「登録」のときだけ。** 一度預けたら二度と表示しない。

| 出す                                                 | 出さない       |

| テスト／本番モード                                   | 署名値         |

## 11. 移行の順序（本番販売開始との関係）

⚠️ **本番販売を始める前に入れる。** 始めたあとに入れると、既存の
`payments` 行へ `credential_id` を埋める移行が要る。件数が増えてからでは
移行そのものが事故の種になる。

1. `payment_credentials` と `payments.credential_id` を追加
2. 配備環境の鍵を世代 1 として取り込む
3. `payments` の既存行へ世代 1 を埋める
4. `credential_id` を `NOT NULL` にする
5. 環境変数の参照を落とす

## 12. テスト項目

**世代と返金経路**

- 切り替え後も、旧世代で処理した決済を旧世代の鍵で照会できる
- 新世代で処理した決済は新世代の鍵で照会される
- 受付世代は常に 1 つだけ（部分 UNIQUE が効く）
- 有効化と旧世代の受付停止が 1 トランザクションで行われる
- 世代を削除できない

**認可と再認証**

- 接続確認を通っていない世代は有効化できない
- オーナー以外は登録・接続確認・有効化できない
- 再認証が古いと断られる
- 緊急停止だけは再認証なしで通る

**Webhook**

- 旧世代の署名でも検証が通る
- どの世代でも通らない署名は 400
- 検証に使った世代が受信記録へ残る
- 保持上限を超えた世代は検証対象から外れる

**秘密の非露出**

- 一覧・詳細・エラー・監査ログのいずれにも鍵が出ない
- 末尾 4 文字も出ない
- 接続に失敗したときの例外へ鍵が混ざらない

**復旧経路**

- CLI から世代を登録・有効化できる
- CLI 実行が監査ログに残る
- 緊急上書きは既定で無効
- 緊急上書きが有効なとき、画面と起動ログに警告が出る

## 13. 今回やらないこと

- 決済事業者を Stripe 以外へ替えること（`payment` という名前は既に
  事業者非依存にしてあるが、別事業者のアダプタは作らない）

- 世代の自動削除・自動退役（判断を人に残す）

| 残り  | 内容                                                                            |

画面で「有効」と出ているのに実際には環境変数の鍵が使われている、という
食い違いが起きうる。**本番販売の開始前に §11-5 まで終わらせること。**
