## 1. 環境

🟡 **仮決定:**

| 環境         | 用途         | 外部接続                            |
| ------------ | ------------ | ----------------------------------- |
| `local`      | 開発者の手元 | すべて Fake。実サービスへ接続しない |
| `test`       | 自動テスト   | すべて Fake。ネットワーク遮断       |
| `staging`    | 結合確認     | 決済・認証は各社のテスト環境        |
| `production` | 本番         | 本番サービス                        |

✅ **事実:** 今回（Phase 0-1）は `local` / `test` のみを対象とする。
本番 Stripe / 本番 Supabase / 本番ブロックチェーンへ接続しない。

🟡 **仮決定:** 環境変数 `APP_ENV` で環境を明示し、
**`APP_ENV !== 'production'` のとき、本番ドメインを指す接続先が設定されていたら起動を拒否する**
ガードを入れる。理由: 開発環境から誤って本番に繋ぐ事故が最も重い。

❓ **未決定 `UD-1101`:** ホスティング先と staging の有無（→ `UD-302`）。

## 2. 起動と停止

| プロセス | 起動                                  | 停止                                           |
| -------- | ------------------------------------- | ---------------------------------------------- |
| api      | `pnpm --filter @sengoku/api start`    | SIGTERM で処理中リクエストを完了させてから終了 |
| web      | `pnpm --filter @sengoku/web start`    | SIGTERM                                        |
| worker   | `pnpm --filter @sengoku/worker start` | SIGTERM で**現在のジョブ完了後**に終了         |

🟡 **仮決定:** worker は 2 モードを持つ。

| モード       | 用途                                         |
| ------------ | -------------------------------------------- |
| 常駐（既定） | ループでジョブを取得し続ける                 |
| `--once`     | 1バッチだけ処理して終了。cron 起動の環境向け |

理由: デプロイ先（`UD-302`）が常駐プロセスを許すか未定のため、
どちらでも動くようにしておく。

> ⚠️ **worker の SIGTERM 処理は特に重要。**
> `processing` のまま強制終了された行は、外部へ送信済みかどうかが分からず、
> 自動復旧できない（[LAZY_MINT_FLOW.md](./LAZY_MINT_FLOW.md) §3.6）。
> グレースフルシャットダウンでこの状態を作らないようにする。

## 3. ヘルスチェック

| エンドポイント | 意味                  | 監視での使い方                   |
| -------------- | --------------------- | -------------------------------- |
| `GET /healthz` | プロセスが生きている  | コンテナの liveness probe        |
| `GET /readyz`  | 依存（DB 等）が使える | ロードバランサの readiness probe |

🟡 **仮決定:** liveness は**外部依存を確認しない**。
DB 障害で liveness が失敗すると、コンテナが再起動を繰り返し、
DB 復旧後の立ち上がりを遅らせる。

## 4. 監視とアラート

🟡 **仮決定:** 次を監視する。優先度の高い順。

| 優先 | 指標                                 | 閾値（仮）       | 意味                                       |
| ---- | ------------------------------------ | ---------------- | ------------------------------------------ |
| P1   | `mint.failed` イベント               | 1件でも          | **人手対応が必要。**顧客は支払済みで未受取 |
| P1   | `mint_jobs` の `processing` 滞留時間 | 15分超           | 外部への送信状況が不明。多重発行リスク     |
| P1   | Webhook 署名検証失敗                 | 急増             | 攻撃または設定ミス                         |
| P2   | `mint_jobs` の `queued` 滞留数       | 100件超 / 30分超 | worker 停止またはチェーン障害              |
| P2   | `outbox_events` の未配信滞留         | 30分超           | 配信ワーカー停止                           |
| P2   | 注文の `pending` 滞留数              | 急増             | 決済導線の障害                             |

## 5. 運用手順（Runbook）

### 5.1 Mint が失敗し続ける

```
1. mint.failed の対象 entitlement_id を特定する
2. mint_jobs.last_error_code で分類を確認する
3. 外部プロバイダの状態を確認する
4. 恒久障害でなければ、管理APIから手動再試行
   POST /api/v1/admin/mint-jobs/{id}/retry
   → attempt_count をリセットし status='queued' に戻す
5. 恒久障害なら顧客対応（UD-402 のポリシーに従う。未確定なら事業判断を仰ぐ）
```

### 5.2 ジョブが `processing` のまま滞留

> ⚠️ **自動で `queued` に戻さない。** 二重発行の危険がある。

```
1. MintingPort.getStatus(submissionRef) で外部側の実状態を照会
2. 外部側で「発行済み」→ 手動で nft_tokens を登録し succeeded にする
3. 外部側で「未受付」→ queued に戻して再試行させる
4. 外部側で「不明」→ 戻さない。プロバイダに問い合わせる
5. いずれも mint_jobs.note に対応内容を記録する
```

### 5.3 Webhook を取りこぼした

```
1. 決済事業者のダッシュボードで該当イベントを特定
2. 事業者側の再送機能で再送させる
3. 冪等性（webhook_events の UNIQUE）により、重複しても安全
4. それでも処理されない場合、webhook_events に記録があるか確認
   - 記録あり・status='failed' → アプリのバグ。修正して再送
   - 記録なし → 到達していない。ネットワーク・署名設定を確認
```

### 5.4 在庫（発行上限）の不整合を疑うとき

```sql
-- reserved_count が実際の pending 注文と一致するか
SELECT a.id, a.reserved_count,
       COALESCE(SUM(ol.quantity), 0) AS actual_reserved
  FROM artworks a
  LEFT JOIN order_lines ol ON ol.artwork_id = a.id
  LEFT JOIN orders o ON o.id = ol.order_id AND o.status = 'pending'
 GROUP BY a.id
HAVING a.reserved_count <> COALESCE(SUM(ol.quantity), 0);

-- issued_count が entitlements 件数と一致するか
SELECT a.id, a.issued_count, COUNT(e.id) AS actual_issued
  FROM artworks a LEFT JOIN entitlements e ON e.artwork_id = a.id
 GROUP BY a.id HAVING a.issued_count <> COUNT(e.id);
```

🟡 **仮決定:** この整合性チェックを**日次で自動実行**し、
不一致があればアラートする。カウンタのずれは静かに進行するため。

## 6. デプロイ

🟡 **仮決定:**

| 原則         | 内容                                                                        |
| ------------ | --------------------------------------------------------------------------- |
| 順序         | DB マイグレーション → api → worker → web                                    |
| 互換性       | マイグレーションは**後方互換**（expand → migrate → contract）               |
| worker       | 新旧が同時に動いても壊れないこと（ジョブの取得は排他制御済み）              |
| ロールバック | アプリは前バージョンへ戻せる。**DB は前方向のみ**（データ損失を避けるため） |

> ⚠️ **DB を戻す前提のデプロイをしない。** 発行記録は再現不能な資産である。
> 「戻せないマイグレーション」を打つ前に、必ずバックアップと復旧手順を確認する。

❓ **未決定 `UD-1103`:** バックアップの取得間隔・保持期間・復旧目標（RPO/RTO）。

### 検証中に見つかり、修正した問題

| 事象                         | 原因                                                                                     | 対応                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 起動ログが出力されない       | pino の既定バッファリングにより、起動直後・終了直前のログが失われていた                  | 標準出力への書き込みを同期に変更（障害調査でいちばん必要な区間を取りこぼさないため） |

### 既知の制約

- `prisma validate` は `DATABASE_URL` が必要（`prisma generate` は不要）。
  CI では実行していない。
- E2E は、ブラウザが事前配置された環境ではバージョン不一致で起動できないことがある。
  その場合は `PLAYWRIGHT_CHROMIUM_EXECUTABLE` で実行ファイルを指定する。
  CI は `playwright install` で正規のブラウザを取得するため、この制約に当たらない。
- 実 PostgreSQL に対する結合テスト（DB 制約の実動作検証）は Phase 2 で実施する。
  Phase 1 ではスキーマ上に制約が定義されていることを静的に検査するに留めている。

### DB 制約（21 個の CHECK ＋ 索引 ＋ トリガ）

指示書が求めた保証は、すべて DB 側で担保している。

| 要求                                     | 実現方法                                                                                        |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `max_supply >= 1`                        | CHECK `artworks_max_supply_positive`                                                            |
| `reserved_count >= 0`                    | CHECK `artworks_reserved_count_non_negative`                                                    |
| `issued_count >= 0`                      | CHECK `artworks_issued_count_non_negative`                                                      |
| `reserved + issued <= max_supply`        | CHECK `artworks_supply_within_max`                                                              |
| 販売価格は 0 円より大きい                | CHECK `listings_price_positive`                                                                 |
| 終了日時は開始日時より後                 | CHECK `listings_period_ordered`                                                                 |
| slug は一意                              | UNIQUE `artworks.slug`                                                                          |
| 公開済み作品だけを出品できる             | **トリガ** `listings_require_published_artwork`（別テーブル参照のため CHECK では表現できない）  |
| 同一作品に同時に複数の有効出品を作れない | **部分ユニーク索引** `listings_one_effective_per_artwork`（`status IN ('active','scheduled')`） |

### 検証中に見つけて対処した問題

| 事象                                                                            | 対応                                                                                                                                                                                    |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `evaluatePurchasability` が「開始日時を過ぎた `scheduled`」を購入不可にしていた | 「バッチを前提にしない」という設計の要点を自分で潰していた。分岐を削除し、DB の CHECK で不整合を防ぐ形に整理                                                                            |
| 販売終了後の画面が「ただいま販売しておりません」になっていた                    | `resolveDisplayState` が状態 `ended` を写していなかった。再開を待たせてしまうため、終了は終了として伝えるよう修正                                                                       |
| Prisma が一意制約違反を独自メッセージに変換し、制約名で判定できなかった         | 一意制約用の判定ヘルパーを分離。CHECK 制約は従来どおり制約名で確認                                                                                                                      |
| ESLint の `no-control-regex` が制御文字検査に抵触                               | 制御文字の検出そのものが目的なので、理由を書いて当該行のみ無効化                                                                                                                        |
| **E2E が保存した画像 9 件をリポジトリへ取り込んでいた**                         | `MEDIA_STORAGE_DIR` の保存先を `.gitignore` に入れていなかった。追跡を外し、`.media/` と `.e2e-media/` を除外。**アップロードされたデータをリポジトリへ入れない**という前提が抜けていた |
| **DB 結合テスト 26 件が `pnpm verify` と CI で黙って飛んでいた**                | 下記「番人が届かなかった件」を参照                                                                                                                                                      |

#### 番人が届かなかった件（最も重い見落とし）

**事象:** DB 結合テスト 26 件が、`pnpm verify` でも CI でも実行されていなかった。
「制約が実際に効くことを確認済み」という報告は、**この時点では裏付けが無かった**。

**原因:** Turborepo 2 は既定で環境変数を絞り込み、`turbo.json` に書いた変数しか
タスクへ渡さない。`TEST_DATABASE_URL` を書いていなかったため接続先が届かず、
結合テストはスキップされていた。

**なぜ気付けなかったか:** スキップを失敗に変えるための番人
（`REQUIRE_INTEGRATION_TESTS=1`）を用意してあったが、**その番人を起動する変数自体が
同じ絞り込みで消えていた。** 合図が届かなければ、合図を頼りにした番人は何もしない。
CI は緑で、テスト件数も増え続けていたので、外からは正常に見えていた。

**対処:**

1. `turbo.json` の `test` タスクへ `DATABASE_URL` / `TEST_DATABASE_URL` /
   `REQUIRE_INTEGRATION_TESTS` を明記した
2. 番人の判定を `REQUIRE_INTEGRATION_TESTS=1` **または** `CI` に広げた。
   片方の合図が消えても止まる（`CI` は `globalEnv` にあり必ず届く）
3. 接続先を外した状態で実際に失敗することを確認した

**教訓:** 「検査を必須にする仕組み」自体が、検査対象と同じ経路で壊れることがある。
番人を置いたら、**番人が実際に噛みつくところまで確かめる。**
テスト件数が 444 → 470 に増えたのは、機能追加ではなく、飛んでいた 26 件が戻ったため。

### 既知の制約

- **画面からの登録・編集フォームは未実装。** 運営のログイン経路が Phase 4 のため、
  現時点では画面に API の手順を案内している。押せるが何も起きないボタンは置いていない。
- 冪等キーの保存先はプロセス内メモリ。複数台構成では効かない。
  取り返しのつかない注文（Phase 3）では DB の一意制約へ移す。
- 作品を `archived` にしても既存の出品は残る。公開APIは作品の状態で絞るため露出しないが、
  出品側も `ended` にする運用とする。
- 一覧取得で作品ごとに出品を引くため N+1 になる。1 ページ最大 100 件で
  実用上問題ない範囲に収めており、必要になってからまとめ取得へ差し替える。

### 運用上の注意

⚠️ **`create_if_missing` の既定値は相手側で `true`。**
照会のつもりで省略すると、副作用として人物が新規作成される。
本システムのポートでは**省略できない必須項目**にしてある。

⚠️ **`CONFLICT` と `ERROR` は自動で解けない。**
ワーカーは件数をログに出すだけで、値は触らない。
`common_user_id` そのものはログに出さない。

### 積み残し

- ログイン直後のベストエフォート解決は入れていない。
  指示書 §5.3 は「試してもよい」（任意）としており、
  認証経路に外部呼び出しを足すと**遅延と失敗の面が増える**ため、
  まずワーカー側だけで運用して様子を見る。
- 掃き出しの間隔は `WORKER_POLL_INTERVAL_MS` に従う。
  常駐と cron のどちらで動かすかは `UD-1101` のまま未決定で、
  **どちらでも動く形**にしてある。
