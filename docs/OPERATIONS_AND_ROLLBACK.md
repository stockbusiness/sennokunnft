## 1. 環境

🟡 **仮決定:**

| 環境         | 用途         | 外部接続                            |
| ------------ | ------------ | ----------------------------------- |
| `local`      | 開発者の手元 | すべて Fake。実サービスへ接続しない |
| `test`       | 自動テスト   | すべて Fake。ネットワーク遮断       |
| `staging`    | 結合確認     | 決済・認証は各社のテスト環境        |
| `production` | 本番         | 本番サービス                        |

✅ **事実:** 今回（Phase 0-1）は `local` / `test` のみを対象とする。
本番 Stripe / 本番 Supabase / 本番ブロックチェーンへ接続しない。

🟡 **仮決定:** 環境変数 `APP_ENV` で環境を明示し、
**`APP_ENV !== 'production'` のとき、本番ドメインを指す接続先が設定されていたら起動を拒否する**
ガードを入れる。理由: 開発環境から誤って本番に繋ぐ事故が最も重い。

❓ **未決定 `UD-1101`:** ホスティング先と staging の有無（→ `UD-302`）。

## 2. 起動と停止

| プロセス | 起動                                  | 停止                                           |
| -------- | ------------------------------------- | ---------------------------------------------- |
| api      | `pnpm --filter @sengoku/api start`    | SIGTERM で処理中リクエストを完了させてから終了 |
| web      | `pnpm --filter @sengoku/web start`    | SIGTERM                                        |
| worker   | `pnpm --filter @sengoku/worker start` | SIGTERM で**現在のジョブ完了後**に終了         |

🟡 **仮決定:** worker は 2 モードを持つ。

| モード       | 用途                                         |
| ------------ | -------------------------------------------- |
| 常駐（既定） | ループでジョブを取得し続ける                 |
| `--once`     | 1バッチだけ処理して終了。cron 起動の環境向け |

理由: デプロイ先（`UD-302`）が常駐プロセスを許すか未定のため、
どちらでも動くようにしておく。

> ⚠️ **worker の SIGTERM 処理は特に重要。**
> `processing` のまま強制終了された行は、外部へ送信済みかどうかが分からず、
> 自動復旧できない（[LAZY_MINT_FLOW.md](./LAZY_MINT_FLOW.md) §3.6）。
> グレースフルシャットダウンでこの状態を作らないようにする。

## 3. ヘルスチェック

| エンドポイント | 意味                  | 監視での使い方                   |
| -------------- | --------------------- | -------------------------------- |
| `GET /healthz` | プロセスが生きている  | コンテナの liveness probe        |
| `GET /readyz`  | 依存（DB 等）が使える | ロードバランサの readiness probe |

🟡 **仮決定:** liveness は**外部依存を確認しない**。
DB 障害で liveness が失敗すると、コンテナが再起動を繰り返し、
DB 復旧後の立ち上がりを遅らせる。

## 4. 監視とアラート

🟡 **仮決定:** 次を監視する。優先度の高い順。

| 優先 | 指標                                 | 閾値（仮）       | 意味                                       |
| ---- | ------------------------------------ | ---------------- | ------------------------------------------ |
| P1   | `mint.failed` イベント               | 1件でも          | **人手対応が必要。**顧客は支払済みで未受取 |
| P1   | `mint_jobs` の `processing` 滞留時間 | 15分超           | 外部への送信状況が不明。多重発行リスク     |
| P1   | Webhook 署名検証失敗                 | 急増             | 攻撃または設定ミス                         |
| P2   | `mint_jobs` の `queued` 滞留数       | 100件超 / 30分超 | worker 停止またはチェーン障害              |
| P2   | `outbox_events` の未配信滞留         | 30分超           | 配信ワーカー停止                           |
| P2   | 注文の `pending` 滞留数              | 急増             | 決済導線の障害                             |
| P3   | API エラー率 / レイテンシ            | —                | 一般的な劣化検知                           |
| P3   | `readyz` 失敗                        | —                | 依存障害                                   |

> 決済は成功しているので売上は立ち、画面も動く。

## 5. 運用手順（Runbook）

### 5.1 Mint が失敗し続ける

```
1. mint.failed の対象 entitlement_id を特定する
2. mint_jobs.last_error_code で分類を確認する
3. 外部プロバイダの状態を確認する
4. 恒久障害でなければ、管理APIから手動再試行
   POST /api/v1/admin/mint-jobs/{id}/retry
   → attempt_count をリセットし status='queued' に戻す
5. 恒久障害なら顧客対応（UD-402 のポリシーに従う。未確定なら事業判断を仰ぐ）
```

### 5.2 ジョブが `processing` のまま滞留

> ⚠️ **自動で `queued` に戻さない。** 二重発行の危険がある。

```
1. MintingPort.getStatus(submissionRef) で外部側の実状態を照会
2. 外部側で「発行済み」→ 手動で nft_tokens を登録し succeeded にする
3. 外部側で「未受付」→ queued に戻して再試行させる
4. 外部側で「不明」→ 戻さない。プロバイダに問い合わせる
5. いずれも mint_jobs.note に対応内容を記録する
```

### 5.3 Webhook を取りこぼした

```
1. 決済事業者のダッシュボードで該当イベントを特定
2. 事業者側の再送機能で再送させる
3. 冪等性（webhook_events の UNIQUE）により、重複しても安全
4. それでも処理されない場合、webhook_events に記録があるか確認
   - 記録あり・status='failed' → アプリのバグ。修正して再送
   - 記録なし → 到達していない。ネットワーク・署名設定を確認
```

### 5.4 提携先（OVEW Wallet）へお届けできていない

管理画面 **「お届け」**（`/admin/wallet-deliveries`）で状態を見る。
必要な権限は閲覧が `integration.view`、送り直しが `wallet_delivery.retry`。

```
1. 「全体の件数」で、打ち切り（DEAD）と失敗（FAILED）の数を見る
   ⚠️ 絞り込みを掛けても、この件数は全体を指す
2. 行を開き、「うまくいかなかった理由」を読む
   - 提携先に断られました（401 / 403） → 資格情報。/admin/integrations を見る
   - 提携先で問題が起きています（5xx） → 相手の復旧待ち。しばらく置いて送り直す
   - お届けの内容を受け付けてもらえませんでした（4xx） → こちらの不具合。
     直してから送り直す。同じ内容を送り直しても直らない
   - 時間内に応答がありませんでした / 接続できませんでした → 経路。復旧後に送り直す
3. 直ったら「もう一度お届けする」を押す
```

⚠️ **「お届けしています」（PROCESSING）の行は送り直せない。**
送信中か、送信直後に落ちた可能性がある。届いたかどうかが分からない状態で
押し直すと、相手の冪等性だけが最後の砦になる。しばらく置くと、
取り残しの回収（`reclaimStale`）で `PENDING` に戻り、自動で送り直される。

⚠️ **お届けした本文は画面に出ない。** お客さまの情報が含まれるため
（指示書 §5）。提携先へ問い合わせるときは「お問い合わせ番号」（`event_id`、
相手の `Idempotency-Key` と同じ値）と「調査用の番号」（`correlation_id`）を伝える。

管理画面が開けないとき（配備の事故・認証の不調）は、CLI が逃げ道として残っている:

```
pnpm wallet:resend --event-id=<お問い合わせ番号>
```

### 5.5 提携先の接続先や鍵を替えたい

管理画面 **「外部サービス」**（`/admin/integrations`）。**オーナーだけ**が操作できる。

```
1. 画面の先頭で staging / production のどちらを触っているか確かめる
2. 「接続先を設定する」に URL と鍵の名前（鍵ID）を入れて保存
   ⚠️ 接続先を変えると、それまでの接続確認の成功は無効になる
3. 「鍵をお預かりする」に新しい鍵を貼り付けて保存
   → この時点では**まだ使われない**（待機中）
4. 「接続を確かめる」を押す
5. 「お預かりしている鍵」の一覧から「この鍵を使いはじめる」を押す
   → 古い鍵はここで退役する
6. 「お届けを始める」を押す
```

⚠️ **鍵は交換の途中で 2 本になったり 0 本になったりしない。**
「使いはじめる」は、新しい鍵の有効化と古い鍵の退役を 1 つの書き込みで行う。

⚠️ **worker の再起動は要らない。** 送信のたびに DB から接続先と鍵を読む
（要決定 03）。再起動を前提にすると、忘れたときに「古い鍵で送り続けている」
ことに誰も気づけない。

⚠️ **「接続を確かめる」で分かるのは、接続先へ届くことまで。**
鍵が正しいかどうかは分からない。先方に安全なテスト手段があるかを
伺えていないため、業務データを送る確認は作っていない（要決定 06）。

⚠️ **管理画面で接続先を入れると、以後は DB が正になる。**
それまで `WALLET_DELIVERY_*` の環境変数で動いていた環境も、
接続先を保存した時点で DB を見るようになる。**「お届けを止める」は
環境変数へ落ちない**——止めたのに送り続ける、を作らないため。

### 5.6 画像が出ない・ログインできない

管理画面 **「外部サービス」** から `画像の保管先` / `ログイン` を開く。
**この 2 つは、この画面からは変更できない**（配備環境の設定が正）。
見られるのは次のとおり。

```
1. 「使っている方式」を確かめる（r2 / local、supabase / dev）
2. 「設定が足りません」と出ていれば、足りない設定の名前が並ぶ
   → 配備環境（Vercel / Fly）に設定して入れ直す
3. 「接続を確かめる」で、公開されている場所へ届くかを見る
   → 画像なら配信元、ログインなら鍵束の置き場
```

⚠️ **確かめられるのは到達性まで。** 保管先への書き込みや、ログインの検証が
うまくいくかどうかは分からない。

⚠️ **ログインの設定をこの画面に置いていないのは、意図的。**
誤ると全員が入れなくなり、直す手段がログインの先にある。

### 5.7 誰が何をしたのかを調べたい

管理画面 **「操作の記録」**（`/admin/audit-logs`）。必要な権限は `audit_log.view`
（`operator` と `auditor`）。「操作の種類」に `staff` や `integration` のように
先頭を入れて絞り込む。

⚠️ **メールアドレスはオーナー以外には伏せて表示される。**
記録そのものは残っているので、必要なときはオーナーが確認する。

⚠️ **この画面から記録を消したり直したりはできない。** 経路そのものが無い。

### 5.8 在庫（発行上限）の不整合を疑うとき

```sql
-- reserved_count が実際の pending 注文と一致するか
SELECT a.id, a.reserved_count,
       COALESCE(SUM(ol.quantity), 0) AS actual_reserved
  FROM artworks a
  LEFT JOIN order_lines ol ON ol.artwork_id = a.id
  LEFT JOIN orders o ON o.id = ol.order_id AND o.status = 'pending'
 GROUP BY a.id
HAVING a.reserved_count <> COALESCE(SUM(ol.quantity), 0);

-- issued_count が entitlements 件数と一致するか
SELECT a.id, a.issued_count, COUNT(e.id) AS actual_issued
  FROM artworks a LEFT JOIN entitlements e ON e.artwork_id = a.id
 GROUP BY a.id HAVING a.issued_count <> COUNT(e.id);
```

🟡 **仮決定:** この整合性チェックを**日次で自動実行**し、
不一致があればアラートする。カウンタのずれは静かに進行するため。

## 6. デプロイ

🟡 **仮決定:**

| 原則         | 内容                                                                        |
| ------------ | --------------------------------------------------------------------------- |
| 順序         | DB マイグレーション → api → worker → web                                    |
| 互換性       | マイグレーションは**後方互換**（expand → migrate → contract）               |
| worker       | 新旧が同時に動いても壊れないこと（ジョブの取得は排他制御済み）              |
| ロールバック | アプリは前バージョンへ戻せる。**DB は前方向のみ**（データ損失を避けるため） |

> ⚠️ **DB を戻す前提のデプロイをしない。** 発行記録は再現不能な資産である。
> 「戻せないマイグレーション」を打つ前に、必ずバックアップと復旧手順を確認する。

❓ **未決定 `UD-1103`:** バックアップの取得間隔・保持期間・復旧目標（RPO/RTO）。

## 7.1 全額返金にともなう取り消し（M3a）

### フラグ（3 本）

⚠️ **1 本にまとめない。** 止めたい対象が 3 段あるため。まとめると、
送信だけ止めたい場面で生成まで止まり、**止めていた期間の返金が永久に
相手へ伝わらなくなる**。

| 環境変数                                     | 役割                                             | 既定    |
| -------------------------------------------- | ------------------------------------------------ | ------- |
| `REFUND_REVOKE_CLAIMED_ENABLED`              | `claimed → revoked` を行うか                     | `false` |
| `WALLET_REVOCATION_EVENT_GENERATION_ENABLED` | 取消イベントを**作る**か（**日次の補完も従う**） | `false` |
| `WALLET_REVOCATION_EVENT_DELIVERY_ENABLED`   | 取消イベントを**送る**か                         | `false` |

- `"true"` の完全一致だけを有効とする。`"1"` や `"TRUE"` は**黙って無効に
  倒さず起動を拒否する**（綴り違いで「有効にしたつもりが無効」を防ぐ）。
- 配送には既存の `WALLET_DELIVERY_ENABLED`（ワーカーの親スイッチ）も要る。
  取消の配送だけ有効にすると**起動時に拒否**する（1 件も送られないため）。
- 取消の配送を止めても、**付与の配送は止まらない**。

### 通常のロールバック（データを消さない）

| 段  | 操作                                               | 効果                                                             |
| --- | -------------------------------------------------- | ---------------------------------------------------------------- |
| 1   | `WALLET_REVOCATION_EVENT_DELIVERY_ENABLED=false`   | 送信のみ停止。行は残り、復旧後に再送できる                       |
| 2   | `WALLET_REVOCATION_EVENT_GENERATION_ENABLED=false` | 生成停止（**日次の補完も止まる**）。取りこぼしは後述の補完で回収 |
| 3   | `REFUND_REVOKE_CLAIMED_ENABLED=false`              | `claimed → revoked` を停止。**返金自体は従来どおり完了する**     |
| 4   | コードを revert                                    | 1〜3 で足りない場合のみ                                          |

### ⚠️ DB 制約は戻さない

**自動ロールバック手順に「CHECK 制約を旧状態へ戻す」操作を含めない。**
`claimed → revoked` の行が 1 件でもできた後は、`ADD CONSTRAINT` が既存行の
検証で失敗し、**ロールバック自体が途中で止まる**。

どうしても戻す必要が生じた場合は、**既存データの扱いを含む個別の移行計画**
として別途承認を得る（データの削除・null 化を伴うため）。

### 後戻りの境目は 2 段階

|          | 境目                                              | 発生条件                                                       | 戻せなくなるもの                                  |
| -------- | ------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------- |
| **第 1** | `claimed → revoked` が本番で **1 件発生**した時点 | `REFUND_REVOKE_CLAIMED_ENABLED` を有効にした後の最初の全額返金 | **CHECK 制約を旧状態へ単純に戻せない**            |
| **第 2** | 取消イベントが Wallet へ **1 件配送**された時点   | 配送フラグを有効にした後                                       | **Market だけ戻しても Wallet 側に取消状態が残る** |

⚠️ **有効化の Go 承認時に、この 2 段階を読み合わせる。**

### 取りこぼしの補完

生成フラグが無効だった期間に全額返金が起きると、取消イベントは作られない。
あとから拾い直す。

```
# 数えるだけ（既定）
pnpm wallet:revocation-backfill

# 実際に積む。⚠️ 生成フラグが有効でなければ拒否する
pnpm wallet:revocation-backfill --execute --limit=200
```

⚠️ **補完はフラグを迂回しない。** 先に生成フラグを有効にしてから実行する。
「止めたはずのものが別の入口から動く」状態を作らないため。

日次の `POST /api/v1/internal/jobs/reconcile-revocations` も同じ処理を行い、
**同じく生成フラグに従う**。

### 適用順序（DB 先行）

⚠️ **マイグレーションを、コードのデプロイより先に当てる。** 逆にすると、
新コードが本番に出ているのに enum も新制約も無い時間が生まれる。

| 環境          | 順序                                                                                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ステージング  | ①事前検証 → ②マイグレーション適用 → ③コードをデプロイ → ④3 フラグ OFF で起動確認 → ⑤Wallet 側の契約テスト（`event_version=1.1` / `reason_code`）→ ⑥レビュー承認 |
| 本番          | ①事前検証 → ②**マイグレーション適用（コードより先）** → ③旧コードが新制約・新 enum で動くことを確認 → ④マージ → ⑤デプロイ → ⑥3 フラグ OFF を確認                |
| 後日（別 Go） | ⑦`REFUND_REVOKE_CLAIMED_ENABLED` → ⑧生成フラグ → ⑨補完を実行 → ⑩配送フラグ                                                                                      |

⚠️ **マイグレーション適用と本番フラグ変更を同じ作業にしない。**

### 監視

| 見るもの                                                 | 意味                                                                                                |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `operations_reviews` の未対応件数                        | 機械が決められなかったことが溜まっていないか                                                        |
| `wallet_delivery_outbox` の `SUPERSEDED` 件数            | 取消に追い越された付与。異常ではない                                                                |
| `REFUND_REVOKE_CLAIMED_ENABLED=true` かつ生成 OFF の期間 | ⚠️ **Wallet との不整合が溜まる。** 長く置かない。手順⑦〜⑧は同じ作業枠で速やかに行い、補完で回収する |

## 8. リポジトリ

✅ **事実:** 本プロジェクトの正式なリポジトリは `stockbusiness/sennokunnft`。
既存システムのリポジトリとは分離しており、コードの流用は行わない。

## 9-4. Phase 3 の前提づくり（保証を手順から構造へ）

実行環境: Node.js v22.22.2 / pnpm 9.15.4 / PostgreSQL 16.14 / 実行日 2026-08-13

決済事業者（`UD-702`）や税（`UD-401`）が未決定でも進められる部分を先に片付けた。
どちらも Phase 2 で「運用でカバーする」「Phase 3 で移す」と書いて先送りしていたもので、
**先送りの理由が「今はまだ壊れていない」だったため、壊れる前に閉じた。**

### 1. 「非公開なのに販売中の出品がある」を作れなくした

Phase 2 では出品側にトリガを置き、非公開の作品に有効な出品を**作れない**ようにしていた。
しかし作品側には何も無く、`published → archived` にするだけで
**有効な出品が非公開の作品を指す状態が成立していた。**
トリガが防ごうとしていた状態そのものを、別の入口から作れていたことになる。

実 PostgreSQL で到達可能なことを確認したうえで、次の 3 段にした。

| 段  | 何をするか                                                                | 位置づけ           |
| --- | ------------------------------------------------------------------------- | ------------------ |
| 1   | ドメイン関数が作品と出品の遷移をまとめて決める                            | 正しい手順を楽に   |
| 2   | リポジトリが**同一トランザクション**で書く                                | 途中で落ちない     |
| 3   | トリガ `artworks_no_effective_listings_when_unpublished` が他の経路を拒否 | **保証はここだけ** |

マイグレーションでは、既に成立してしまっている行を先に修復してからトリガを張る。
トリガは既存行を検証しないため、これを飛ばすと
「制約はあるのに違反した行がある」状態が残る。

**制約は「作れないこと」だけでなく「残らないこと」まで見ないと守れない。**

### 2. 冪等キーを DB へ移し、「先に占有する」方式にした

保存先の変更（メモリ → DB）だけでなく、**判定の順序**を変えた。

| 方式                      | 同時に 2 本来たとき                  |
| ------------------------- | ------------------------------------ |
| 探す → 無い → 実行（旧）  | 両方が「無い」を見て**両方実行する** |
| 先に占有 → 取れた側が実行 | 取れるのは 1 本だけ                  |

読み取りと書き込みのあいだの隙間は `if` では塞げない。占有は一意制約が決める。

実 PostgreSQL に対して 8 本同時に取り合わせ、占有できたのが 1 本だけであることを確認した。

失敗時の扱いは非対称にしてある。

- **本体が失敗したら解放する。** 解放しないと、一度失敗しただけのキーが
  期限切れまで塞がり、利用者がやり直せなくなる
- **結果の記録に失敗しても解放しない。** 本体は成功しているので、解放すると
  やり直しで本体がもう一度走る。塞がったままなら「やり直せない」で済むが、
  解放すると「二重に実行される」

## 9-7. Claim API のレート制限（`UD-601`）検証結果

実行環境: Node.js v22.22.2 / pnpm 9.15.4 / 実行日 2026-08-14

| #   | 検査項目                               | 結果                              |
| --- | -------------------------------------- | --------------------------------- |
| 1   | 上限を超えると `429` ＋ `RATE_LIMITED` | ✅                                |
| 2   | `Retry-After` を秒で返す               | ✅ 切り上げ・最低 1 秒            |
| 3   | `GET` と `POST` が別枠                 | ✅ GET が枯れても POST は通る     |
| 4   | **署名に失敗した要求は枠を消費しない** | ✅ 締め出しに使えない             |
| 5   | 既定値が 5 秒ポーリングを妨げない      | ✅ 毎分 12 回で余裕あり           |
| 6   | 窓が変わればまた通る                   | ✅                                |
| 7   | 拒否した要求も数える                   | ✅ 超過分を受け続けない           |
| 8   | 窓の開始時刻が送信のたびに動かない     | ✅ 永久に拒否される状態を作らない |

### 設定

| 対象            | 既定値（1 分・鍵IDごと） | 環境変数                        |
| --------------- | ------------------------ | ------------------------------- |
| `GET` 状態取得  | 3000                     | `CLAIM_RATE_LIMIT_GET_PER_MIN`  |
| `POST` 受取確定 | 300                      | `CLAIM_RATE_LIMIT_POST_PER_MIN` |

### 運用上の注意

⚠️ **台数を増やすと、実効の上限が台数倍になる。**
数を覚えているのがプロセス内メモリのため、各プロセスは自分の分しか知らない。
2 台なら 2 倍まで通る。nonce や冪等キーのように「効かなくなる」のではなく
**静かに緩む**ので、**壊れていることが外から見えない。**

台数を増やすときは、次のどちらかを行う。

1. 上限値を台数で割る（`CLAIM_RATE_LIMIT_*` を変更する）
2. 共有の実装へ差し替える（`RateLimiterPort` の実装を入れ替えるだけ）

置き場所（Redis / DB）はホスティング（`UD-1101`）が決まってから選ぶ。
1 リクエストごとに共有ストアへ往復すると、その書き込み自体が負荷の増幅になるため、
台数が決まる前に先回りしない。

⚠️ **`GET` の値を実利用より小さくしない。**
OVEW Wallet の Claim 画面は `DELIVERY_PENDING` のあいだ **5 秒間隔で
ポーリングする既存実装**（1 セッションあたり毎分 12 回）。既定の 3000 なら
同時 250 セッションまで耐えるが、ここを絞ると**攻撃ではなく正規の利用者が弾かれる。**
しかも症状は「受け取り画面が進まない」であり、レート制限が原因だと気づきにくい。
値を下げるときは、同時セッション数の見積もりと突き合わせる。

⚠️ **窓の境目では短時間に上限の 2 倍まで通りうる**（固定窓のため）。
上限が実利用より桁で大きいうちは問題にならない。実利用へ近づけるときに思い出すこと。
