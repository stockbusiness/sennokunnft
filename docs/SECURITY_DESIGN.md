## 1. 守るべき資産

🟡 **仮決定:** 優先度の高い順に整理する。

| 優先 | 資産                     | 毀損した場合の影響                                 |
| ---- | ------------------------ | -------------------------------------------------- |
| 1    | **署名鍵・Mint実行権限** | 不正なトークンが無制限に発行されうる。**回復不能** |
| 2    | **受取権（Claim権限）**  | 他人の購入分を奪取される。金銭被害＋信頼失墜       |
| 3    | 決済Webhookの真正性      | 未払いで商品が発行される                           |
| 4    | 購入者の個人情報         | 法令上の報告義務・信頼失墜                         |
| 5    | 在庫（発行上限）         | 発行上限を超えた発行。作品価値の毀損。**回復困難** |
| 6    | 監査証跡                 | 事故時に原因を追えない                             |

> 1と5は**取り返しがつかない**（オンチェーンに書かれたものは消せない）。
> ここに最も厚く防御を置く。

## 2. 脅威モデル

STRIDE で整理する。

| 脅威                            | 具体例                                 | 対策                                                                                    |
| ------------------------------- | -------------------------------------- | --------------------------------------------------------------------------------------- |
| **S**poofing<br>なりすまし      | 他人としてClaimする                    | 認証必須＋購入者ID一致検証（[AUTHORIZATION_DESIGN.md](./AUTHORIZATION_DESIGN.md) §2.4） |
|                                 | 決済完了Webhookの偽造                  | 署名検証必須。検証前に一切処理しない                                                    |
| **T**ampering<br>改竄           | 価格を書き換えて安く購入               | 価格は**サーバー側でlistingから取得**。リクエストの価格を信用しない                     |
|                                 | 数量を負数・巨大値にする               | サーバー側の zod 検証＋DB CHECK 制約                                                    |
|                                 | JWT の改竄・`alg: none`                | 署名検証＋許可アルゴリズム明示                                                          |
| **R**epudiation<br>否認         | 「注文していない」                     | `audit_logs` と `outbox_events` に不変の記録                                            |
| **I**nfo disclosure<br>情報漏洩 | 他人の注文を ID 指定で閲覧（IDOR）     | 所有権チェックを全リソースで実施                                                        |
|                                 | ログにトークン・個人情報が出る         | ロガーで自動マスキング（§4）                                                            |
|                                 | Claim URL の漏洩                       | トークンだけでは Claim できない（本人性は認証で担保）                                   |
|                                 | エラー応答から内部構造が漏れる         | エラー本文を定型化。スタックトレースを返さない                                          |
| **D**oS                         | 在庫の枯渇攻撃（注文だけして払わない） | 仮引当に期限を設け自動解放＋レート制限                                                  |
|                                 | Claim トークンの総当たり               | 十分な乱数長＋レート制限＋404統一                                                       |
| **E**oP<br>権限昇格             | buyer が operator API を呼ぶ           | 既定 deny のミドルウェア一括保護                                                        |
|                                 | JWT クレームのロール偽装               | **ロールはDBを正とし、トークンから読まない**                                            |

## 3. 秘密情報の取り扱い

### 3.1 リポジトリ

✅ **事実:**

- 秘密情報をリポジトリへ保存しない。
- `.env.example` には**変数名と説明のみ**を記載する（値・サンプル値・ダミー鍵も置かない）。

🟡 **仮決定:** 次で機械的に担保する。

| 対策                   | 実装                                                           |
| ---------------------- | -------------------------------------------------------------- |
| `.gitignore`           | `.env`, `.env.*`（`.env.example` を除く）, `*.pem`, `*.key`    |
| CI での秘密検出        | GitHub Actions に gitleaks 相当のスキャンを追加（🟡 `UD-901`） |
| GitHub Secret Scanning | リポジトリ設定で有効化（要リポジトリ管理者）                   |

❓ **未決定 `UD-901`:** 秘密検出ツールの選定（gitleaks / trufflehog / GitHub 標準）と
組織のセキュリティポリシー。Phase 1 CI では**`.env` 系ファイルの混入検査**と
`.env.example` に値が書かれていないことの検査を自前スクリプトで実装し、
本格的なスキャナ導入は決定後とする。

### 3.2 秘密鍵（最重要）

✅ **事実:** 今回、**秘密鍵の生成・保存を行わない**。

🟡 **仮決定（将来に向けた原則）:**

1. **アプリケーションのプロセスに秘密鍵を持たせない。**
   環境変数に秘密鍵を置く方式は、ログ・コアダンプ・プロセス一覧から漏れうる。
2. 署名は **KMS / HSM / 管理型カストディサービス**に委譲し、
   アプリは「署名を依頼する権限」だけを持つ。
3. 万一の漏洩に備え、**鍵のローテーションと失効の手順**を先に決める。

❓ **未決定 `UD-902`:** 鍵管理方式。[BLOCKCHAIN_DECISION_RECORD.md](./BLOCKCHAIN_DECISION_RECORD.md) の
カストディ選定（`UD-502`）と一体で決める。**決まるまで Mint を実装しない。**

### 3.3 環境変数

🟡 **仮決定:** すべての環境変数を `packages/config` の zod スキーマで定義し、
**プロセス起動時に一括検証**する。

- 検証に失敗したら**即座に異常終了**する（不完全な状態で動かさない）。
- エラーメッセージには**変数名のみ**を出し、**値を出さない**。
- `process.env` への直接アクセスを ESLint で禁止し、必ず検証済みオブジェクト経由にする。

```
✗ FAIL  環境変数の検証に失敗しました:
  - DATABASE_URL: Required
  - PAYMENT_WEBHOOK_SECRET: Required
```

> ⚠️ 「値が不正です: `postgres://user:pass@...`」のように**値をエラーに含めない**。
> 起動ログは広く共有されるため、そこに秘密が載る。

## 4. ログ

✅ **事実:** ログにトークン・秘密鍵・個人情報を出力しない。

🟡 **仮決定:** ロガー（`packages/observability`）で**構造的に防ぐ**。

| 対策             | 内容                                                                                                                                                                              |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 自動マスキング   | キー名が秘匿パターンに一致する値を `[REDACTED]` に置換                                                                                                                            |
| 秘匿パターン     | `password`, `token`, `secret`, `authorization`, `cookie`, `apiKey`, `privateKey`, `claimToken`, `email`, `phone`, `address`, `card`, `signature` 等（部分一致・大文字小文字無視） |
| 深いオブジェクト | 再帰的にマスク。配列内も対象                                                                                                                                                      |
| 既定の出力       | JSON。`message` に生の入力値を埋め込まない                                                                                                                                        |
| 相関ID           | `requestId` を全ログに付与し、値そのものを出さずに追跡できるようにする                                                                                                            |

> ⚠️ **「開発時だけ詳細ログ」を作らない。** 環境差でマスキングを緩めると、
> 設定ミスで本番に適用される。マスキングは常時有効にする。

🟡 **仮決定:** 個人情報を業務上ログに残す必要が出た場合は、
**ハッシュ化した識別子**（例: `emailHash` の先頭8文字）を使い、平文を残さない。

⚠️ **`emailHash` は鍵付き HMAC である**（`EMAIL_LOOKUP_PEPPER`。`UD-121`）。
素の SHA-256 にしない。メールアドレスは取りうる値が狭く、よくあるアドレスを
並べた表と突き合わせれば元に戻せる。それでは平文を持たない意味が無い。

⚠️ **照合値そのものも監査ログへ残さない。** 元へは戻せないが、手元の
アドレスを同じ鍵で変換すれば一致を確かめられる。監査ログは閲覧範囲が広く、
長く残る。残してよいのは「誰が、いつ、メールからの照合を使ったか」までである
（`order.buyer_lookup`）。

## 4-A. 外部連携の資格情報（管理画面・外部連携 指示書 §6）

✅ **決定 2026-08-18:** 運営中に交換する外部サービスの資格情報だけを、
**暗号化して DB に持つ**。それ以外の秘密は今までどおり配備環境の Secret に置く。

### 置き場の分け方

| 種類                               | 置き場             | 例                                                               |
| ---------------------------------- | ------------------ | ---------------------------------------------------------------- |
| 基盤の秘密（消えると起動できない） | 配備環境の Secret  | `DATABASE_URL`、`AUTH_DEV_SECRET`、`INTEGRATION_ENCRYPTION_KEYS` |
| 運営中に交換する外部API資格情報    | 暗号化して DB      | OVEW Wallet の HMAC 鍵、APIキー                                  |
| 公開してよい設定                   | 通常の設定テーブル | 接続先URL、待ち時間、再送回数                                    |

⚠️ **管理画面から `.env` や配備環境の環境変数を書き換える機能は作らない**（指示書 §6.3）。
書き換えられると、画面を取られた時点で基盤ごと乗っ取られる。

### 暗号方式

- **AES-256-GCM**（Node 標準の `crypto`）。独自方式は作らない。
- **鍵は DB に置かない。** `INTEGRATION_ENCRYPTION_KEYS` に
  `version:base64鍵` の並びで持ち、配備環境の Secret から渡す。
- **`key_version` を必ず持つ。** 鍵を交換したあとも、古い version で
  包まれた行を読めなければならない。
- **結び付け情報（AAD）に `service:environment` を入れる。**
  これにより、staging の暗号文を production の行へ貼り替えても復号が失敗する。
  DB を触れる人にだけできる攻撃を、暗号の側で塞ぐ。

### 再表示しない

⚠️ **登録済みの資格情報を返す経路を作らない。** 復号してよいのは
送信アダプタ（`revealForAdapter`）だけで、一覧や詳細から辿れない。
API が返すのは `status` / `lastFour`（末尾 4 文字）/ `keyVersion` /
`activatedAt` まで。

⚠️ **暗号鍵を失ったら、資格情報は復旧しない。** 再表示できない設計なので、
その場合は各外部サービス側で新しい資格情報を発行し直す。
`INTEGRATION_ENCRYPTION_KEYS` を消さないこと。

### 交換の手順

「登録 → 待機 → 接続テスト → 有効化」の順に進む。

⚠️ **登録と同時に有効化しない。** 間違った値を入れた瞬間に連携が止まり、
しかも元の値は再表示できないため戻せない。**戻せる状態を必ず経由させる。**

⚠️ **有効なものは用途ごとに 1 件だけ。** 部分UNIQUE が担保する。
2 件あると、どちらで署名したのか分からなくなる。

### 監査ログ

値ではなく、移り変わりを残す（指示書 §10）。

```text
未設定 → 設定済み
末尾識別子 ****7K9P → ****2ABC
```

⚠️ **接続先の値も残さない。** ホスト名も業務上の秘密になりうる。
残すのは「変えたかどうか」だけ。

## 5. 入力検証

✅ **事実:** 入力値はサーバー側で検証する。

🟡 **仮決定:**

| 対象                            | 方式                                                                    |
| ------------------------------- | ----------------------------------------------------------------------- |
| HTTP ボディ・クエリ・パラメータ | zod スキーマ（`packages/contracts`）。**未知フィールドは除去**（strip） |
| 数値                            | 型・範囲・整数性を明示。`Number.isSafeInteger` で上限も確認             |
| ID                              | UUID 形式を検証。文字列連結でSQLを作らない（Prisma 経由）               |
| 画像アップロード                | MIME・拡張子・サイズ上限・マジックナンバーを検証（🟡 Phase 2）          |
| リダイレクト先                  | 許可リスト方式。任意URLへリダイレクトしない                             |

> ⚠️ **クライアント検証は UX のためのもの**であり、セキュリティ境界ではない。
> 同じスキーマを両側で使うが、**サーバー側の実行を省略しない**。

## 6. Webhook

✅ **事実:** 外部Webhookは署名検証を前提とする。

🟡 **仮決定:** 受信処理の必須手順。

| #   | 手順                       | 注意                                                |
| --- | -------------------------- | --------------------------------------------------- |
| 1   | **raw body** を取得する    | JSON パース後の再シリアライズでは署名が一致しない   |
| 2   | 署名を検証する             | **タイミング安全な比較**（`timingSafeEqual`）を使う |
| 3   | タイムスタンプの鮮度を確認 | 🟡 5分を超えたものは拒否（リプレイ攻撃対策）        |
| 4   | `webhook_events` に INSERT | 一意制約違反 = 既受信 → **即 200 で終了**           |
| 5   | 業務処理                   | 重い処理は Outbox へ逃がす                          |
| 6   | `processed_at` を更新      |                                                     |

> ⚠️ **署名検証の前に本文を解釈しない。** ログ出力すらしない。
> 検証前の本文は攻撃者が自由に制御できるデータである。

> ⚠️ 業務エラーで 5xx を返さない。送信元が再送を繰り返し、
> 二重処理の検証負荷とアラート疲れを招く。

## 7. 冪等性（セキュリティ観点）

✅ **事実:** 冪等性をドメイン設計に組み込む。
✅ **事実:** 1つの受取権から複数Mintできない設計にする。

🟡 **仮決定:** 冪等性を**アプリのif文で担保しない**。

| 保護対象         | 担保手段                                                                        |
| ---------------- | ------------------------------------------------------------------------------- |
| Webhook 二重処理 | `webhook_events` の UNIQUE 制約                                                 |
| 二重注文         | `orders` の UNIQUE(account_id, idempotency_key)                                 |
| **多重 Claim**   | 条件付きUPDATE（`WHERE status='issued'`）の更新行数判定                         |
| **多重 Mint**    | `nft_tokens` の UNIQUE(entitlement_id) ＋ `mint_jobs` の UNIQUE(entitlement_id) |
| ジョブの多重実行 | `FOR UPDATE SKIP LOCKED` による排他取得                                         |

> 「読んで、判定して、書く」（read-check-write）は競合状態で破れる。
> **DB の制約または条件付きUPDATEの更新行数**で判定する。
> 詳細は [DATABASE_DESIGN.md](./DATABASE_DESIGN.md) §4、[LAZY_MINT_FLOW.md](./LAZY_MINT_FLOW.md)。

## 8. Claim トークン

🟡 **仮決定:**

| 項目         | 決定                                           | 根拠                           |
| ------------ | ---------------------------------------------- | ------------------------------ |
| 生成         | CSPRNG（`crypto.randomBytes`）で 32 バイト     | 予測不能性                     |
| 符号化       | base64url                                      | URL 安全                       |
| 保存         | **SHA-256 ハッシュのみ**。平文をDBに保存しない | DB 漏洩時に Claim されないため |
| 照合         | 入力をハッシュ化して一致検索                   |                                |
| 露出         | ログ・イベント・エラー本文に出さない           | §4 のマスキング対象            |
| 単独での権限 | **なし。** 認証＋購入者一致が別途必要          | 多層防御                       |

> ⚠️ `Math.random()` を使わない。ESLint ルールで禁止する。

### 8.1 紛失時の復旧（`UD-1009` 未決定・**本番前必須**）

✅ **事実:** 平文を保存していないため、**利用者が Claim URL を失うと再表示できない。**
これは設計として正しいが、**復旧手段が無いままでは運用できない。**
受け取れないまま問い合わせが来たとき、運営側に打つ手が無い。

🟡 **仮決定:** 「再表示」ではなく「**再発行**」で復旧する。

```text
購入者がログイン → マイページ → Claim URL 再発行
  → 旧 Token を失効させる
  → 新 Token を生成し claim_token_hash を差し替える
  → 新しい Claim URL を表示する
```

⚠️ **旧 Token を必ず失効させる。**
新しい URL を出すだけで古い方を生かしておくと、
**漏れた URL がそのまま有効な受取口として残る。**
再発行は「新しい経路を足す」操作ではなく、「経路を差し替える」操作。

⚠️ **再発行そのものを認可の穴にしない。**
再発行できるのは購入者本人だけであり、
**ログイン済みであることをサーバー側で確かめてから**行う。

✅ **実装済み（2026-08-14）:** `POST /api/v1/entitlements/{id}/claim-token`。

| 守っていること           | 方法                                                      |
| ------------------------ | --------------------------------------------------------- |
| 旧 URL が残らない        | `claim_token_hash` を差し替える（同じ列なので併存しない） |
| 本人以外が再発行できない | `claim.reissue` は buyer のみ＋所有権をサーバー側で確認   |
| **運営が代行できない**   | 免除（bypass）を与えていない                              |
| 受取済みを再発行できない | 条件付き UPDATE に `status = 'issued'` を含める           |
| 使えない URL を渡さない  | 現在のハッシュを条件にし、**書けた側だけが成功を名乗る**  |
| 平文が残らない           | 応答に 1 回だけ。ログ・監査・イベントへ出さない           |

⚠️ **「新しい URL を出す」と「古い URL を止める」を別々にしない。**
2 つの操作に分けると、片方だけ成功した状態が作れる。
差し替えは 1 つの UPDATE で行い、**成否をひとつの結果として扱う**。

⚠️ **同時に 2 本走ったとき、負けた側に「発行できました」と返さない。**
保存できるハッシュは 1 つなので、負けた側のトークンは**作られた瞬間から
無効**。渡せば「開かない URL」を掴ませることになる。

❓ **未決定 `UD-1009`（残り）:** 再発行の**回数制限**と、**運営代行の可否**。
回数制限は未実装。本人しか呼べず、呼ぶたび自分の古い URL が無効になるだけなので
他人への実害は無いが、**本番運用の前に上限の要否を決める。**
運営代行は、決まるまで**経路そのものを作らない**方針にしてある。

## 9. Web アプリ側の対策

🟡 **仮決定:**

| 対策                     | 内容                                                                          |
| ------------------------ | ----------------------------------------------------------------------------- |
| CSP                      | `default-src 'self'`。インラインスクリプトは nonce 方式                       |
| HSTS                     | `max-age=31536000; includeSubDomains`                                         |
| `X-Content-Type-Options` | `nosniff`                                                                     |
| `Referrer-Policy`        | `strict-origin-when-cross-origin`（**Claim URL がリファラで漏れるのを防ぐ**） |
| Cookie                   | `httpOnly` / `Secure` / `SameSite=Lax`                                        |
| CSRF                     | Cookie 認証の状態変更操作に CSRF トークンを要求                               |
| CORS                     | 既定は同一オリジンのみ。ワイルドカード（`*`）を使わない                       |

> ⚠️ **`Referrer-Policy` は Claim フローで特に重要。**
> Claim URL を開いたページから外部リンクを踏むと、
> 既定設定ではトークンを含む URL がリファラとして送信されうる。

❓ **未決定 `UD-903`:** 本番のオリジン（ドメイン名）が未定のため、
CSP / CORS の許可リストを確定できない。設定値は環境変数化しておく。

## 11. Phase 1 で実装するセキュリティ機構

✅ **事実:** 本 Phase で**実際にコードとして入るもの**は次に限る。

| #   | 機構                                         | 配置                     |
