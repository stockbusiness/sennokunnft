## 1. スコープ判断の原則

🟡 **仮決定:** 次の3原則でスコープを切る。

1. **一次販売のみ。** 二次流通・転売・ロイヤリティは MVP に含めない（✅ 指示により禁止）。
2. **オンチェーン依存を最後段に閉じ込める。** チェーン仕様が未決定（[BLOCKCHAIN_DECISION_RECORD.md](./BLOCKCHAIN_DECISION_RECORD.md)）
   でも、それ以外は完成できる構造にする。
3. **1受取権 = 1トークン。** 数量を持つ「注文」ではなく、1枚単位の「受取権」を一級市民として扱う。

### 2.2 Phase 1 — Monorepo開発基盤（今回）

✅ **事実:** 実装するもの。

| 項目 | 内容 |
| --- | --- |
| pnpm workspace | `apps/*` `packages/*` の workspace 定義 |
| Turborepo | `lint` / `typecheck` / `test` / `build` のタスクグラフとキャッシュ |
| Next.js アプリ | `apps/web`。起動・ビルドできる最小構成 |
| NestJS API | `apps/api`。起動・ビルド・ヘルスチェックできる最小構成 |
| Worker | `apps/worker`。起動・グレースフルシャットダウンできる最小構成 |
| Prisma パッケージ | `packages/database`。schema と Client 生成。**マイグレーション適用は行わない** |
| 共通TypeScript設定 | `packages/config` の tsconfig プリセット |
| ESLint / Prettier | 共通設定と全パッケージへの適用 |
| 環境変数の型検証 | `packages/config` の zod スキーマ。不足時は起動失敗 |
| 構造化ログ | `packages/observability`。JSON出力＋秘匿値マスキング |
| APIヘルスチェック | `GET /healthz` `GET /readyz` |
| 単体テスト基盤 | Vitest。各パッケージで実行可能 |
| E2Eテスト最小構成 | Playwright。web のスモーク1本 |
| GitHub Actions | install → lint → typecheck → test → build → 循環依存検査 |

✅ **事実:** Phase 1 で**実装しないもの**。

NFT販売の本実装 / Stripe決済の本実装 / Claim の本実装 / ブロックチェーン Mint の本実装。

🟡 **仮決定:** ただし **ドメイン層の型・状態遷移・不変条件は Phase 1 で実装する**。
理由: これらはフレームワーク非依存の純粋関数であり、外部接続を一切伴わない。
Phase 2 以降の設計をコードで固定でき、テストで検証できる価値が大きい。
外部との境界はすべて**ポート（interface）＋ Fake 実装**に留め、実サービスへは接続しない。

## 3. In Scope / Out of Scope（MVP全体）

### 3.1 In Scope

| 領域 | 含むもの |
| --- | --- |
| 作品 | 作品登録、画像1枚、説明、発行上限 |
| 販売 | 固定価格出品、在庫（発行上限）管理、公開/非公開 |
| 決済 | カード決済1手段、Webhook による確定、冪等処理 |
| 受取権 | 1枚単位の発行、Claim URL、有効期限 |
| Claim | ログイン必須、購入者照合、1回限りの実行 |
| Mint | Claim 起点の非同期Mint、再試行、多重防止 |
| 表示 | 受取済み作品の一覧・詳細 |
| 運用 | 構造化ログ、ヘルスチェック、監査イベント記録 |

### 3.2 Out of Scope（MVPに含めない）

| 領域 | 除外理由 |
| --- | --- |
| 二次流通・転売・オファー・オークション | ✅ 指示により禁止 |
| ロイヤリティ分配 | 二次流通に付随するため |
| 外部ウォレット送信（トークンの外部アドレスへの移転） | ✅ 指示により禁止 |
| MetaMask 等のウォレット接続 | ✅ 指示により禁止 |
| 暗号資産決済 | 一次販売はカード決済のみ |
| 複数通貨 / 多言語 | 🟡 通貨・言語は単一。i18n の**器のみ**用意し翻訳は行わない |
| クーポン・割引・ポイント | 🟡 価格モデルを固定価格に限定するため |
| 紹介・アフィリエイト報酬 | 🟡 既存代理店システム側の責務。連携は Webhook で後付け（[EXTERNAL_INTEGRATION_POLICY.md](./EXTERNAL_INTEGRATION_POLICY.md)） |
| メール送信 | ❓ `UD-201` 送信基盤未定。イベントは発火させ、購読者は後付け |
| 定期購入・サブスクリプション | 一次販売のみのため |
| 作家による自己登録・入稿 | `UD-102` |

❓ **未決定 `UD-201`:** トランザクションメール（購入完了・Claim案内）の送信基盤と
差出人ドメイン。Claim URL をメールで送る運用なら必須だが、決まっていない。
MVP では「購入完了画面に Claim URL を表示する」経路を主とし、メールは
イベント購読者として後付けする設計にする。

## 4. スコープ外だが設計上の余地を残すもの

🟡 **仮決定:** 次は実装しないが、**データモデルと境界だけは将来拡張できる形にする**。
（YAGNI と拡張性のバランスとして、テーブル追加のみで対応でき、
既存レコードの移行が不要になる範囲に限定する。）

| 項目 | 残す余地 |
| --- | --- |
| 複数価格・セール価格 | `listing` を作品と分離し、1作品に複数 listing を持てる構造にする |
| 複数決済手段 | `payment` を注文から分離し、provider 識別子を持たせる |
| 複数チェーン | `mint_job` に `chain_id` 相当のフィールドを持たせる（値は未確定） |
| 外部システム連携 | ドメインイベントを永続化し、後から購読者を追加できるようにする |
