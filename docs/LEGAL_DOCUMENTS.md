# 法務文書の版管理（利用規約・プライバシーポリシー・特定商取引法に基づく表記）

**版**: 1.0 / **作成**: 2026-08-19 / **対象**: 運営者・開発者

---

## 1. なぜ普通のコンテンツと分けるのか

作品の説明文なら、直したら直った内容だけが残っていればよい。
法務文書は違って、**過去にどの版が有効だったか**が意味を持つ。

- 返金や苦情の場面で「そのご注文の時点では、こう書いてありました」と示せる必要がある
- 特商法の表記は**販売前に掲げる義務**がある。掲げていない状態で売ると、販売そのものが法に触れる
- 「あとから静かに書き換えられる」文書は、書いてあることの証明力を持たない

したがってこの機能は、**編集機能ではなく版管理**として作ってある。

---

## 2. 決めたこと

| 事項                   | 決定                                   | 理由                                                                      |
| ---------------------- | -------------------------------------- | ------------------------------------------------------------------------- |
| 公開済みの版の書き換え | **できない**                           | 書き換えられると、過去の版が失われ、上のことが成り立たない                |
| 削除                   | **できない**（口を作らない）           | 消せると、いつか「古いから」と消される。困るのは消したあと                |
| 状態                   | `draft` / `published` の 2 つだけ      | 「施行中」を状態にすると、日付が来ても誰かが切り替えるまで変わらない      |
| 「いま適用中」         | **施行日と現在時刻から毎回決める**     | 予約公開があるので「公開済み＝いま有効」ではない                          |
| 下書き                 | 種類ごとに **1 つだけ**（部分UNIQUE）  | 2 つあると、どちらを直しているのか操作する人に分からない                  |
| 版番号                 | 種類ごとの連番（1 から）               | 「規約 第3版」と言えるようにする。表全体の通し番号にしない                |
| 特商法の中身           | **12 項目の欄**（自由文 1 枚にしない） | 抜けているかどうかを機械が判定できる                                      |
| HTML                   | **保存の時点で断る**                   | 描画側で無視するだけだと、別の描画経路（メール・PDF）ができたときに流れる |
| 施行日                 | 過去にできない／現行版より後           | さかのぼれると、過去の注文に紐づく「その時点の版」が入れ替わる            |

### 権限

| 操作             | 必要な権限      | オーナーの印                 |
| ---------------- | --------------- | ---------------------------- |
| 版の一覧を見る   | `legal.view`    | 不要（閲覧者も可）           |
| 下書きを保存する | `legal.edit`    | 不要（運営スタッフが書ける） |
| **公開する**     | `legal.publish` | **必要**                     |

⚠️ 公開した版は取り消せず、書いた内容は購入者への約束になる。
**書く人と決める人を分ける**ため、公開だけをオーナーに限っている。

## 3. データ

`legal_document_versions`（migration `20260819130000_legal_documents`）。

| 縛り                                                       | 何を防ぐか                                                                                                                                                 |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `legal_document_versions_kind_valid`                       | 知らない種類の行                                                                                                                                           |
| `legal_document_versions_status_valid`                     | 知らない状態の行                                                                                                                                           |
| `legal_document_versions_published_complete`               | 施行日・公開日時・公開者の欠けた「公開済み」。あると、施行中の版を選ぶ問い合わせがそれを飛ばし、画面には「公開済み」と出ているのに利用者には古い文が見える |
| `legal_document_versions_body_shape`                       | 本文と特商法の項目が両方入った行（どちらが表示されるか実装依存になる）                                                                                     |
| `legal_document_versions_kind_version_key`                 | 同じ種類での版番号の重複                                                                                                                                   |
| `legal_document_versions_one_draft_per_kind`（部分UNIQUE） | 下書きが 2 つ以上                                                                                                                                          |
| `legal_document_versions_effective_from_key`（部分UNIQUE） | 同じ瞬間に 2 つ施行される（どちらが有効かが並び順まかせになる）                                                                                            |

⚠️ 部分UNIQUE は Prisma のスキーマでは表せない。**マイグレーションが正**。
この表を作り直すときは、必ず持っていくこと。

## 4. API

| メソッド | 経路                                | 権限                                       |
| -------- | ----------------------------------- | ------------------------------------------ |
| `GET`    | `/api/v1/legal/:kind`               | 公開（認証不要）。**施行中の版だけ**を返す |
| `GET`    | `/api/v1/admin/legal/:kind`         | `legal.view`                               |
| `PUT`    | `/api/v1/admin/legal/:kind/draft`   | `legal.edit`                               |
| `POST`   | `/api/v1/admin/legal/:kind/publish` | `legal.publish`（オーナー限定）            |

`:kind` は `terms` / `privacy` / `tokushoho`。

⚠️ **削除の経路は存在しない。**
⚠️ 下書きは種類ごとに 1 つなので、**下書きの ID を画面に持たせない**。
持たせると、古い画面から別の下書きへ書き込む余地が生まれる。

## 5. 画面

| 経路                                               | 用途                             |
| -------------------------------------------------- | -------------------------------- |
| `/legal/terms` `/legal/privacy` `/legal/tokushoho` | 公開ページ。フッタから常に辿れる |
| `/admin/legal`                                     | 3 種類の入口                     |
| `/admin/legal/:kind`                               | 下書きの編集・公開・これまでの版 |

- 本文は限られた印だけを解釈する（`## ` 見出し、`- ` 箇条書き、空行で段落）
- **HTML 文字列を組み立てない。** `renderLegalBody` が構造を返し、React の要素として描く
- 施行中の版が無ければ「準備中です」と出す。**空の文を作って取り繕わない**

## 6. 同意（`UD-126` 決定 2026-08-19）

### 何をどこで記録するか

**性質の違う 2 つを記録する。**

|                            | 何を                                               | 意味                                           |
| -------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| 会員登録（初回ログイン）時 | どの版に同意したか＋日時を `legal_consents` へ     | **同意**の記録                                 |
| 購入時                     | その時点の版番号を `orders.terms_version{,_id}` へ | 同意ではなく「**何が表示されていたか**」の記録 |

後者はこの案件のスナップショット原則（価格・手数料率・作品名を注文時点の値で保存する）
と同じ扱い。**登録時の記録だけでは足りない**——第1版のときに登録した人が、8 か月後に
第3版のもとで購入することが必ず起きるため。注文に版を残せば、「そのご注文の時点で
どう書いてあったか」に常に答えられる。

### 同意を求めるのは利用規約だけ

⚠️ **プライバシーポリシーを同じチェックへ束ねない。** 個人情報保護法では利用目的は
原則「公表」で足り、「同意」が要るのは第三者提供などの場面。束ねると、
**必要な同意が取れていないのに取れたつもりになる**。同意画面ではリンクで示すに留めている。

⚠️ **特商法表記は同意の対象ではない**（表示義務）。ただし返品特約は購入の最終確認画面へ
表示する必要がある（特商法12条の6）。これは同意とは別の作業として残っている。

DB 側でも `legal_consents_kind_valid` が `terms` 以外の行を拒否する。

### どこで求めるか

この構成には**会員登録の画面が無い**。登録もログインも同じマジックリンクで、
アカウントの行は初回ログインが通った時点（`/api/auth/confirm`）で作られる。
そのため同意の判定は**その confirm 経路**で行う。初回も 2 回目も必ず通る唯一の場所なので、
改定後の再同意も「次にログインしたとき一度だけ」求まる。

### 締め出しを作らない

⚠️ **規約が未公開なら、同意を求めない。**

求める作りにすると、立ち上げ時に誰もログインできない。規約を公開できるのは管理画面へ
入れる人で、その人がログインできなければ**永久に公開できない**。締め出しは復旧の
手立てが無いので、通す側へ倒してある。同じ理由で、**API から状態を確かめられないときも
求めない**（`consentRequired` は失敗したら `false`）。

「規約が無いまま販売しない」は、公開前の手順（`UD-111`）で守る。

### 再同意を求めるか

公開画面の**「この改定について、お客さまに再度ご同意いただく」**を、公開する人が立てる。

⚠️ **システムに判定させない。** 誤字を直しただけの改定で全員を止めると、同意の画面が
「とりあえず押すもの」になり、同意という記録の意味が薄れる。逆に重要な改定を機械が
「軽微」と判断してしまうのも避けたい。実質的な変更かどうかは、公開する人が判断する。

|                            |                                                                  |
| -------------------------- | ---------------------------------------------------------------- |
| 印が立った版が施行されると | その版より前に同意した人へ、次のログイン時に一度だけ求める       |
| 印が立っていなければ       | 新しい版が出ても求めない。ただし**注文には新しい版が記録される** |
| 施行日が来ていない版の印   | **効かない**。まだ効いていない条件に同意させない                 |

印は `legal_document_versions.requires_reconsent` に載る。⚠️ 下書きには立たない
（`legal_document_versions_reconsent_published_only`）。あとから立てられると
「いつから求め始めたのか」が版から読めなくなるため、公開のときにしか決められない。

### 読んでいない条件に同意させない

同意の記録は、**画面が見ていた版の ID を送らせる**。いま施行中の版と食い違えば
`LEGAL_CONSENT_VERSION_MISMATCH` で断り、画面の読み込み直しを促す。
サーバー側で黙って「いまの版」に差し替えると、利用者が読んだものと記録が食い違う。

二度押しは `(account_id, version_id)` の一意制約で吸収し、**最初に同意した日時を残す**。
上書きすると「いつ同意したのか」が動く。

### API

| メソッド | 経路                    | 権限                              |
| -------- | ----------------------- | --------------------------------- |
| `GET`    | `/api/v1/legal-consent` | `legal.consent`（会員なら誰でも） |
| `POST`   | `/api/v1/legal-consent` | `legal.consent`                   |

⚠️ 同意は本人が行う。**運営に代理の経路を与えていない。**

## 7. 購入の最終確認画面（特商法12条の6）

### なぜ画面に出すのか

通信販売では、**申込みの最終確認画面そのもの**に一定の事項を表示する必要があります
（特定商取引法 第12条の6）。特商法のページへのリンクを置くだけでは要件を満たしません。

⚠️ **返品特約は特に重い。** 最終確認画面に表示していないと、こちらの返品条件は効かず、
法定の解除権（8日間）が適用されます。別のページに「返品不可」と書いてあっても主張できません。

### 出しているもの

| 出どころ   | 項目                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| 注文       | 分量（数量）・販売価格（税込）                                             |
| 特商法表記 | 商品代金以外の必要料金・お支払い方法・お支払い時期・お引渡し時期・返品特約 |

⚠️ **12 項目すべては並べません。** 事業者の名称や所在地は特商法のページで足ります。
最終確認画面に並べるのは**この申込みの条件**にあたるものだけ。全部載せると読む気を失い、
いちばん大事な返品特約が埋もれます（`CHECKOUT_NOTICE_FIELD_KEYS`）。

⚠️ **たたんで隠しません。** 開かないと読めない形にすると、「表示した」と言えるかどうかが
怪しくなります。

### 掲げるものが無ければ売らせない

特商法表記が未公開、または最終確認画面に出す 5 項目のどれかが空欄なら、
**支払い口を作りません**（`SALES_SETUP_INCOMPLETE`）。表示義務を果たせない状態での通信販売は、
販売そのものが法に触れるためです。手数料率が 0 のときに作らせないのと同じ扱いです。

止める場所は 2 か所あります。

| 場所                                | 何をするか                                             |
| ----------------------------------- | ------------------------------------------------------ |
| 購入の確認画面                      | 申し込みボタンを出さず「購入準備を行っています」と表示 |
| `POST /orders/:id/checkout-session` | `SALES_SETUP_INCOMPLETE` で断り、監査ログへ理由を残す  |

⚠️ **購入者に設定の中身を見せません。** 応答にも理由の詳細を載せず、監査ログにだけ
`TOKUSHOHO_NOT_PUBLISHED` を残します。

⚠️ **法務文書を繋いでいない配備でも売らせません。** 「確かめられないから通す」にすると、
表示義務を果たせないまま販売できてしまいます。配線の欠けは運営が直せますが、
法に触れた販売は取り消せません。

### 手元・E2E での扱い

手元と CI では、シードの運営アカウントに**オーナーの印**が付きます（`prisma/seed.ts`）。
印が無いと法務文書を公開できず、誰も印を配れないためです（昇格 API は無い＝`UD-803`）。
⚠️ シードは `APP_ENV=production` で実行を拒否します。

E2E は**本番と同じ経路（管理API）で特商法表記を公開してから**購入へ進みます。
中身は試験用の文字列で、実際の文面は `UD-111` の法務確認を経て管理画面から入力します。

## 8. まだできないこと

| 事項                                                                   | レジスタ |
| ---------------------------------------------------------------------- | -------- |
| 規約・プライバシーポリシーへの**同意記録**（いつ・どの版に同意したか） | `UD-126` |
| 改定を既存の購入者へ知らせる経路                                       | `UD-127` |
| 出品者ごとの特商法表記（マーケットとしての表示義務）                   | `UD-111` |

⚠️ 同意記録が無いということは、**「この購入者はこの版に同意した」と言えない**ということ。
同意をどの時点で取るか（会員登録／購入）と、改定時に再同意が要るかは業務の決定なので、
実装の前に決める必要がある（`UD-126`）。
