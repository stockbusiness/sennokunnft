## 3. 選択肢の整理（`UD-501` チェーン）

⚠️ 以下は**評価軸の提示**であり、推奨ではない。実際の数値は決定時点で再調査すること。

| 観点         | 評価すべき点                                            |
| ------------ | ------------------------------------------------------- |
| 手数料       | 1 Mint あたりの費用と変動幅。販売価格に対する比率       |
| 確定時間     | Claim から発行完了までの体感時間                        |
| 実績・安定性 | 稼働年数、障害履歴、チェーン停止時の影響                |
| ツール・SDK  | TypeScript から扱えるか、管理型サービスの選択肢があるか |
| 対外的な認知 | 購入者・パートナーへの説明のしやすさ                    |
| 撤退可能性   | 将来別チェーンへ移る場合の移行コスト                    |
| 法務・会計   | 当該チェーンの資産に関する国内の取扱い                  |

**カテゴリとしての選択肢:**

| カテゴリ                                              | 概要                           | 主なトレードオフ                           |
| ----------------------------------------------------- | ------------------------------ | ------------------------------------------ |
| A. パブリックEVM L1                                   | 最も一般的。ツールが豊富       | 手数料が高くなりうる                       |
| B. パブリックEVM L2                                   | 手数料が低い                   | L1 への依存、ブリッジの複雑さ              |
| C. 非EVM パブリックチェーン                           | 手数料・性能で有利な場合がある | ツール資産が使えない、人材確保             |
| D. 許可型／プライベートチェーン                       | 費用と統制で有利               | 「パブリックに検証可能」という価値が薄れる |
| E. **オフチェーン台帳のみ（当面チェーンを使わない）** | 最も低コスト・低リスク         | 「NFT」と称する妥当性の検討が必要          |

> **選択肢 E を最初から捨てない。** MVP の目的が
> 「デジタル作品を安全に販売し、所有を記録する」ことなら、
> オフチェーン台帳で始めて後からオンチェーン化する道がありうる。
> 本システムの設計（`nft_tokens` の不透明参照、`MintingPort`）は
> **E を選んでもそのまま動く**ようになっている。
> ただし「NFT」という呼称・訴求と整合するかは事業・法務判断（`UD-106`）。

## 4. 選択肢の整理（`UD-502` カストディ）

| 方式                                         | 概要                                                 | 利点                                                 | 欠点                                                      |
| -------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------- |
| C1. 完全カストディ（運営が一括保管）         | 運営の管理下で全トークンを保持し、DB上で所有者を管理 | 購入者に知識不要。✅「外部ウォレット送信なし」と整合 | 運営が単一障害点。法的性質の検討が必要                    |
| C2. アカウント単位のカストディウォレット     | 購入者ごとに管理型ウォレットを自動生成               | 将来の持ち出しに道が残る                             | 鍵管理の複雑さが増える                                    |
| C3. ノンカストディ（購入者自身のウォレット） | 購入者が鍵を持つ                                     | 運営の鍵リスクなし                                   | ✅ MetaMask連携が禁止。UI方針（Web3用語を出さない）と矛盾 |
| C4. 管理型カストディSaaS                     | 外部事業者に委託                                     | 鍵管理の専門性を借りられる                           | 事業者依存、費用、事業継続リスク                          |

> **C3 は今回のスコープと明確に矛盾する**（✅ MetaMask連携禁止、外部ウォレット送信禁止、
> Web3用語をUIに出さない）。実質的な候補は C1 / C2 / C4。
> ただしどれを選ぶかは `UD-902`（鍵管理）と `UD-106`（法務）に依存し、**本設計では決定しない**。

## 5. 決定を先送りしても実装を進められる構造

🟡 **仮決定:** チェーン仕様が未確定でも Phase 1〜4 を完了できるよう、次の分離を行う。

### 5.1 `MintingPort`（`packages/domain` が定義）

```ts
// 実際の型定義は packages/domain/src/ports/minting.port.ts
export interface MintingPort {
  /** 発行を依頼する。idempotencyKey により再送しても多重発行しない。 */
  submit(request: MintRequest): Promise<MintSubmission>;
  /** 依頼の現在状態を問い合わせる（コールバック非対応プロバイダ向け）。 */
  getStatus(submissionRef: string): Promise<MintStatus>;
}
```

- `MintRequest` は **チェーン非依存**。`entitlementId` / `idempotencyKey` /
  `metadataRef` / `recipientRef` のみを持つ。
- 戻り値の識別子は**すべて不透明文字列**。EVM のアドレス形式等を型で固定しない。

### 5.2 データベース

`nft_tokens` の `chain_ref` / `contract_ref` / `token_ref` / `owner_ref` は
**TEXT の不透明参照**。決定後に CHECK 制約や正規化を追加する。
（[DATABASE_DESIGN.md](./DATABASE_DESIGN.md) §3.10）

### 5.3 Phase 1 での実装

✅ **事実:** `FakeMintingAdapter` のみ実装する。

- 決定論的なダミー識別子を返す（テストで再現可能）。
- 実際のネットワーク通信を行わない。
- ✅ 本番ブロックチェーンへ接続しない。秘密鍵を扱わない。
